### 1.1 · M2 L6 — the drift diagnosis is inverted ✅ FIXED 2026-09-22

`lesson-06-two-sensor-following.mdx`, five places: the table at 46–52, the knowledge
check at 60–67, the explanation at 101–102, and the wrap-up at 177.

> `| Drifted left | 0.8 | 0.2 | +0.6 | steer left to correct |`

With black = 0.8 and white = 0.2 (M2 L1's convention), a left sensor reading 0.8
means the **line** is to the robot's left, which means the **robot** has drifted
**right**. So a positive error means drifted right, and the correction is to steer
left.

The table is also self-contradictory on its face: "drifted left … steer left to
correct" would drive the robot further off the line.

The code is fine — `arcade(base_effort, -correction)` does steer left, and
`arcade`'s positive turn is a right curve (M1 L6, M2 L5:52). So the robot behaves
correctly and every word explaining why is wrong. That's the worst kind of error to
leave in: nothing fails, and the student who reasons from the text gets a wrong
mental model that Module 3's turning logic then builds on.

*Verified: read M2 L1's 0.2/0.8 convention and M2 L5's arcade sign convention, then
traced the geometry.*

### 1.2 · M3 and M4 — `turn_right()` does not clear the intersection ⏸ DEFERRED (needs a robot)

The claim, in five places (M3 L3:66–69, L3:79, L3:86, M3 L4:90–91, L4:121, and again
M4 L8:125–127):

> "the turn methods already drive forward off the intersection as part of turning"

The actual method (M2 L10:153–158):

```python
def turn_right(self):
    self.drivetrain.set_effort(0.3, -0.3)
    time.sleep(0.5)
    while self.sensor.is_off_line():
        pass
    self.drivetrain.stop()
```

`set_effort(0.3, -0.3)` is one wheel forward, one back — a spin in place. There is
no forward travel anywhere in it, so the robot finishes the turn still sitting on
the intersection.

This matters beyond the wording, because M4 `Navigator.drive_path` (L8:114–123) is
built on it: it clears only in the *straight-ahead* case, on the grounds that turns
clear themselves. If the premise is false, every turn leg needs clearing too. **I
can't settle the behaviour from the source alone** — whether `track_until_cross()`
re-detects the cross it's standing on depends on sensor spacing and the cross
geometry. This one needs a robot on a real grid before it's rewritten.

*Verified: read the real method in M2 L10 and all six places that describe it.*

## 2. The Module 4 / Module 5 interchangeability claim

This is the module pair's stated pedagogical payoff, and it's the biggest structural
question in the course. The claim is that Dijkstra drops in for Manhattan because
they share an interface. What's actually there:

| | Manhattan (M4 L5) | Dijkstra (M5 L4) |
|---|---|---|
| Constructor | `__init__(self, start)` | `__init__(self, start, blocked)` |
| Grid size | any (pure arithmetic) | 4×4 only (hard-coded) |
| `compute_path(self, destination)` | start-excluded list | start-excluded list ✓ |
| Used by | created once, `position` synced each leg | re-created inside the loop (L5-7:138, L5-9:100) |

The method that matters does match. Around it, three things don't:

**The constructors differ**, so "drop-in replacement" (L5-4:20) and "same method
signature" (L5-6:166) overstate it. L5-6 is honest — it calls it a two-line swap —
but then the "before" code it shows uses `pathfinder = Manhattan((0,0))`, while the
program students actually wrote in M4 L9 names it `manhattan` throughout. So it's a
two-line swap against a program that doesn't exist.

**The position sync disappears.** M4 L9 calls `manhattan.position = navigator.position`
"the line nearly everyone misses". That line appears nowhere in Module 5, which
silently switches to re-creating the planner instead — the exact thing M4 L9 tells
students not to do.

**Module 5 never drives a robot with it.** `Navigator`, `drive_path`,
`track_until_cross` appear in Module 5 only in prose and quiz options; there is no
executable code joining the two. The payoff is asserted, never demonstrated.

My suggestion, in order of cost: give `Dijkstra.build_graph` `rows` and `cols`
(smallest fix, removes the impossible instruction in 1.5); make L5-6's "before"
match M4 L9's actual variable names and keep the position sync; and decide whether
Module 5 should end with a program that actually drives the grid, since right now the
capstone's loop has no drive call in it at all.

## 4. Convention drift

**`board.wait_for_button()` is missing from most robot programs outside Module 1 and 2.**
*(Scope narrowed 2026-09-23 — Brad: the wait belongs on programs students actually
run, not on illustrative snippets, where it only obscures the point. Counting any
block containing a drive call overstated this. M1 L8's Activity and M1 L12's
skeleton were fixed; M1 L10 and L11 turned out to need nothing.)*
Module 2 is good (9 of 10 top-level programs have it; the gaps are L2:148, L3:135,
L7:128). Module 3 has it in 2 of 8 robot-touching blocks. Module 4 has it in one
lesson. Since programs run the instant they upload, this is the rule with the most
direct physical consequence.

**`Kp` vs `kp`.** 25 occurrences of `Kp` (M2 L5, L6, L7, and a quiz option in L10)
against 4 of `self.kp` (L9, L10). The switch happens silently at L2-9. Now that
Lesson 1-9 teaches snake_case for variables and Capitalized for classes, `Kp` is a
rule violation the course itself created. Either rename to `kp` throughout, or keep
`Kp` and add one sentence that control gains are conventionally capitalized in
engineering — both are defensible, but the current split is not.

**`base_effort` drifts** from 0.3 (L2-5, L2-6, L2-7) to 0.4 (L2-9, L2-10) with no
comment, while L2-5's teacher note says to start everyone at 0.3 and L2-10's
troubleshooting check says to lower it — against a program that ships at 0.4.

**IDE links.** Module 3 has one, Module 4 has none, Module 5 has none. The
`/staging` sweep only covered lessons that already had a link.

**ALL_CAPS constants** appear in M4 (`HEADING_NAMES`) and M5
(`OBSTACLE_THRESHOLD`, `NORTH, EAST, SOUTH, WEST`, `ACTUAL_OBSTACLES`) — a naming
convention the course never teaches. Lesson 1-9 now teaches snake_case and
Capitalized-class and nothing else, so a student meeting `HEADING_NAMES` has no rule
that covers it. Worth one sentence in 1-9 or in M4 L7.

**Wide tables** — M2 L5:77 (4 columns), M2 L6:46 (5), M4 L4:72 and :85 (4 each),
M5 L3:103 and :116 (5 each), plus four 3-column tables. The 5-column ones are the
real problem in a 570px column.

**Missing sections** — M4 L0 and M5 L4 and L6 have no `## Real-world connections`.
(Final-project lessons across every module lack Wrap-up and Real-world; that's
consistent house style, not a defect.) M2 L8 has **no `## Activity ·` at all** — the
only lesson in the course without student work, confirmed.

**M5 L9's duration chip is `'90+ min'`**, and `extract_pacing.js` matches `\d+` and
silently drops the `+`, so the pacing guide records a 90-minute capstone that the
lesson's own teacher note says spans 2–3 days. The established value for this is
`'Multi-day'`.
