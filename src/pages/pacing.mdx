# Pacing guide

Everything below is generated from the lessons themselves — the time estimate in
each lesson header, the activities students hand in, and the knowledge checks.
Change a lesson and this page follows on the next build, so it can't quietly go
stale.

Set your period length and how often the class meets, and the totals re-count.
Print the page for a planning sheet with one module per sheet.

## Before you start the course

Time is only half of planning. The other half:

- **Robots.** One XRP per two students works; one each is better from Module 2
  on, where the line-tracking work is fiddly and students need their own runs.
  Charge everything the night before — a low battery presents as a hundred
  different bugs.
- **Floor space.** Modules 1 and 2 need open floor with a taped line course.
  Modules 3–5 need the grid, which is worth taping down once and leaving.
- **Computers.** Chrome or Edge, and nothing to install: the whole course runs in
  XRP Code in the browser — Blockly to start with, then Python files in the same
  editor from Module 1 Lesson 8 on.
- **The first USB pass.** Every robot needs one cable connection before it can
  go wireless, and that also installs its software. Do it before day one if you
  can; it's the single biggest time sink in Lesson 1.

## Where the natural pauses are

The phase chips in Module 1 mark real transitions: Blockly foundation through
Lesson 5, driving challenges in 6–7, then Python from Lesson 8. Each is a
sensible place to stop, assess, and pick up after a break. Modules 3, 4 and 5
build one continuous system — Manhattan navigation then Dijkstra's algorithm on
the same grid — so they're better run without a long gap between them.

If you're short on time, Module 3 is the most compressible: four lessons that
establish the grid, which Modules 4 and 5 then use.
