## The strategy: across first, then up or down

Each step moves the robot to a neighboring intersection, so **exactly one of x or y
changes, by 1**. Never both: that would be a diagonal, and the robot can't drive one.

<Figure
  src="/img/lesson-m4-03/one-step.svg"
  alt="A 3 by 3 grid with the robot's intersection (1, 1) in the middle. Red arrows go right to (2, 1), x + 1, and left to (0, 1), x − 1. Green arrows go up to (1, 2), y + 1, and down to (1, 0), y − 1. A dashed diagonal to (2, 2) is crossed out: x and y both change, so it is not one step."
  caption="One step changes x or y by 1, never both."
/>

The strategy is the simplest one that always works: **step across until x is right,
then step up or down until y is right.** That traces an L-shaped path, or a straight
line if x or y is already right.

The planner makes three promises, and every planner in this course keeps them:

1. The path **never includes the start.** The robot is already there.
2. The path **ends at the destination.**
3. The path is **empty** if the robot is already at the destination.

## From the trace table to a loop

Write the code the same way you worked out each new position. `x` and `y` are where the
robot is *during the plan*: they start as the start (`x, y = start`) and change by 1 on
every move. `dest_x` and `dest_y` are the destination.

In one loop, keep adding 1 to x while x is less than `dest_x`. In a second loop, do the
same for y. Inside each loop, append the new `(x, y)` to the path.

<Figure
  src="/img/lesson-m4-03/trace-to-loops.svg"

## This lesson's skeleton

Replace the planner stub in the MANHATTAN PLANNER section with this. The east loop is
written for you, and so is `run_test()`, which compares the planner's answer with yours.

```python
def compute_manhattan_path(start, destination):
    """Return the (x, y) steps from start to destination, across
    first, then up or down. The start itself is not in the list."""
    path = []
    x, y = start              # where the plan is now
    dest_x, dest_y = destination   # where it is going

    # East: keep stepping right until x matches dest_x
    while x < dest_x:
        x = x + 1             # one step right
        path.append((x, y))   # record the new spot

    # West: copy east, flip < to > and + to -

    # North: copy east, but step y until it matches dest_y

    # South: copy north, flip < to > and + to -

    return path

def run_test(test_name, start, destination, expected):
    """Plan start -> destination and compare the result
    with expected; print test_name with PASS or FAIL."""
    actual = compute_manhattan_path(start, destination)
    if actual == expected:
        print(test_name, "- PASS")
    else:
        print(test_name, "- FAIL")
        print("  Expected:", expected)
        print("  Actual:  ", actual)

def test_planner():
    # expected = your answer key, traced by hand
    run_test("Leg 1",       (0, 0), (2, 3), [(1, 0), (2, 0), (2, 1), (2, 2), (2, 3)])
    run_test("Leg 2",       (2, 3), (1, 0), [])   # your answer key
    run_test("Same column", (2, 0), (2, 3), [])   # your answer key
    run_test("Same row",    (0, 2), (3, 2), [])   # your answer key
    run_test("Same spot",   (1, 1), (1, 1), [])   # your answer key
```

The expected lists **must come from your own tracing.** Copy what the code prints and the
test only checks that the code agrees with itself.

### Step 4 · West and south: copy and flip

West is the east loop flipped: copy it under the west comment, then flip `<` to `>` and
`+ 1` to `- 1`. South is the north loop, flipped the same way.

**Why two x loops can sit next to each other:** a while loop checks its condition before
its first trip. Going left, x is already bigger than `dest_x`, so the east loop's
`x < dest_x` is False on that first check and the east loop never runs. Only the west
loop moves x. The two y loops work the same way, so no `if/else` is needed.

<Figure
  src="/img/lesson-m4-03/one-x-loop-runs.svg"
  alt="Going left with x = 3 and dest_x = 1. The east loop, while x < dest_x, is grayed out: 3 < 1 is False on the first check, so it never runs. The west loop, while x > dest_x, is highlighted: 3 > 1 is True, so it runs twice and x goes 3, 2, 1."
  caption="For any trip, at most one of the two x loops runs. The same goes for the two y loops."
/>

The two x loops come before the two y loops, so the path always goes across first. Run
`test_planner()`: five PASS lines.

<TeacherNote title="Redirect anyone reaching for if/else">

The four-loop design is the lesson's big idea: *a while loop whose condition starts False
simply does nothing.* Students who've seen conditionals will try `if x < dest_x ... elif`.
Steer them back: the four loops handle every case, including same spot (all four skipped,
`[]`). Take real time on the double parentheses in `path.append((x, y))`: the outer pair is
the function call, the inner pair is the tuple.

Promise 1 is the one that bites later: a path that includes the start gives the driver a
zero-length move in Lesson 4-5. Keep `run_test()` in the file: Module 5 comes back to it.

</TeacherNote>

## When a test fails

Don't guess: add prints inside `compute_manhattan_path()` to watch it run. One at the top,
and one in each loop right after the `append`:

```python
    print("Computing from", start, "to", destination)   # first line
    ...
        print("  added:", (x, y))                          # in each loop
```

The output shows which loop ran and what it added. Once the bug is fixed, **remove the
debug prints** so the output stays clean. Try it: change one `+ 1` to `- 1`, run
`test_planner()`, watch a test catch it, then change it back.

<OptionalExtension title="Unit testing" gate="Optional: open it if you have time. Nothing later depends on it.">

`test_planner()` is a set of **unit tests**: each one checks one small piece of a program,
here one function, on its own, against an answer worked out separately. Professional
software runs thousands of them every time the code changes, so a mistake is caught minutes
after it's made, not weeks later by a user.

The planner is an ideal unit because of **separation of concerns**: it only *computes* a
path, and it is handed the robot's position, so there is nothing to set up. Tuples in,
list out, on any computer.
