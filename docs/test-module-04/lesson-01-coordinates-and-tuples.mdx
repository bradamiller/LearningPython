In Lesson 4-0, every intersection was a pair of numbers in parentheses, like `(1, 1)` or
`(3, 4)`. That notation is built into Python, and it's called a **tuple**. This lesson
pins down what the two numbers mean, on paper first, then puts tuples to work in code.

<Objectives>

By the end of this lesson you will be able to:

- Name any intersection with an `(x, y)` pair, and tell x (across) from y (away from you)
- Create a tuple to hold an `(x, y)` coordinate
- Read its parts: the x coordinate of the tuple is `position[0]`, and the y coordinate is `position[1]`; or unpack both at once
- Explain **immutability** and why it suits coordinates
- Compare positions with `==`

</Objectives>

## Two numbers name any spot

You already know coordinate systems: Battleship ("B4"), chess ("e5"), a spreadsheet
cell ("A1"). Our grid names every intersection with two numbers, **(x, y)**, counted
from **(0, 0)**, the corner nearest you. x counts across to the right and y counts up,
away from you, both starting at zero. Order matters: `(2, 3)` and `(3, 2)` are
different spots.

<TeacherNote title="Getting x and y in the right order is the #1 stumble">

Repeat the convention constantly — "x first, y second; x is across, y is away from
you" — and consider posting it. Students who have graphed in math class know the
order already; what is new is counting from zero and that `(0, 0)` is the corner
nearest them. Zero-indexing trips most of them: they count from 1 by habit, so name
*why* (Python indexes from 0, and matching now avoids pain later). If you can, have
students stand at the near edge, physically **walk the grid** and call out their
coordinates — kinesthetic beats diagrams here. Keep the first half code-free; when they ask "when do we code?", answer "once you can
name every spot — that's the map the code will use."

</TeacherNote>

## One value, two numbers

Now store a position in Python. Try this lesson's code in a new file, not `robot.py`.

You *could* store a position in two variables — `x = 2`, `y = 3` — but that gets
messy fast (ten positions would need twenty variables). A **tuple** packs both into
one value, written just as on the map in 4-0:

```python
position = (2, 3)
start = (0, 0)
destination = (3, 2)
```

Pull the pieces out by **index** — and since Python counts from zero (just like our
grid), index `0` is x and index `1` is y:

```python
position = (2, 3)
print(position[0])   # 2  -> x, across
print(position[1])   # 3  -> y, away from you
```

## Unpacking: both numbers at once

Indexing pulls out one part at a time. Often you want both, as ordinary variables, and
Python has a one-line way to get them:

```python
position = (2, 3)
x, y = position      # x is 2, y is 3
```

That's **tuple unpacking**. Python takes the variables on the left in order and gives each
one the matching part of the tuple: the first variable gets index 0, and the second gets
index 1. It does exactly what these two lines do:

```python
x = position[0]
y = position[1]
```

The variable names are yours to choose (`dest_x, dest_y = destination` works the same way), but
there must be exactly as many variables as parts. Two variables and a three-part tuple, or three
variables and a two-part tuple, and Python stops with a `ValueError`.

  question="After start = (3, 2) and then a, b = start, what is b?"

    {text: 'An error'},
  ]}
  explanation="The variables take the parts in order: a gets index 0, which is 3, and b gets index 1, which is 2. The variables don't have to be called x and y."

## Tuples can't change (and that's good)

Try to modify a tuple and Python stops you:

```python
position = (2, 3)
position[0] = 5      # TypeError: 'tuple' object does not support item assignment
```

Tuples are **immutable** — once made, they can't be altered. That's exactly right for
a coordinate: `(2, 3)` should *always* mean x = 2, y = 3. To represent a new spot,
you make a new tuple:

```python
old_position = (2, 3)
new_position = (3, 3)    # one step east -- a brand-new tuple
```

Think of a street address: it doesn't change. Move, and you get a *new* address — you
don't edit the old one.

<TeacherNote title="Index mix-ups and the parentheses/brackets split">

Expect `[0]` vs `[1]` confusion for a few exercises — post "the x coordinate is
`position[0]`, the y coordinate is `position[1]`" on the wall. Also flag the bracket rule early: tuples are made with
parentheses `()`; square brackets `[]` are *only* for indexing (and, next lesson, for
lists). The immutability payoff isn't obvious yet — the street-address analogy is
enough for now; it really pays off once tuples live inside lists and the algorithm.

</TeacherNote>

## Comparing positions

`==` checks whether two tuples are the *same* position — both parts must match, in
order:

```python
current = (1, 2)
target  = (1, 2)
print(current == target)   # True

other = (2, 1)
print(current == other)    # False -- order matters!
```

This matters later: the algorithm asks "have we reached the destination yet?" by
comparing tuples.

  explanation="Two tuples are equal only if every element matches in order. (1, 3) is 1 for x and 3 for y; (3, 1) is 3 for x and 1 for y — different, so False."

## Wrap-up

- Which number comes first, and what does it mean? (x — how far across to the right.)
- How do you get x and y out of a tuple? (The x coordinate is `position[0]` and the y coordinate is `position[1]`, or unpack both at once.)
- What does immutable mean, and why is it good for coordinates? (Can't change; a position should stay fixed.)
- Why is `(2, 3) == (3, 2)` False? (Elements must match in order.)
