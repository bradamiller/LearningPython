## A position is one value

In Lesson 4-0 every intersection was a pair of numbers, `(x, y)`: x counts across to the
right, y counts up, away from you, both from `(0, 0)`, the corner nearest you.

<Figure
  src="/img/lesson-m4-01/coordinate-axes.svg"
  alt="A 4 by 4 grid of black tape. The bottom-left intersection is ringed and labeled origin (0, 0). A red arrow starts at the origin and points right along the bottom line, labeled increasing x. A green arrow starts at the origin and points up along the left line, labeled increasing y. x is numbered 0 to 3 along the bottom and y 0 to 3 up the left side. Labeled intersections: (3, 0) bottom-right, (0, 3) top-left, (2, 1), (1, 2) and (3, 3) top-right."
  caption="x increases to the right and y increases up."
/>

Python can store that pair as **one value**, written just as on the map. It's called a
**tuple**:

```python
position = (0, 0)
destination = (2, 3)
```

Parentheses, a comma, x first. Order matters: `(2, 3)` and `(3, 2)` are different
intersections.

## Destinations are a list

The delivery robot has five destinations. Five variables would need five copies of the
code. A **list** holds them all, in order, in one variable: square brackets, commas
between the items.

```python
DESTINATIONS = [(2, 3), (1, 0), (3, 1), (2, 2), (0, 0)]
```

Each item is a tuple, so this is a list of positions. To do something with every item,
loop over the list:

```python
for destination in DESTINATIONS:
    print("Go to", destination)
```

Each time around, the next item of the list is assigned to `destination`, first to last.
It's the `for` loop from Lesson 1-10, with a list in place of `range()`.

## The main program in words

The robot starts at (0, 0) facing North. For each destination on its list:

1. **Plan** the path from where it is now.
2. **Drive** the path, which leaves it somewhere new, facing a new way.

Then it plans the next leg from *there*. So the program keeps track of two things: the
robot's **position**, a tuple, and its **heading**, a number from 0 to 3. Today all you
need is that 0 means North; the rest comes in Lesson 4-4. Together they are the robot's
**pose**.

<Figure
  src="/img/lesson-m4-06/pose.svg"
  alt="A 4 by 4 grid with the robot at (1, 1) facing East. Beside it: the robot's pose, where it is and which way it faces, written ((1, 1), 1). The (1, 1) is labeled position; the final 1 is labeled heading, 1 = East. Below: position, heading = drive_path(...), drive_path hands back the pose."
  caption="The pose ((1, 1), 1): at (1, 1), facing East."
/>

The planner will be `compute_manhattan_path(start, destination)`, and the driver
`drive_path(path, current_position, current_heading)`.

## Stubs: run it before the parts exist

A **stub** is a stand-in function: same name, same parameters, same kind of return value,
but only enough inside to let the program run. Each stub **prints its name and what it
was given**, so the printout shows that the main program called it, and with what.

```python
def compute_manhattan_path(start, destination):
    """STUB: a pretend path that jumps straight to the
    destination. Lesson 4-2 replaces it."""
    print("  STUB compute_manhattan_path:", start, "to", destination)
    return [destination]

def drive_path(path, current_position, current_heading):
    """STUB: pretend to drive -- just jump to each
    intersection in path. Lesson 4-4 replaces it."""
    print("  STUB drive_path:", path)
    for next_pos in path:
        current_position = next_pos
    return current_position, current_heading
```

The planner stub's path is wrong (a robot can't jump three blocks), but `[destination]`
is a list with one position in it, and a list of positions is all the main program needs
today.

## Handing back two values

`drive_path()` ends with `return current_position, current_heading`. A comma between two
values makes a tuple, so it hands back both at once: the pose. Where it is called, give
each value its own variable:

```python
position, heading = drive_path(path, position, heading)
```

That's **unpacking**: the first variable on the left gets the first value, the second
gets the second.

**Why it has to hand them back.** When the call runs, `current_position` starts with the
value of `position`. Inside the function, `current_position = next_pos` changes only
`drive_path()`'s own variable. As with assigning inside a function in Lesson 2-7, the
caller's `position` is never touched. So the only way the main program learns where the
robot ended up is the return value.

<TeacherNote title="Why the main program comes first">

Students taught the standard order wrote three lessons of parts before anything
connected, and lost the thread. Here the whole program runs in the first coding lesson,
and every later lesson swaps one stub for the real thing and runs the same test. The
printout is always there to check against.

Tuples, lists and the `for` loop get about fifteen minutes here, on purpose: just enough
to write the program. Don't expand them. `append()`, indexing and the rest arrive in the
lessons that need them, and Lesson 4-7 pulls them together.

Step 3 is the lesson's point. The dropped return value is the most common Module 4 bug,
and it normally surfaces on the floor, on leg 2. Here students cause it on purpose, on
screen, in two minutes. If someone asks why the stub planner returns a wrong path, that's
the right question: a stub only has to keep the program running.

</TeacherNote>

## Wrap-up

- How does Python store a position, and several destinations? (A tuple, `(x, y)`; a list of tuples, in square brackets.)
- What does `for destination in DESTINATIONS:` do? (Runs the loop body once per item, with `destination` set to each item in turn.)
- What is a stub for, and why does it print? (It lets the program run before the real function is written; the print shows it was called, and with what.)
- Why must the main program write `position, heading = drive_path(...)`? (Assigning to a parameter changes only the function's own variable; the return value is the only way the new pose gets back.)
