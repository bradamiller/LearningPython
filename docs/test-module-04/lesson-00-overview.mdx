Here's the problem this module solves: **get the robot from where it starts to a
destination on the grid, all by itself.**

<Figure

A taxi in Manhattan has the same problem. Buildings fill every block, so it can't drive
straight from A to B; it drives along the streets, 2 blocks east, then 3 blocks north. The robot
is the same: it can only drive along the tape. So the route comes from one rule:

> **Go east or west until we are at the destination avenue, then north or south until we're at the destination street.**

That's the whole algorithm. It's called the **Manhattan algorithm**.

<Callout kind="note" title="The big assumption: every street is clear">

The algorithm assumes nothing is in the way, so it never needs a detour. **Module 5**
adds obstacles; **Module 6** (optional) adds slow streets.

</Callout>

<TeacherNote title="Manhattan, for the curious">

The grid dates from 1811 and is turned about 29 degrees from true north; the same
distance is called **taxicab distance** in math. The map is a hook, not a lesson.
Lesson 4-4 assumes students have seen it.

</TeacherNote>

## Breaking down a complex problem

Now you know how to find the route. Getting the robot to do it is the next problem.

Street and avenue names are hard to use in a robot program, so we number each
intersection instead: a column number, **x**, and a row number, **y**. The taxi's trip
becomes (1, 1) to (3, 4).

<Figure
  src="/img/lesson-m4-00/manhattan-xy.svg"
  alt="The same cartoon map of midtown Manhattan, with every intersection labeled by a pair of numbers (x, y). x is the column: the avenues are numbered from the west, 9th Ave is x = 0, 8th Ave x = 1, up to Madison, x = 5. y is the row: the streets are numbered from the south, 53rd St is y = 0, 54th St y = 1, up to 58th St, y = 5. The taxi starts at A, (1, 1), the corner of 8th Avenue and 54th Street, and follows the blue route to B, (3, 4), the corner of 6th Avenue and 57th Street."
  caption="Each intersection gets a column number x and a row number y, written (x, y)."
/>

"Drive over there" sounds like one job, but it's too much to get right in one go. One way to tackle a complex problem is to **break it into simpler
sub-problems** and solve each one. That's called **problem decomposition** (or **top-down design**).

## Discuss · How would you split it?

1. Before the robot moves, could you write down every intersection it will drive through?
2. How could you check that list is right, without the robot?
3. Once the list is right, what's left for the robot to do?

<TeacherNote title="Leading the discussion (5–8 min)">

Ask the questions in order and let the class answer; draw the grid on the board.

1. **Yes.** Expect "two right, then three up." Mark each intersection on the board grid in order. If someone says the robot should decide as it goes, ask: "Does it need to? Nothing on the grid changes."
2. **Trace it on the grid by hand**, or have the computer print it and compare. Steer to: *no robot needed*, so the route can be tested on a laptop.
3. **Just drive it:** at each intersection on the list, face the next one and follow the tape there. It doesn't have to decide anything.

Then name the split: **plan** the route, **drive** the plan, with the list passed between
them. Ideas about motors, sensors or turning belong to the driving half; park them there.

</TeacherNote>

## Plan first, then drive

That's one way to split the problem, and the one this module uses: **plan** the whole
route first, then **drive** it.

<Figure
  src="/img/lesson-m4-00/plan-then-drive-points.svg"
  alt="Left: a 4 by 4 grid with (0, 0) at the bottom-left. The robot starts at (0, 0). A blue route goes right to (1, 0) and (2, 0), then up to (2, 1), (2, 2) and (2, 3), each intersection labeled with its coordinates. Right: step 1, Plan: work out the route, print it, check it, no robot needed. An arrow carries the points (1, 0), (2, 0), (2, 1), (2, 2), (2, 3), a list of (x, y) coordinates, down to step 2, Drive: take the list and drive it, one intersection at a time."
  caption="The plan is a list of (x, y) coordinates. One function makes it; another drives it."
/>

1. **Plan.** The planner, `compute_manhattan_path`, works out the whole route. It never
   moves the robot, so you can test it **without a robot**: print the route and check it
   against the grid.
2. **Drive.** Once the plan is right, the driver, `drive_path`, **takes the plan and
   drives it**, then reports where the robot ended up.

Each intersection is an `(x, y)` pair, so the plan is a **list of coordinates**, the one
thing the two functions share.

One job each is called **separation of concerns**, and it makes bugs easy to find: a
wrong route is a planner problem; a wrong turn is a driver problem.

## From one destination to several

Picture a delivery driver with packages for several houses, each with its own address.
The driver plans a route to the first house and drives it, then plans from there to the
next, until every package is delivered.

The robot does the same. Once it can reach one destination, several is just a loop: plan
from where it is, drive, repeat.

## Build it from the top down

You'll build this program **top-down**: the top of the tree first, then one level at a
time. The main program comes first, and it runs on day one, because every part below it
starts as a **stub**: a stand-in function that does just enough for the program to run,
and prints what the real one would do.

Then you swap the stubs for real functions, one per lesson, and run the program after
every change. The output tells you right away whether it still works. The robot only
drives in the last lesson, so you never have to wonder whether a bug is in your code
or in the robot.

## Wrap-up

- What problem does Module 4 solve? (Drive the robot from where it starts to a destination on its own, then to several destinations in a row.)
- Why plan first? (The planner never moves the robot, so its list of coordinates can be printed and checked with no robot at all. Then the driver only has to follow a plan you already trust.)
- What are the two halves and their jobs? (`compute_manhattan_path` plans; `drive_path` drives.)
- What is a stub? (A stand-in function that lets the program run before the real function is written.)
