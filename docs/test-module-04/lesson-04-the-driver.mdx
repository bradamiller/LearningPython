## Heading is a number

Since Lesson 4-1 the program has carried a `robot_heading` that never changed. Now it gets
used. The four directions are numbered clockwise from North:

| Heading | 0 | 1 | 2 | 3 |
|---|---|---|---|---|
| Direction | North | East | South | West |

Numbers are easy to do arithmetic on (a clockwise quarter turn adds 1), but `0` in a
printout is hard to read. So the program needs a way to turn 0 into `N` and 2 into `S`.

## Picking one item: indexing

Put the four letters in a list, in heading order:

```python
HEADING_NAMES = ["N", "E", "S", "W"]
```

Every item in a list has a position number, its **index**, counting from **0**. Square
brackets after the name pick one item out:

```python
print(HEADING_NAMES[0])    # N
print(HEADING_NAMES[2])    # S
heading = 3
print(HEADING_NAMES[heading])    # W
```

The headings were numbered 0 to 3 so that a heading **is** the index of its own letter.

A tuple is indexed the same way. For a position, index 0 is x and index 1 is y:

```python
next_pos = (2, 3)
print(next_pos[0])    # 2 -> x
print(next_pos[1])    # 3 -> y
```

For a position you'll usually want both numbers, so this program keeps unpacking them,
as the planner does. Indexing is for picking one item out of many. Asking for an index that isn't
there, like `HEADING_NAMES[4]`, stops the program with an `IndexError`.

## Which way to face?

Between two *adjacent* intersections, either x changes by one **or** y changes by one,
never both. That's four cases, one per compass direction:

| Coordinate change | Direction | Heading |
|---|---|---|
| y +1 (up, away from you) | North | 0 |
| x +1 (right) | East | 1 |
| y −1 (down, toward you) | South | 2 |
| x −1 (left) | West | 3 |

The part to keep straight: x comes first in the tuple, but North and South change the
*second* number. **North is away from you**, so moving North makes y *bigger*.

`get_desired_heading(position, next_pos)` works out that table. It unpacks both
positions, as the planner did; then `x_diff` is next minus now for x, `y_diff` the same
for y, and four `if` lines return the matching heading. Each `if`
checks *both* differences: North means y went up by one **and** x didn't move.

<OptionalExtension title="Catching mistakes early" gate="Optional: open it if you have time. Nothing later depends on it.">

`get_desired_heading()` only makes sense when the next intersection is **one step away**.
If none of the four `if` lines matches, there is no right answer. **When would that
happen?** Think about it before you open the answer.

<Reveal title="When would the next intersection not be adjacent?" hint="make a guess first">

Only when there's a **bug in the planner**. A correct planner only lists adjacent steps.
A path that includes the start (promise 1) is one way: the first "move" goes nowhere.

</Reveal>

Without a check, `get_desired_heading()` quietly returns `None`, and the program breaks
somewhere else: here, at `HEADING_NAMES[None]`; on the robot, in a turn that never ends.
With a check, the program stops at once and says which two positions caused it:

```python
raise ValueError(str(position) + " and " + str(next_pos) + " are not neighbors")
```

`raise` stops the program on the spot and prints your message. `ValueError` is Python's
name for "the values I was given make no sense". `str(position)` turns a tuple into text.

<TeacherNote title="What to watch">

The grid orientation (x first in the tuple, but North is +y, away from you) is the #1
confusion; draw it, point at it, quiz it. Check that each `if` tests both differences: a
version that checks only `y_diff == 1` returns North for (2, 1) to (3, 2), a diagonal.

The turns aren't real yet: the `turn_to()` stub just hands back the heading it was asked
for, so the printout shows which way the robot must face, not how it gets there. That's
Lesson 4-5. A student whose every `turning:` line starts from N forgot to assign
`current_heading = turn_to(...)`: the same dropped return as Lesson 4-1, one level down.

Indexing is new here. The heading-is-its-own-index trick is worth saying out loud, and
`HEADING_NAMES[4]` is worth trying once in the shell so `IndexError` isn't a surprise
later. `raise` needs no more teaching than "the program stops and prints your
message"; don't detour into `try`/`except`.

</TeacherNote>

```python
# ===== NAVIGATOR =====
# Drives a planned path, one intersection at a time, and hands
# back where the robot ended up and which way it faces.
HEADING_NAMES = ["N", "E", "S", "W"]    # HEADING_NAMES[2] -> "S"

def get_desired_heading(position, next_pos):
    """Return the heading (0-3) that points from position to
    next_pos, which must be one step away."""
    x, y = position
    next_x, next_y = next_pos
    x_diff = next_x - x
    y_diff = next_y - y
    if x_diff == 0 and y_diff ==  1: return 0   # North
    if y_diff == 0 and x_diff ==  1: return 1   # East
    if x_diff == 0 and y_diff == -1: return 2   # South
    if y_diff == 0 and x_diff == -1: return 3   # West
    raise ValueError(str(position) + " and " + str(next_pos) + " are not neighbors")

def test_headings():
    for next_pos in [(0, 1), (1, 2), (2, 1), (1, 0)]:
        heading = get_desired_heading((1, 1), next_pos)
        print("(1, 1) to", next_pos, ":", heading, HEADING_NAMES[heading])

def turn_to(current_heading, desired_heading):
    """STUB: pretend the robot turned. Lesson 4-5
    replaces it."""
    print("turning: from", HEADING_NAMES[current_heading],
          "to:", HEADING_NAMES[desired_heading])
    return desired_heading

def fake_track_to_intersection():
    """STUB for track_to_intersection(): print instead of
    driving. Lesson 4-6 swaps in the real one."""
    print("tracking to intersection")

def drive_path(path, current_position, current_heading):
    """Turn and drive through every intersection in path;
    return the final position and heading."""
    for next_pos in path:
        desired_heading = get_desired_heading(current_position, next_pos)
        print("moving: from", current_position, "to:", next_pos,
              "heading:", HEADING_NAMES[desired_heading])
        current_heading = turn_to(current_heading, desired_heading)
        fake_track_to_intersection()
        current_position = next_pos     # the robot is there now
    return current_position, current_heading

# --- The main program: the delivery run ---
DELIVERY_STOPS = [(2, 3), (1, 0), (3, 1), (2, 2), (0, 0)]

def test_delivery():
    robot_position = (0, 0)
    robot_heading = 0               # facing North
    for delivery_destination in DELIVERY_STOPS:
        path = compute_manhattan_path(robot_position, delivery_destination)
        print(path)
        robot_position, robot_heading = drive_path(
            path, robot_position, robot_heading)
        print("new position:", robot_position,
              "heading:", HEADING_NAMES[robot_heading])

# ===== RUN =====
board.wait_for_button()
test_delivery()
```

## Wrap-up

- What two steps happen at each intersection? (Turn to face the next one, then drive to it.)
- Between adjacent intersections, what can change? (x *or* y, by one: four cases, four headings.)
- What does `HEADING_NAMES[heading]` do? (Picks the item at that index, counting from 0: the heading's letter.)
- Why does `drive_path()` write `current_heading = turn_to(...)`? (`turn_to()` hands back the new heading; assigning it is the only way `drive_path()` keeps it.)
