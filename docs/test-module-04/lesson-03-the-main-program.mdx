## The robot's pose

To plan from the right place, the program has to know two things about the robot: where
it is, and which way it faces.

- **Position** is an `(x, y)` tuple, as in Lesson 4-1.
- **Heading** is a number: **0** is North, **1** East, **2** South, **3** West. They count
  clockwise, so a clockwise turn adds 1.

Together they are the robot's **pose**.

## The main program in words

The delivery robot starts at (0, 0) facing North. For each destination on its list:

1. **Plan** the path from where it is now.
2. **Drive** the path, which leaves it somewhere new, facing a new way.

Then it plans the next leg from *there*. That's the whole main program. The planner is
`compute_manhattan_path(start, destination)`, and the driver is
`drive_path(path, current_position, current_heading)`.

## Stubs: run it before the parts exist

A **stub** is a stand-in function: same name, same parameters, same kind of return value,
but only enough inside to let the program run. These two are today's:

```python
def compute_manhattan_path(start, destination):
    """STUB: a pretend path that jumps straight to the
    destination. Lesson 4-4 replaces it."""
    return [destination]

def drive_path(path, current_position, current_heading):
    """STUB: pretend to drive -- just jump to each
    intersection in path. Lesson 4-5 replaces it."""
    for next_pos in path:
        current_position = next_pos
    return current_position, current_heading
```

The planner stub's path is wrong (a robot can't jump three blocks), but it's a list of
`(x, y)` tuples that ends at the destination, and that's all the main program needs today.

## Handing back two values

`drive_path()` ends with `return current_position, current_heading`. A comma between the
values makes a tuple, so it hands back both at once: the pose. Where it is called, unpack
it the way you unpacked `x, y = start` in Lesson 4-1:

```python
position, heading = drive_path(path, position, heading)
```

**Why it has to hand them back.** When the call runs, `current_position` starts with the
value of `position`. Inside the function, `current_position = next_pos` changes only
`drive_path()`'s own variable. As with assigning inside a function in Lesson 2-7, the
caller's `position` is never touched. So the only way the main program learns where the
robot ended up is the return value. The different names are a reminder:
`current_position` belongs to `drive_path()`, and `position` belongs to the main program.

## This lesson's skeleton

Paste this into `robot.py` above `RUN`, after the GRID DRIVING section. It starts two
new sections, each with a stub, and the main program at the end.

## Activity · Write it, run it

### Step 1 · Write `test_delivery()`

Write the body from its outline. Set the run line to `test_delivery()`, run it, and press
the button. The robot stays on the desk; nothing moves.

**What correct looks like:** two lines per destination, five destinations. Each `Plan from`
starts at the destination of the line before it, the first one at (0, 0). Each path is just
`[destination]`, because the planner is a stub. The last line says `Finished at (0, 0)
facing N`: the driver stub never turns.

<Reveal title="Check your test_delivery() and its output" hint="write it and run it first">

```python
def test_delivery():
    position = (0, 0)
    heading = 0                     # facing North
    for destination in DESTINATIONS:
        print("Plan from", position, "to", destination)
        path = compute_manhattan_path(position, destination)
        print("  path:", path)
        position, heading = drive_path(path, position, heading)
    print("Finished at", position, "facing", HEADING_NAMES[heading])
```

### Step 2 · Break it on purpose

Change the driving line to just `drive_path(path, position, heading)`, with nothing on the

<TeacherNote title="Why stubs first">

Students taught the old order wrote three lessons of parts before anything connected,
and lost the thread. Here the whole program runs on day one, and every later lesson
swaps one stub for the real thing and runs the same test. The output is always there to
check against.

Step 2 is the lesson's point. The dropped return value was the most common Module 4 bug,
and it used to surface on the floor, on leg 2. Here students cause it on purpose, on
screen, in two minutes. If someone asks why the stub planner returns a wrong path, that's
the right question: a stub only has to keep the program running.

</TeacherNote>

## Wrap-up

- What is the robot's pose? (Its position, an `(x, y)` tuple, and its heading, 0 to 3.)
- What is a stub for? (It lets the program run before the real function is written.)
- Why must the main program write `position, heading = drive_path(...)`? (Assigning to a parameter changes only the function's own variable; the return value is the only way the new pose gets back.)
