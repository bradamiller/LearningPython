## The mission

each of the 4 corners. Done right, it finishes where it began.

## One loop, four sides

The whole square is a four-iteration loop: each pass drives one side, then turns the
corner. The piece that drives a side is `drive_intersections(count)` — you built and
tested it in Lesson 3-2 — so the loop body is a call to it and a turn.

Sketch the loop body in English first: what happens once per side? Then write it. The
loop body is two calls and a print or two; if yours is longer, ask what the extra
lines are for. There is nothing between the drive and the turn: the helper leaves the
robot parked on the corner, and the turn ends with a sensor on the next side's line.

<TeacherNote title="Solution (teacher copy)">

This lesson's addition to the GRID DRIVING section of `robot.py`, plus the run block;
the rest of the file is as the Lesson 3-3 teacher copy left it. Use it to unstick a
team; the loop is the graded work, and there is no student reveal for it. The file is
`lesson-04-final-project.py` in the Module 3 solutions. Class-track students write
`tracker.turn_clockwise()`.

```python
# --- Lesson 3-4: final project, the square ---
# The module project: four sides of SIDE intersections with a
# right turn at every corner, back to the start. Built from
# drive_intersections() and one turn; nothing new is defined.
SIDE = 2                 # intersections per side

def test_one_side():
    drive_intersections(SIDE)
    turn_clockwise()
    print("One side done")

def test_square():
    print("Module 3 Final Project -- Square Pattern!")
    for side in range(4):
        print("Side", side + 1, "of 4")
        drive_intersections(SIDE)
        print("  Turning right...")
        turn_clockwise()
    print("Square complete! Back at start.")

# ===== RUN =====
board.wait_for_button()
test_square()
```

</TeacherNote>

Four right turns add up to a full 360°, which is why the robot comes back around to
its starting heading as well as its starting intersection.

## Activity · Test one side at a time

Don't run all four sides first. Build up, one test at a time:

1. **One side** — write `test_one_side()` and set the run line to it. The robot
   should drive `SIDE` intersections, pivot on the corner, and stop facing along the
   next side. Don't go on until it does.
2. **Two sides** — write `test_square()` with `range(2)` for now. What shape should
   that give you? Predict, then run.
3. **Full square** — change it to `range(4)`; does it close back to the start?

<TeacherNote title="Run it as a build; tuning is the lesson">

Treat this as plan → build → test → present, and insist on **incremental testing** —
one side, then two, then four. The common fixes are all tuning: turns that aren't
quite 90° (the blind part of the turn too long or `TURN_EFFORT` too high, so the
sensor-ended finish spins past the line), a `drive_past_intersection()` distance
that doesn't match the robot's sensor-to-axle gap, or too much `BASE_EFFORT`. Frame that as real engineering. Returning *approximately* to
start is success; a perfectly closed square on real tape is a bonus. Two clean sides
already show mastery of the concept.

</TeacherNote>
