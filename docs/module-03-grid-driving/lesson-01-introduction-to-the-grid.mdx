## A grid is just a lot of intersections

A grid is a set of taped lines running two directions — rows and columns. Wherever
two lines cross is an **intersection**, and to the robot's two sensors an
intersection looks exactly like the taped cross from Module 2: both sensors go high
at once.

<Figure

Labels: an intersection is where two lines cross and looks to the sensors just like the cross from Module 2; a segment is the stretch of line from one intersection to the next; the robot on a segment, facing the next intersection, is taken there by track_to_intersection()."
  caption="Rows and columns of tape. Every place they cross is an intersection — a spot the robot can stop and turn."
/>

That's the whole insight: you already built everything needed to drive a grid. The
LINE TRACKING section you finished in Lesson 2-9 has the four functions that do it all:

- `track_to_intersection()` — follow the line to the next intersection and stop.
- `drive_past_intersection()` — put the wheels on the intersection, sensors past it.
- `turn_clockwise()` — turn onto the perpendicular line to the right.
- `turn_counterclockwise()` — turn onto the perpendicular line to the left.

<Callout kind="note" title="If you built the LineTrack class">

Use it — that's what it's for. Your LINE TRACKING section is the class, with
`tracker = LineTrack()` right under it, and every skeleton in this module is written
with the function names; yours is the same name on your object:

```python
tracker.track_to_intersection()
tracker.drive_past_intersection()
```

So where a test outline in this module says "arrive at the intersection," your body
says `tracker.track_to_intersection()` and `tracker.drive_past_intersection()`, and
the helper you write in Lesson 3-2 calls the tracker the same way. Notice what you
*don't* have to carry along: no threshold constant at the top of the file, no sensor
to hand in, nothing shared through `global`. The tracker brought its sensor and its
settings with it. That is what the class bought you, and it shows up on every line
from here to the end of the course.

</Callout>

<TeacherNote title="Sell the reuse — it's the point of the module">

The big idea of Module 3 isn't a new Python concept — it's *reuse*. Make it explicit:
"we're running the exact same functions on a new course." That's how professionals
work — a well-designed toolkit outlives the problem it was written for.

The grid is the same color surface with the same tape the circle was made from, so
there is nothing to re-measure and nothing to re-tune: both sections of `robot.py`
come across untouched. Worth saying out loud, because students expect a new problem
to need new code.

**The hint level drops this module.** Module 2 gave the test functions in full; from
here the skeleton gives `def test_x():` and a comment, and the body is the student's
— test-driven development, lightly. The bodies in this lesson are two to five calls
they have made before, so it is the right place to start that habit.

</TeacherNote>

## This lesson's skeleton

A new kind of driving gets a new section. Paste this into `robot.py` above `RUN` — it
goes after the whole LINE TRACKING section, and it starts with no functions of its
own, only tests, because there is nothing new to write yet.

```python
# ===== GRID DRIVING =====
# Drives the taped grid one intersection at a time, using only
# the LINE TRACKING functions: a grid intersection is the
# cross from Module 2. To ARRIVE at an intersection is
# track_to_intersection() then drive_past_intersection(); a
# turn happens parked on one. Nothing here touches a sensor.

def test_first_intersection():
    # from a line, arrive at the next intersection and say so
    pass

def test_arrive_and_turn():
    # arrive at the intersection, then turn right onto the
    # crossing line
    pass
```

Two things are different from Module 2's skeletons. The tests have no bodies — the
comment says what the test should do and you write it, which from here on is how
every test arrives. And `pass` holds the place, as it did in Lesson 2-1, so the file
runs before you've written anything.

## Drive to the first intersection

Place the robot centered on a line, facing toward the next intersection, and the
first test is two calls: `track_to_intersection()` follows the line right up to the
cross, and `drive_past_intersection()` rolls forward so the wheels are over the
intersection — exactly as `test_park()` did in Lesson 2-9. Those two calls together
are the **arrival pair**, and they are what "arrive at an intersection" means for the
rest of the course.

### Step 1 · test_first_intersection()

Write the body: a print saying what it's about to do, the arrival pair, and a print
saying it got there. Set the run line to `test_first_intersection()`, put the robot on
a line segment facing the next intersection, and run. It should stop with its wheels
on the intersection. Try it from a few starting spots. Don't go on until it does.

### Step 2 · test_arrive_and_turn()

Once you're parked on an intersection you can turn onto the crossing line. Write the
body: the arrival pair, then `turn_clockwise()`, with a print before the turn and one
after. Set the run line to it and run. The robot should arrive, pivot on the
intersection, and stop facing along the crossing line with a sensor on the tape.

One thing to watch in both tests: if the robot detects an intersection *immediately*,
it started sitting right on one — nudge it back onto the line first.

<Reveal title="Check your two tests" hint="write and run both first">

```python
def test_first_intersection():
    print("Driving to the first intersection...")
    track_to_intersection()
    drive_past_intersection()
    print("Intersection reached!")

def test_arrive_and_turn():
    track_to_intersection()
    drive_past_intersection()
    print("Turning right...")
    turn_clockwise()
    print("Now facing a new direction!")
```

Your prints can say anything; the calls, and their order, are what matter.

</Reveal>

<TeacherNote title="Common setup snags & differentiation">

The usual issues: starting on an intersection (detects instantly), a threshold that
needs re-calibrating for the grid's surface, or the robot not centered before a
turn. **More support:** have students get `test_first_intersection()` reliable
before writing the turn test. **More challenge:** a `test_two_segments()` — arrive,
turn, arrive again — previewing Lesson 3-2.
