Reaching the *first* intersection is easy. Reaching the *third* is the same two calls,
three times — and that is what a `for` loop is for. This lesson turns "arrive at an
intersection" into a building block you can repeat a chosen number of times — the
first real function in the GRID DRIVING section — and looks closely at why the second
call works at all.

<Objectives>

By the end of this lesson you will be able to:

- Explain why `track_to_intersection()` called twice in a row would not move the robot without `drive_past_intersection()` between them
- Drive past one intersection to reach the next
- Use a `for` loop to drive a chosen number of intersections
- Write `drive_intersections(count)` from its docstring, test it, and use it

</Objectives>

## Why the second call works

Try a thought experiment: call `track_to_intersection()` twice in a row with nothing in
between. Where does the robot end up?

<Figure
  src="/img/lesson-m3-02/second-track.svg"
  alt="Two animated top-down drawings of the XRP driving up a taped line that crosses two other lines, each beside the code it runs. Left: track_to_intersection() then track_to_intersection() again. The first call follows the line until the sensors reach the first cross; the second returns at once, because the sensors are still on the cross and is_at_cross() is already True, so the robot never gets past the first intersection. Right: track_to_intersection(), drive_past_intersection(), track_to_intersection(). The drive-past moves the robot 8.75 cm so its center of rotation is on the cross and its sensors are past the tape, and the second track follows the line to the next intersection."
  caption="Without the drive-past, the second track starts with its sensors on the cross and is finished before it begins. With it, the sensors are on plain line and there is a new cross ahead."
/>

The first call stops with both sensors on the cross, so the second call's loop
condition — `not is_at_cross()` — is already `False` and the robot "arrives" without
moving. That is the second job of `drive_past_intersection()`, the one Lesson 2-9
mentioned: as well as parking the center of rotation on the intersection, it carries the
sensors past the tape, so the next `track_to_intersection()` has a line to follow and a
new cross to find.

So the pattern for driving across the grid is just the arrival pair, repeated:
**track, drive past, track, drive past, …** — and because the drive-past parks the
robot on the intersection, it always ends up sitting on the last one, ready to turn.

## Drive a set number with a `for` loop

Writing the pair out by hand for each intersection is repetitive, and it's wrong the
moment you want a different number. A `for` loop over `range(count)` repeats the pair
a chosen number of times — the same shape as `polygon()` in Module 1, a loop and a
count, packaged into a function with the count as its parameter.

Nothing in the loop body changes from one pass to the next; the only thing the loop
variable is good for is the print ("Intersection 1 of 3", and so on — remember it
starts at 0). And there is no special case for the last intersection: the drive-past
parks the robot on it, which is exactly where you want to be.

<TeacherNote title="The off-by-one is gone; the thought experiment is the lesson">

Older versions of this lesson taught a timed nudge after each intersection, with an
`if i < count - 1` guard to skip it on the last one. The toolkit's
`drive_past_intersection()` replaces both: it is a fixed distance, and it parks the
wheels on the cross rather than past it, so there is nothing to skip. Spend the saved
time on the thought experiment at the top — trace two `track_to_intersection()` calls
with no drive-past on the board and have students say why the second one returns at
once. Then walk the loop with `i = 0, 1, 2` and have them say where the robot is after
each pass.

</TeacherNote>

## Activity · Two by hand, then the helper

The skeleton is pasted in. For every step the robot starts on a line segment, facing
the next intersection, with at least three intersections ahead of it.

### Step 1 · test_two_by_hand()

Before the loop, prove the thought experiment. Write the body: the arrival pair, then
the arrival pair again — four calls, no loop — and a print at the end. Set the run
line to `test_two_by_hand()` and run it. The robot should end parked on the *second*
intersection. Then try it: take out the first `drive_past_intersection()` and run
again. Where does the robot stop now, and what does the second track do? Put the call
back. Don't go on until the four-call version reaches the second intersection.

### Step 2 · drive_intersections(count)

Now write the function from its docstring: one parameter, a `for` loop over it, the
arrival pair inside, and a print so you can follow along. Write the body of
`test_drive_run()` — one call, `drive_intersections(3)`, and a print — set the run
line to it, and run. The robot should arrive three times, printing each one, and end
parked on the third intersection.

<Reveal title="Check your drive_intersections()" hint="write and test it first">

```python
def drive_intersections(count):
    """Arrive at count intersections in a row, printing
    which one it is each time. Ends parked on the last one
    with the sensors past it, ready to turn or to go on."""
    for i in range(count):
        print("  Intersection", i + 1, "of", count)
        track_to_intersection()
        drive_past_intersection()
```

If yours has an `if` in it, ask what it is guarding against — and whether
`drive_past_intersection()` actually drives the robot past anything. The two tests
are the arrival pair twice over, and `drive_intersections(3)` followed by a print.

</Reveal>

Now `drive_intersections(4)` drives four segments in one clean line — the building
block the next two lessons are made of.

<TeacherNote title="Solution (teacher copy)">

This lesson's addition to the GRID DRIVING section of `robot.py`, plus the run block;
the rest of the file is as the Lesson 3-1 teacher copy left it. The file is
`lesson-02-driving-multiple-intersections.py` in the Module 3 solutions. Class-track
students write `tracker.track_to_intersection()` and
`tracker.drive_past_intersection()` inside the helper; the helper itself stays a plain
function in this section.

```python
# --- Lesson 3-2: a run of intersections ---
# drive_intersections(count) is the arrival pair in a loop.
# It ends parked on the count-th intersection, so Lessons 3-3
# and 3-4 build every path out of it and the two turns.

def drive_intersections(count):
    """Arrive at count intersections in a row, printing
    which one it is each time. Ends parked on the last one
    with the sensors past it, ready to turn or to go on."""
    for i in range(count):
        print("  Intersection", i + 1, "of", count)
        track_to_intersection()
        drive_past_intersection()

def test_two_by_hand():
    track_to_intersection()
    drive_past_intersection()
    track_to_intersection()
    drive_past_intersection()
    print("Parked on the second intersection")

def test_drive_run():
    drive_intersections(3)
    print("Done! Parked on intersection 3")

# ===== RUN =====
board.wait_for_button()
test_drive_run()
```

</TeacherNote>

## Wrap-up

- Why does `drive_past_intersection()` have to come between two tracks? (The sensors are still on the cross; the second track would return at once.)
- What loop drives a set number of segments? (A `for` loop over `range(count)`, with the arrival pair inside.)
- Where is the robot after the last pass? (Parked on the last intersection — the drive-past puts the wheels on it.)
