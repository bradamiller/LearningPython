## A better toolbox

In Module 4 you built the `Manhattan` class — a path planner for a clear grid. `Dijkstra`
is a better one: it can route around obstacles. Compare the constructors:

```python
class Manhattan:
    def __init__(self, start):
        self.position = start

class Dijkstra:
    def __init__(self, start, rows=4, cols=4):
        self.position = start
        self.rows = rows
        self.cols = cols
        self.set_blocked_intersections([])    # nothing in the way, yet
```

You create them **the same way**. `Manhattan((0, 0))` and `Dijkstra((0, 0))` are both
valid, both mean "a planner that starts at the top-left corner," and that is not a
coincidence — it's the whole design, and Lesson 5-6 collects the reward.

`rows` and `cols` have defaults, so `Dijkstra((0, 0))` gives you the 4×4 grid you've been
driving. Manhattan never needed them, because its arithmetic works on a grid of any size;
Dijkstra has to actually *build* the graph, so it has to be told how big. Pass different
ones — `Dijkstra((0, 0), rows=3, cols=3)` — and the same class plans on a 3×3, which is
how you'll test it against the traces you did by hand in Lesson 5-3.

That last line is doing two jobs, and it's the more interesting half of the class.

### Telling the planner about obstacles

Obstacles aren't part of what a planner *is* — they're something it **finds out**. The
robot in Lesson 5-7 doesn't know where anything is when it starts; it discovers a blocked
intersection halfway through a journey, and then another one after that. So they get
handed over in their own method:

```python
def set_blocked_intersections(self, blocked):
    self.blocked = blocked
    self.graph = self.build_graph()      # rebuild around the new obstacles
```

Two lines, and the second one matters. The graph was built around whatever the planner
knew at the time, so changing `self.blocked` alone would leave a graph that still has
routes through a node you just blocked. Storing the new list and rebuilding go together —
that's exactly why this is a method rather than something you do by hand.

And now look back at `__init__`. It doesn't build the graph itself; it calls this method
with an empty list. **A brand-new planner is simply one that has been told there is
nothing in the way** — which is both true and one less place for `build_graph()` to be
called from. Setting up an object by calling its own methods is a good habit: there's
exactly one piece of code that knows how to bring the graph in line with the obstacles,
and everything goes through it.

<Callout kind="tip" title="Why appending to your own list isn't enough">

`self.blocked = blocked` is the reference idea from Lesson 4-3 doing real work: it stores
the *address* of your list, so the planner and your program now share one list. Append to
yours and the planner's `self.blocked` shows the new obstacle immediately — same list.

But `self.graph` is a different object entirely, built earlier, and nothing rebuilds it
just because a list changed. The planner would agree that (1,1) is blocked while happily
routing straight through it. Call `set_blocked_intersections()` and the rebuild happens.

</Callout>

## Activity · Build the Dijkstra class

Three steps, the same shape as the Manhattan class: store what has to persist,
stub out what you haven't written yet, and test the structure before you write
any of the hard part. `set_blocked_intersections()` from the section above goes into the
class too — it's two lines and you already have both of them.

### Step 1 · `build_graph` — build and block in one pass

This is the `build_grid_graph(rows, cols)` function from Lesson 5-2, adapted as a method
that also skips blocked nodes. It reads its grid size from `self` instead of taking
parameters, and does both jobs at once — skip a node if it's blocked, and only add a
neighbor if *that* neighbor isn't blocked:

```python
def build_graph(self):
    graph = {}
    for row in range(self.rows):
        for col in range(self.cols):
            if (row, col) in self.blocked:
                continue                                   # skip blocked node entirely
            neighbors = []
            if row > 0 and (row - 1, col) not in self.blocked:
                neighbors.append((row - 1, col))
            if row < self.rows - 1 and (row + 1, col) not in self.blocked:
                neighbors.append((row + 1, col))
            if col > 0 and (row, col - 1) not in self.blocked:
                neighbors.append((row, col - 1))
            if col < self.cols - 1 and (row, col + 1) not in self.blocked:
                neighbors.append((row, col + 1))
            graph[(row, col)] = neighbors
    return graph
```

Building and blocking together is cleaner than building the full graph and then removing
nodes in a second pass — a blocked node never enters the graph at all.

### Step 3 · Test the structure

Create a planner and check the graph against what you know from Lessons 5-1 and 5-2.
Start clear, then tell it about an obstacle and watch the graph change under you:

```python
d = Dijkstra((0, 0))
print(len(d.graph))          # 16 — the full 4×4 grid, nothing blocked yet
print(d.graph[(1, 1)])       # 4 neighbors

d.set_blocked_intersections([(1, 1)])
print(len(d.graph))          # 15
print((1, 1) in d.graph)     # False
print(d.graph[(0, 1)])       # does NOT include (1,1)
```

Each blocked node vanishes from the keys *and* from every neighbor list, so
`d.set_blocked_intersections([(1, 0), (2, 1)])` leaves you 14.

Notice the second call *replaced* what the planner knew — it didn't add to it. The list
you hand over is the complete set of obstacles, which is what makes it safe to call over
and over while driving.

Now try a different grid size — this is the one you traced by hand in Lesson 5-3:

```python
d = Dijkstra((0, 0), rows=3, cols=3)
d.set_blocked_intersections([(1, 1)])
print(len(d.graph))          # 8 — nine squares minus the blocked one
```

## The shared interface

Here's the design payoff, and it's worth being precise about what "matches" means. Two
things have to line up: how you **create** the object, and how you **ask** it for a path.

<CardGrid>
  <InfoCard tag="Module 4" title="Manhattan(start)">
    <code>compute_path(destination)</code> → list of tuples. Fast, but no obstacles.
  </InfoCard>
  <InfoCard tag="Module 5" title="Dijkstra(start)">
    <code>compute_path(destination)</code> → list of tuples. Handles obstacles.
  </InfoCard>
</CardGrid>

Same creation, same method name, same return type — right down to both leaving the start
out of the path they hand back. So the Navigator can call
`pathfinder.compute_path(dest)` without knowing or caring which planner it's holding, and
swapping one for the other changes one word. You'll do it in Lesson 5-6.

Dijkstra has `set_blocked_intersections()` on top, which Manhattan doesn't. That's fine,
and it's worth seeing why: the Navigator never calls it. Extra abilities don't break a
swap — only a difference in the parts both classes are *used* through would.

<TeacherNote title="Build incrementally; watch the self. mistakes">

Build it bottom-up: `build_graph` first, tested on its own, then the setter, then
`__init__`. Where the methods sit in the file doesn't matter — `__init__` can happily call
a method written below it, because Python looks it up when the line actually runs — but
the method does have to be *written* before you create an object. A student who types
`__init__` and immediately tests it gets an AttributeError until the setter exists; worth
predicting out loud, so it lands as a rule about when names are looked up rather than
half an hour of confusion. Test the graph after each step, and add the placeholder last.
Never dump the whole class at once. Put the Manhattan and Dijkstra constructors side by
side — students who wobbled on classes in Module 4 get another pass here, and the fact
that the two lines now look the same is the point of the whole module. Common errors:
forgetting `self` (`position = start` instead of `self.position = start`), and expecting
to call `build_graph` manually when the constructor already does. Show what a graph looks
like if you forget the blocked-neighbor checks — a blocked node reappears as someone's
neighbor and the path goes wrong.

**The mistake worth staging on purpose:** append to a blocked list *after* handing it to
the planner and then ask for a path. Because the planner holds a reference to that same
list (Lesson 4-3), `d.blocked` shows the new obstacle — but `d.graph` was built before it
existed, so the path drives straight through. Print both and let the class work out why.
It takes five minutes and it teaches the difference between a value that is shared and a
result that was computed from it, which is a distinction they'll meet for the rest of
their lives in code.

</TeacherNote>

## Wrap-up

- What does `__init__` store, and which part does it hand to another method? (`self.position` and `self.rows`/`self.cols` directly; `set_blocked_intersections([])` does `self.blocked` and `self.graph`.)
- What two jobs does `build_graph` do at once? (Builds the grid and excludes blocked nodes.)
- Why does `set_blocked_intersections` rebuild the graph instead of just storing the list? (The graph was built around the old obstacles; storing alone would leave routes through a node you just blocked.)
- Why are obstacles not a constructor parameter? (The robot discovers them while driving — and keeping them out is what makes `Dijkstra(start)` look exactly like `Manhattan(start)`.)
