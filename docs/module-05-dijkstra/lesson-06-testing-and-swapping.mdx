## What makes a good test

A good test has a **known input**, an **expected output** you worked out yourself, and a
**check** that compares actual to expected. Test two scenarios: clear grids (Dijkstra
should match Manhattan's length) and grids with obstacles (Dijkstra should detour).

```python
d = Dijkstra((0, 0))
path = d.compute_path((3, 3))
print("Path:", path)
print("Steps:", len(path))         # expect 6 — the Manhattan distance
```

On a clear 4×4 grid, the path from (0,0) to (3,3) is 6 steps. The *route* Dijkstra picks
may differ from Manhattan's, but the **step count** must match — because there are many
shortest paths of equal length.

## Activity · Test the obstacle case

Block a node on the direct route and confirm Dijkstra both detours *and* never steps on a
blocked node:

```python
blocked = [(1, 0), (2, 2)]
d = Dijkstra((0, 0))
d.set_blocked_intersections(blocked)
path = d.compute_path((3, 3))
print("Path:", path)

for node in path:
    if node in blocked:
        print("ERROR: path goes through", node)
        break
else:
    print("PASS: path avoids all blocked nodes")
```

That `for/else` is handy: the `else` runs only if the loop finishes *without* `break` — so
it prints PASS only when no blocked node was found.

<KnowledgeCheck
  question="In a for/else loop, when does the else block run?"
  options={[
    {text: 'Every time, always'},
    {text: 'Only if the loop finishes without hitting break', correct: true},
    {text: 'Only if break is hit'},
    {text: 'Never'},
  ]}
  explanation="The else clause of a for loop runs only when the loop completes normally. A break skips it — perfect for 'passed unless we found a problem' checks."

## Activity · The two-line swap

Here's the reward for building Dijkstra with Manhattan's interface. Open the program you
wrote for the Lesson 4-9 project — your own file, not a copy of one. Near the top it
creates the planner:

```python
from manhattan import Manhattan

manhattan = Manhattan((0, 0))
navigator = Navigator((0, 0), 0)
# ... then the destination loop: compute_path, drive_path, and the
#     manhattan.position = navigator.position line after each leg
```

Change **two lines** — the import, and the object you create:

```python
from dijkstra import Dijkstra

manhattan = Dijkstra((0, 0))          # ← the only real change
navigator = Navigator((0, 0), 0)
# ... and the loop below is untouched. All of it.
```

That's the whole swap. The destination loop doesn't change, `drive_path` doesn't change,
and `manhattan.position = navigator.position` — the line you were warned everyone forgets
— is still there doing the same job for the same reason. The Navigator calls
`compute_path(dest)` exactly as before and never finds out that anything happened.

<Callout kind="tip" title="Then rename it, once the robot has driven">

Leaving a Dijkstra planner in a variable called `manhattan` is confusing, and you should
fix it — but *after* you've watched the robot drive. Make the swap work first with the
smallest possible change, then rename `manhattan` to `planner` everywhere as a separate
step. Two changes at once means that when something breaks you don't know which one did
it, and that habit is worth more than the tidy name.

</Callout>

### Where the obstacles go now

One thing genuinely is new. A Dijkstra that's never been told anything believes the grid
is clear, so a straight swap gives you exactly Manhattan's behaviour — which is the right
way to start, because it proves the swap itself works before obstacles can muddy the
picture.

When you're ready for a detour, tell the planner what's out there:

```python
manhattan.set_blocked_intersections([(1, 0), (2, 2)])
```

That's a line you *add*, not one you change — and it is the one thing you could not have
done with Manhattan at all.

## Shared interface = polymorphism

When two classes offer the same method names, parameters, and return types, code that uses
one automatically works with the other. That's a **shared interface**, and the ability to
swap them is called **polymorphism** ("many forms").

<CardGrid>
  <InfoCard tag="Everyday" title="USB-C">
    One connector, many devices. The port doesn't care what's plugged in — same interface.
  </InfoCard>
  <InfoCard tag="Everyday" title="Power outlets">
    Any appliance with a standard plug works in any outlet. Shared interface, swappable devices.
  </InfoCard>
  <InfoCard tag="Code" title="Pathfinders">
    Navigator + compute_path() = any planner that fits the interface. Manhattan or Dijkstra, its choice.
  </InfoCard>
</CardGrid>

You've been *using* polymorphism the moment you swapped planners — the fancy word is just
a label for something simple: if two things work the same from the outside, use either.

<KnowledgeCheck

## Wrap-up

- What three parts make a good test? (Known input, hand-calculated expected output, a check.)
- What two lines change to swap in Dijkstra? (The import, and the line that creates the planner.)
- What has to happen before Dijkstra will route around anything? (`set_blocked_intersections()` — a new planner assumes the grid is clear.)
- What is a shared interface, and what's the swap ability called? (Same method signature/return; polymorphism.)

<TeacherNote title="Make the swap dramatic — and don't over-formalize polymorphism">

The two-line swap is the concrete payoff for the careful design in Lessons 5-4 and 5-5; show the
old code, make the change live, run it. Spend time on *testing* before the swap even though
students want the "cool part" — hand-calculate expected paths, don't copy code output.
Keep polymorphism light: "if two things work the same from the outside, you can use either"
is enough; USB-C and outlets make it concrete. Let students notice Manhattan and Dijkstra
sometimes return different paths of equal length — a good teaching moment about multiple
optimal solutions. Save the test files; Lessons 5-7 through 5-9 reuse them.

</TeacherNote>

## Note on the interface

Both planners take a **start** when created and a **destination** in `compute_path`:
`Manhattan((0,0))` and `Dijkstra((0,0))` both answer `compute_path((3,3))` with a list
of grid tuples. That shared shape is exactly what makes the swap a two-line change.

The agreement has to be exact, down to the first element. Neither planner includes
the robot's current position in what it returns — it's already there — so both step
counts are plain `len(path)` and `Navigator.drive_path` can drive either list
without knowing which planner produced it. If one of them returned the start and
the other didn't, the swap would still *run*, and the robot would quietly waste its
first move on every route. That's the kind of bug a shared interface is supposed to
prevent, and it only works if both sides honour it.
