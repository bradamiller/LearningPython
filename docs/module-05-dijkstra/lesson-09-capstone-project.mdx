## The mission

Your robot is an autonomous delivery vehicle. It must visit four or more grid destinations
in sequence, and for each leg: plan a path, drive it while watching for obstacles, and
reroute whenever the rangefinder finds one. Everything you need already exists — Dijkstra
(Lessons 5-4 and 5-5), the swap into Navigator (Lesson 5-6), detection (Lesson 5-7), and file memory
(Lesson 5-8). Today you connect them.

You'll demonstrate with **two runs**: Run 1 (delete the obstacle file, discover obstacles
the hard way, save them) and Run 2 (load the file, plan around known obstacles, reroute
less). The drop in step count between runs *is* the learning.

## Program structure

The whole program has a clear skeleton:

```
1. Load obstacles from file
2. Define destinations
3. For each destination:
     While not arrived:
        Compute a path with Dijkstra (from current position, current blocked list)
        Walk the path, checking the rangefinder at each intersection
        If obstacle: add to blocked list, recompute
        If clear all the way: arrived
4. Save obstacles to file
5. Print results (steps, reroutes)
```

The **blocked list is the thread** tying it together: `load_obstacles` produces it,
`Dijkstra` consumes it, detection appends to it, and `save_obstacles` writes it out.

## The navigation loop

The core is a nested loop — destinations on the outside, rerouting in the middle, walking a
single path on the inside:

```python
for dest in destinations:
    arrived = False
    while not arrived:
        pathfinder = Dijkstra(current, blocked)
        path = pathfinder.compute_path(dest)
        if len(path) == 0:
{/* TODO-BUG: compute_path returns an empty list both for "already there" and for "unreachable", so a round trip that ends where it started reports "No path" and skips its last leg. [REVIEW §1.7] */}

            print("No path to", dest); break

        rerouted = False
        for next_stop in path:                       # path starts at the NEXT
            distance = rangefinder.distance()        # intersection, not here
{/* TODO-BUG: THRESHOLD is undefined — L5-7 defines OBSTACLE_THRESHOLD. The loop also reads the rangefinder BEFORE turning toward next_stop and then blames next_stop for the reading, so if the next stop is left or right the wrong node gets blocked. And there is no drive call anywhere in this loop, so the robot never moves. [REVIEW §1.7] */}

            if distance < THRESHOLD:
                blocked.append(next_stop)            # obstacle ahead
                reroute_count += 1
                rerouted = True
                break
            current = next_stop                      # drive one intersection
            step_count += 1

        if not rerouted:
            arrived = True
```

When an obstacle appears mid-path, you `break` out, having added it to `blocked` — and the
`while` loop computes a fresh path from where you now stand.

## Activity · Test in simulation, then drive

{/* TODO-ANSWERS: the capstone's core loop is printed on the student page, and the rubric below grades the part it hands over. M4 L9 is the model: skeleton for students, working program in a TeacherNote. [REVIEW §3] */}

Get the whole thing working with a **simulated** rangefinder before the robot — verify
paths compute, obstacles register, the blocked list grows, and `obstacles.txt` is written
correctly. Then swap in the real sensor and the `DifferentialDrive`.

```python
ACTUAL_OBSTACLES = [(1, 0), (2, 2), (1, 3)]
def simulate_rangefinder(next_pos):
    return 8.0 if next_pos in ACTUAL_OBSTACLES else 50.0
```

Watch for the classic integration bugs: the blocked list getting reset between destinations
(it must persist across all of them), `current` not updating after a move, or forgetting to
make a *new* Dijkstra after the blocked list changes.

<TeacherNote title="Integration is the hard part — simulate first, celebrate the journey">

Students underestimate how hard connecting working parts is. The recurring bugs: passing a
stale blocked list, not updating `current`, not rebuilding Dijkstra after the blocked list
changes, and mis-formatted file I/O. Insist everyone gets the simulation version working
before the robot — logic first, hardware second. Use the rubric as a self-assessment
checklist; each row maps to a lesson. At the demo, ask *why* Run 2 is better and listen for
"better data," not "the robot is smarter." For 50-minute periods this spans 2–3 days
(assembly/simulation, robot testing, demos). Finally: take a moment to mark how far students
have come — from "Hello, World" to an autonomous robot that navigates, senses, and learns.
That's a real accomplishment.

</TeacherNote>
