In Lesson 5-7 the robot rediscovered every obstacle from scratch each run — like being
surprised by the same construction zone every morning. This lesson gives it **memory**: it
remembers obstacles from one run and plans smarter on the next. Just like Waze learns from
drivers, the robot learns from its own experience.

<Objectives>

By the end of this lesson you will be able to:

- Explain why remembering obstacles improves navigation
- Keep a blocked list across runs so the robot pre-plans around known obstacles
- Compare Run 1 and Run 2 with metrics (steps, reroutes)
- Explain the GPS/Waze analogy for crowd-sourced obstacle data
- Carry what one run discovered into the next by handing the blocked list back in

</Objectives>

## Why memory matters

The Dijkstra algorithm doesn't change between runs. The Navigator doesn't change. Only the
**input** changes — the blocked list starts with more information:

```
Run 1: empty blocked list  → discover obstacles the hard way → many reroutes
Run 2: pre-loaded list     → plan around known obstacles      → few or no reroutes
```

**Better data leads to better performance.** The robot isn't running a smarter algorithm on
Run 2 — it's running the *same* algorithm on better information.

```

```

Fill it in from your own two runs — the numbers are the evidence, and they'll
differ with your grid and where the obstacles sit.

Keeping the same `blocked_list` variable across both runs is all it takes — its Run 1
discoveries are already there when Run 2 begins.

## Could Run 2 still find new obstacles?

Yes. Run 2 avoids everything it *already* knows, but its smarter route may pass nodes Run 1
never visited — and one of those could be blocked. So Run 2 can still discover something
new, and Run 3 would start with even more knowledge. Eventually the robot knows every
relevant obstacle and its paths are optimal from the start — that's **convergence**.

## Activity · Carry what you learned into the next run

Within one program run, a list variable persists between function calls. But close
the program and it's gone — Python variables don't survive a restart. So how does
Run 2 begin already knowing what Run 1 found out?

You tell it. At the end of the run, print what the robot learned:

```python
print("Obstacles found:", blocked)
# → Obstacles found: [(1, 2), (2, 2), (3, 0)]
```

Then type that list into the top of your program, where the blocked list starts out:

```python
blocked = [(1, 2), (2, 2), (3, 0)]        # what Run 1 discovered
pathfinder = Dijkstra((0, 0))
pathfinder.set_blocked_intersections(blocked)
```

Run it again. The robot plans around all three from its very first path and never
reroutes for them — and if it finds a fourth, print the list again and carry that
across too.

That's the whole lesson in two lines of typing: **you are the memory.** The robot
found the obstacles, you carried them from one run to the next, and the algorithm
never changed. A real system would write the list somewhere and read it back itself
rather than waiting for a person — but *what* gets carried across, and what it's
worth, is exactly what you just did by hand.

<TeacherNote title="The Waze analogy lands; make Run 1 vs Run 2 dramatic">

Frame memory with Waze — students get it instantly ("what if Waze forgot every traffic
report when you closed the app?"). Set up the grid so Run 1 has 2–3 reroutes; the contrast
with a zero-reroute Run 2 is the "aha." Use the simulation (`two_run_navigation.py`) before
hardware so the concept lands without sensor noise. Insist on recorded numbers — steps,
reroutes — the quantitative comparison convinces far more than "it felt faster."

**Carrying the list by hand is the point, not a shortcut.** Typing Run 1's discoveries
into the top of the program makes the "same algorithm, better data" claim something
students do with their own fingers, and it keeps the lesson about navigation instead of
about file formats. If someone asks why the robot can't save it itself — good question,
that is exactly what a real one does, and it changes nothing about *what* is carried.
Be honest about limits:
what if an obstacle *moves*? Real systems need to forget stale data, not just accumulate —
good discussion for advanced students. Connect lightly to machine learning: accumulate
data, make better decisions.

</TeacherNote>
