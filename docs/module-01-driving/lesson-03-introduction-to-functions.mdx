Your square program works — but what if you want to draw *three* squares? Copying
the whole loop three times gets long and messy fast. In this lesson you'll learn
to write the square code **once**, give it a name, and reuse it as many times as
you like. That's a **function**.

<Objectives>

By the end of this lesson you will be able to:

- Explain what a function is — a named, reusable block of code
- Define a function in Blockly using the **"to do something"** block — and say why
  the version with a **return** value isn't the one you want here
- Call your function from the main program
- Recognize when a function will make your code shorter and easier to change

</Objectives>

## The copy-paste problem

Here's how you'd draw three squares *without* a function — the same loop, pasted
three times:

<BlockProgram
  blocks={[
    {name: 'repeat', note: 'square #1', children: [
      {name: 'straight', note: 'cm: 30'},
      {name: 'turn', note: 'Deg: 90'},
    ]},
    {name: 'repeat', note: 'square #2 — same thing again', children: [
      {name: 'straight', note: 'cm: 30'},
      {name: 'turn', note: 'Deg: 90'},
    ]},
  ]}
  caption="Repetition like this is a signal you want a function."
/>

If you later want bigger squares, you have to change the number in *three* places
and hope you don't miss one. A function fixes that.

<TeacherNote title="Hook">

Put the copy-pasted version on the board and ask "what's annoying about this?"
Students will land on *it's long* and *hard to change* on their own — that felt
need is the reason functions exist. Use the recipe-card analogy: write the recipe
once, cook from it as many times as you want.

</TeacherNote>

## Define once, call many times

A function has two parts, and keeping them straight is the whole lesson:

- **Define** — where you *write* what the function does. In Blockly this is the
  **"to do something"** block; rename it to `square` and drop your Repeat
  loop inside it.
- **Call** — where you *use* it. A new **square** block appears in the
  Functions palette; drag it into your main program wherever you want a square.

<BlockProgram
  blocks={[
    {name: 'function_def', note: 'rename to "square"', children: [
      {name: 'repeat', note: 'repeat 4 times', children: [
        {name: 'straight', note: 'cm: 30'},
        {name: 'turn', note: 'Deg: 90'},
      ]},
    ]},
  ]}
  caption="The definition: the square loop now lives inside a function named square."
/>

<Callout title="Two function blocks in the palette — take the first one">

Open the **Functions** category and you'll find *two* definition blocks that look
almost the same. The one you want says **to do something** and nothing else. The
other one has a **return** socket on its bottom row — leave that one alone for
this whole module.

The difference isn't cosmetic. A plain function is a stack block: it snaps into
your program like any other command. A function with a return value is a
*rounded* block instead, because it stands for a **value**, not an action — so
when you go to call it, it won't snap into your program at all. It only fits in
a slot where a number or a word belongs, like the *cm* box on a Straight block.

If your `square` call block looks rounded and refuses to click into place, that's
the symptom: you picked the return version. Delete it and build the definition
again with the plain block.

</Callout>

You'll use `return` eventually — in Lesson 1-10, when you write Python functions
that *work something out* and hand back the answer, like the turn angle for a
polygon. But `square` doesn't compute an answer; it drives the robot. There's
nothing to hand back, so there's no return.

Your main program then becomes short and readable — wait for the button, then
call `square` as many times as you want:

<BlockProgram
  blocks={[
    {name: 'wait_for_button_press'},
    {name: 'call_square', alt: 'square call block', note: 'the call block is just the function’s name'},
    {name: 'call_square', alt: 'square call block'},
    {name: 'call_square', alt: 'square call block'},
  ]}
  caption="Three squares, three blocks. Everything about how a square gets drawn lives in the definition — the main program only says when."
/>

Notice the call block carries no extra wording: it's labelled **square**, because
that's the name you gave the function. Your own functions turn into blocks that
sit in the palette alongside the built-in ones.

## Activity · Build reusable shapes

**Say it in English first.** Before you build anything, write one or two plain
sentences on paper describing what your function should do — for example:
*"square: repeat 4 times — drive 30 cm, then turn 90°."* If you can't
describe it in words, you're not ready to build it in blocks. Do the same for
`triangle` before step 3.

1. Take your square loop from Lesson 1-2 and move it inside a new function named
   `square`.
2. In the main program, call `square` a few times and watch the robot retrace the
   same square each time.
3. Now make a second function, `triangle` — Repeat 3, and work the turn angle out
   with the rule from Lesson 1-2 rather than looking it up. Call both in a sequence.

<KnowledgeCheck
  question="You want bigger squares everywhere in your program. With a square function, how many places do you change the size?"
  options={[
    {text: 'One — just inside the function', correct: true},
    {text: 'One for every time you called it'},
    {text: 'You have to rewrite the function'},
    {text: 'Two'},
  ]}
  explanation="That's the payoff of a function: fix or change it in one place, and every call updates automatically."
/>

<TeacherNote title="Differentiation & common slip">

**More support:** give a program with the function already made and ask students
just to add `call` blocks. **More challenge:** have them build a pattern —
square, triangle, square, triangle — from four calls. **Watch for:** students who
*re-define* the function instead of *calling* it. Point them to the ready-made
`square` block in the Functions palette.

**The return-block slip.** The two definition blocks sit next to each other in the
palette and read almost identically, so a handful of students will grab the one
with the return socket every year. They usually don't notice at the definition
stage — everything looks fine until the call block comes out rounded and won't
connect, and then they assume they've broken something. Name the two blocks when
you demo, and when a hand goes up over a call block that won't snap, that's the
first thing to check. The fix is to delete the definition and rebuild it with the
plain block; the blocks inside can be dragged out and reused rather than rebuilt.

</TeacherNote>

## Wrap-up

- Why put repeated code in a function? (Write once, reuse, and change it in one place.)
- What are the two parts of using a function? (Define it, then call it.)
- Does defining a function make the robot move? (No — only calling it does.)
