## From "to do something" to `def`

Here's the reusable square, Blockly on top and Python below:

```python
def square():
    for i in range(4):
        drivetrain.straight(30)
        drivetrain.turn(90)

square()
square()
square()
```

The pieces map to what you already know:

- `def` — the keyword that *defines* a function (like the "to do something" block).
- `square` — the name (lowercase, words joined by underscores).
- `()` — the parameter list (empty for now).
- `:` and indentation — everything indented is the function **body**.
- `square()` — *calls* it. Define it once at the top; call it as often as you like.

<TeacherNote title="Order matters in Python">

A difference from Blockly worth calling out: Python reads **top to bottom**, so a
function must be *defined above* the line that calls it. "Called before it's
defined" is a common first error — the fix is simply to move the `def` block up.
Reinforce that this is the text version of the exact same define/call idea from
Lesson 1-3.

</TeacherNote>

## Parameters make it flexible

Just like the gear icon added an input in Blockly, a name inside the parentheses
adds a parameter in Python:

```python
def square(side_length):
    for i in range(4):
        drivetrain.straight(side_length)
        drivetrain.turn(90)

square(30)
square(50)
square(20)
```

The `side_length` **parameter** is a local variable; the numbers you pass (`30`,
`50`, `20`) are the **arguments** — the same names you used in Blockly. Add more
parameters by separating them with commas: `def square(side_length, effort):`.

## Returning a value

Some functions *do* something (draw a square); others *calculate* something and
**return** an answer. The `return` keyword hands a value back to whoever called it:

```python
def calculate_angle(sides):
    return 360 / sides

angle = calculate_angle(6)
print(f"Hexagon angle: {angle}")     # → Hexagon angle: 60.0
```

You can then build bigger functions from smaller ones — a `polygon` that uses
`calculate_angle`:

```python
def polygon(sides, side_length):
    angle = calculate_angle(sides)
    for i in range(sides):
        drivetrain.straight(side_length)
        drivetrain.turn(angle)

polygon(4, 30)   # square
polygon(3, 25)   # triangle
polygon(8, 15)   # octagon
```

## Where a variable lives

Look at `angle` in that last program. It's created inside `polygon`, and it's
**local** to it: it comes into existence when `polygon` starts running, and it's
gone the moment `polygon` finishes. Ask for it from the main program and Python
says it doesn't know the name.

```python
def polygon(sides, side_length):
    angle = calculate_angle(sides)      # angle is born here
    ...                                 # and dies when polygon returns

polygon(4, 30)
print(angle)          # NameError — there's no angle out here
```

Parameters work the same way. `sides` and `side_length` are locals too; they're
just locals that arrive already holding the values you passed in. That's why two
different functions can both use a parameter called `sides` without interfering —
each call gets its own.

This is a feature, not a restriction. Because a function's working names are
sealed inside it, you can write one without checking what every other function in
your program happens to have called things.

### So why does `drivetrain` work?

Fair question, because it breaks the pattern. Look again:

```python
drivetrain = DifferentialDrive.get_default_differential_drive()

def square(side_length):
    for i in range(4):
        drivetrain.straight(side_length)      # not local — where's this from?
```

`drivetrain` isn't a parameter and it isn't created inside `square`. It's defined
out in the main program, and the rule is this: when Python meets a name inside a
function, it looks for a local one first, and if there isn't one it looks
**outside**. So a function can *read* names from the surrounding program. That's
exactly why the three-step XRPLib pattern works — you make the drivetrain once at
the top and every function you write can reach it.

Reading outward is fine and this course does it constantly. **Assigning** to an
outside name from inside a function is a different matter, and Python deliberately
makes it awkward: writing `drivetrain = something` inside a function creates a
*new local* by that name rather than changing the outer one. We're not going to
need that in Module 1. When you get to classes in Module 2, `self.` turns out to
be the clean answer to "how does an object remember something between calls" —
this is the problem it solves.

<TeacherNote title="Don't over-promise the sealed box">

The tempting simplification — "functions can't see outside themselves" — is one
students will immediately disprove, because every robot program in this course
calls `drivetrain` from inside a function. Teach the actual rule instead: **local
first, then look outward**. It's no harder and it survives contact with the code
in front of them.

Keep `global` out of it. It isn't needed anywhere in this course, and the honest
framing is that the read/write asymmetry is a nudge toward passing values in and
returning them out — which is the habit Module 2's classes then formalize.

If a student asks what happens when a local has the same name as an outer one, the
answer is that the local wins inside the function and the outer one is untouched.
Demonstrating that with two `print()` calls takes thirty seconds and settles it.

</TeacherNote>

## Activity · Build a shape library

   function you built in Blockly in Lesson 1-5, now in Python.
2. Add a helper `calculate_perimeter(sides, side_length)` that **returns**
