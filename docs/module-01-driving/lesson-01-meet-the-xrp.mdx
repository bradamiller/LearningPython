## Part 1 · The parts of the robot

Before we program the XRP, let's see what we're working with. Every part has one
job, and knowing them makes debugging much easier later.

<Figure
  src="/img/lesson-01/xrp-parts.jpg"
  alt="The XRP kit laid out and labeled: chassis, wheels, O-rings, hobby motors with encoders, XRP controller board, battery holder and cover, ultrasonic distance sensor, line follower, servo, casters, clips, lift arm, and Qwiic cable"
  caption="Everything in the XRP kit, labeled. Find each part in front of you as it comes up below."
/>

- **Wheels & motors** — Two motors, one per side. Each motor spins one wheel.
  Because the sides move independently, the robot can steer.
- **Controller board** — The robot's "brain." It receives your program over USB
  and tells the motors what to do.
- **Battery** — Powers everything. A low battery makes the robot sluggish.
- **Sensors** — Reflectance sensors (see light vs. dark — labeled *Line Follower*
  in the diagram) and an ultrasonic rangefinder (measures distance). You'll use
  these in later modules.
- **Caster wheel** — The little rear wheel that keeps the robot balanced.

<TeacherNote title="Hardware tour tips (15–20 min)">

Hold up a real robot and point to each part as you go. Quick checks for
understanding:

- Point out the left and right motors — ask which one spins to turn the robot left.
- Show where the USB plugs in; explain this is how programs get onto the robot.
- Only *name* the sensors for now — they come into play in Modules 2–5.

</TeacherNote>

## Part 2 · How the robot gets instructions

A robot only does what you tell it. The workflow is always the same:

1. **Write** a program (we'll use Blockly).
2. **Connect** your computer to the robot — by USB cable or over Bluetooth.
3. **Upload** the program to the robot.
4. The robot **runs** the program — each command in order.

Step 3 matters: writing a program isn't enough. It has to be uploaded before the
robot can run it.

### Two ways to connect

**USB cable.** Plug the robot into your computer. This is how you'll connect
today, and it's the connection every robot needs the *first* time — XRP Code
uses it to install and update the software that lives on the robot.

**Bluetooth.** Once a robot has been set up over USB, XRP Code can reach it
wirelessly. Unplug the cable, turn the robot on, click **CONNECT**, choose
**Bluetooth**, and pick your robot from the list. Everything works exactly as it
does over USB — you're just not tethered to the table anymore, which matters a
lot once the robot is driving around the floor.

Every XRP has its own **ID**, shown under the RUN button while it's connected.
Write yours on the robot so you can pick it out of the list — and don't pair
with somebody else's robot.

<TeacherNote title="Bluetooth in a classroom">

Worth setting up early — a tethered robot can only drive as far as the cable,
and Lesson 2 has them driving squares on the floor. Practical notes:

- **Do the USB pass first.** Connect every robot by cable once, let XRP Code
  finish its update, and **label each robot with its ID** (it shows under the RUN
  button). Without labels, a room full of XRPs in the pairing list is chaos.
- **Low batteries kill Bluetooth before anything else.** If a robot connects
  over USB but not wirelessly, charge it before troubleshooting anything else.
- **A running program can block the connection** — press the robot's reset button
  so it restarts without running, then connect.
- Use **Chrome or Edge**; XRP Code's Bluetooth support needs a Chromium browser
  (Safari and Firefox won't show the option). On Windows, give it up to ~20
  seconds after a dropped connection before retrying.
- Keep a few known-good USB cables at the demo station regardless — USB is the
  fallback whenever wireless acts up.

</TeacherNote>

## Part 3 · Your first program in XRP Code

Open **[xrpcode.wpi.edu](https://xrpcode.wpi.edu/)** in your browser. This is
where you'll build programs by dragging blocks.

<Video
  placeholderLabel="Screen recording — creating a project & the three key blocks"
  caption="A quick tour of XRP Code: the block palette, the work area, and the upload button."
/>

A few blocks do everything you need today. Drag them out of the block palette:

- The **Wait for button press** block <Block name="wait_for_button_press" /> goes
  at the very top. A program starts running the moment it's uploaded — this block
  makes the robot sit still until you press its button, so it doesn't drive off
  the table while you're still holding it.
- The **Straight** block <Block name="straight" /> drives in a straight line.
  **cm** is how far to go — a *negative* number drives backward — and **Effort**
  is how hard the motors push, from `0` to `1` (`0.5` is a good starting speed).
- The **Turn** block <Block name="turn" /> turns the robot in place. **Deg** is
  the angle (`90` is a quarter turn); **Effort** works the same way.

You don't need a block to stop at the end — when the program finishes, the robot
stops the motors for you.

Here's the program we'll build together — wait for the button, drive forward,
then come back. Set the second **Straight** block's *cm* to a negative number so
the robot reverses:

## Part 4 · Upload and run it

<TeacherNote title="Guided practice — first upload (10–15 min)">

Have students create a new project named `Lesson_1_First_Drive` and rebuild the
worked example. Then: plug in USB → **Upload** → pick the robot → wait for
"Upload Successful" → press the button on the robot to run. Expect it to drive
~20 cm out and back to roughly where it started. Keep everyone on the cable for
this first upload — it's also the USB pass that makes Bluetooth possible later.

</TeacherNote>

Follow these steps:

1. Create a new project called **Lesson_1_First_Drive**.
2. Build the forward/backward program from above.
3. Connect the robot: plug in the USB cable (use the cable today — your robot
   needs one USB connection before it can go wireless).
4. Click **Upload** and choose your robot from the list.
5. Wait for **"Upload Successful,"** set the robot on the floor, then press the
   button on the robot — your **Wait for button press** block releases the
   program and it runs.

**You've succeeded when:**

- [ ] The program uploads without errors
- [ ] The robot drives forward about 20 cm
- [ ] The robot drives back about 20 cm
- [ ] It stops near where it started

### If something goes wrong

- **Robot won't move** — check the battery is charged and the USB is seated, then re-upload.
- **Drives the wrong way** — motor directions can be reversed; that's normal and fixable later.
- **Not exactly the distance you set** — floor friction and battery level affect distance. Close is fine for now.
- **Robot not in the upload list** — try another USB port or cable (some cables are charge-only), then reload the page.
- **Robot doesn't appear over Bluetooth** — charge the battery first (a low battery stops Bluetooth before anything else), press the robot's reset button so it isn't busy running a program, and make sure you're in Chrome or Edge. Still stuck? Plug in the cable and keep going.

<TeacherNote title="Common setup snags">

The USB-not-detected issue is almost always a **charge-only cable** or a flaky
port. Keep a couple of known-good data cables at the demo station. If an upload
"fails," have students wait ten seconds and try once more before troubleshooting
further.

</TeacherNote>

## Part 5 · Make it your own

Now experiment. Try these in order:

1. **Go farther** — change the *cm* on both **Straight** blocks to `30` and re-run.
2. **Change the effort** — try `0.3`, then `0.8`. What changes: how *far* the
   robot goes, how *fast* it gets there, or both? Measure before you decide.
3. **Add a turn** — drop a **Turn** block <Block name="turn" /> between the two
   Straight blocks. What shape does the path make now?
4. **Challenge** — can you make the robot drive a square and end up back where
   it started? No hints: try something, run it, watch, adjust. (Lesson 2 picks up
   right here, so whatever you figure out now is a head start.)

<TeacherNote title="Differentiation">

**Need more challenge?** Have students measure the distance the robot travels at
Effort `0.3`, `0.5`, `0.7`, and `1.0` and report what changes. **Need more
support?** Provide a starter project with the blocks pre-placed and ask them to
change only the *cm* number, and pair-program with defined Driver/Navigator roles.

</TeacherNote>
