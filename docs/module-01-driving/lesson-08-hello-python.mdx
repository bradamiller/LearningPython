## Why switch to Python at all?

Blockly wasn't training wheels. Every idea you've used so far — loops, functions,
parameters — is a real programming idea, and you learned it without spending a
single minute on typos. That was the point: get the thinking first.

But Blockly can only offer you the blocks somebody built for it. Python is a
**general-purpose programming language**, which means it isn't tied to robots, or
to any one job. It's one of the most widely used languages in the world, and the
same Python you're about to write also shows up in:

- **Web development** — the servers behind sites and apps
- **Data science** — analyzing and charting real data sets
- **Machine learning and artificial intelligence** — most of the field's everyday
  tools are written in or driven by Python
- **Automation** — the scripts that do a tedious job so a person doesn't have to
- and plenty more, from scientific research to finance to visual effects

The practical reason matters just as much. As programs get bigger, the thing that
saves you isn't writing faster — it's **not having to write it at all**. Python
gives you access to an enormous body of software **libraries and frameworks**:
code other people have already written, tested, and handed over for anyone to use.
Need to read a sensor, talk to a website, do statistics, or draw a graph? Somebody
has almost certainly published good code for it, and using it is usually a single
import line.

You're about to meet exactly that in the next section — `XRPLib`, the library that
makes your robot's motors and sensors a few words of Python instead of a semester
of electronics. It's the same deal the professionals get, just aimed at a robot
that fits on a desk.

<TeacherNote title="Answering 'why did we waste time on blocks, then?'">

Somebody asks this every year, usually the student who's already programmed a
little, and the honest answer lands better than a defensive one: they learned
loops, functions and parameters without losing a single class period to missing
colons, and those ideas transfer intact — which they're about to see for
themselves when the same square program comes out the other side in text.

If you want a concrete hook for the library argument, name something students
recognize: Instagram's servers run on Django, a Python web framework; Spotify
leans on Python for the data and recommendation pipelines behind its playlists;
and the first image of a black hole was assembled with Python libraries. The point
isn't the trivia, it's that none of those teams wrote their own math, plotting or
networking code from scratch. Neither will your students, starting with XRPLib in
the next section.

</TeacherNote>

## The same program, two ways

Here's the **Straight** block you've used all module, and the Python that does the
exact same thing:

<BlockProgram
  blocks={[{name: 'straight', note: 'the block you know'}]}
/>

```python
from XRPLib.differential_drive import DifferentialDrive

drivetrain = DifferentialDrive.get_default_differential_drive()
drivetrain.straight(30)
```

Reading it line by line:

```python
from XRPLib.differential_drive import DifferentialDrive
```

Bring in the robot-control library.

```python
drivetrain = DifferentialDrive.get_default_differential_drive()
```

Get the robot's wheels as an object you can command.

```python
drivetrain.straight(30)
```

Drive straight 30 cm. Use a negative number to go backward, just like the block.

### What's a library?

`XRPLib` is a **library** — code somebody else already wrote, tested, and left on
the robot for you to use. Making a motor turn a wheel at a steady speed means
timing electrical pulses and counting encoder ticks; reading the reflectance
sensor means measuring how much light bounces back and turning that into a number.
That work is genuinely hard, it's already done, and it's sitting in the library.

Picture a shelf of books, one book per piece of hardware — one for the drivetrain,
one for the reflectance sensor, one for the rangefinder, one for the servo. You
don't read the whole shelf. You take down the one book you need, when you need it.

<Figure
  src="/img/lesson-08/library-shelf.svg"
  alt="A bookshelf labeled XRPLib with a book for each device — Reflectance, Rangefinder, Servo, IMU, Board, Encoder, Motor — and the DifferentialDrive book taken off the shelf, its pages listing straight(), turn() and set_effort()"
  caption="XRPLib is the shelf; each class is a book. An import takes one book down — and what's written inside it are the commands you can use."
/>

That's what `import` does. This line:

```python
from XRPLib.differential_drive import DifferentialDrive
```

takes the **DifferentialDrive** book off the shelf and opens it on your desk.
What's written inside are the things a drivetrain can do: `straight()`, `turn()`,
`set_effort()`. Leave the book on the shelf and Python has no idea those words
mean anything.

You import each device as you need it, which is why the import lines at the top of
a program are a decent table of contents for what the program touches.

### Three steps — and they never change

Those three lines aren't a driving recipe. They're how you use **any** piece of
hardware in XRPLib, so once you have the shape you can read code for a device
you've never touched:

**1 · Import the class.**

```python
from XRPLib.differential_drive import DifferentialDrive
```

This tells Python where the code for that piece of hardware lives. Nothing
happens to the robot yet.

**2 · Make an instance.**

```python
drivetrain = DifferentialDrive.get_default_differential_drive()
```

This hands you an object that stands for the real hardware bolted to your robot.
The name on the left is yours to pick — `drivetrain` is just a good one.

**3 · Use it.**

```python
drivetrain.straight(30)
```

Instance name, a dot, then what you want it to do. That `instance.method()` shape
is most of the Python you'll write from here on.

The device changes; the three steps don't. Here is the **reflectance sensor** you
meet in the next module — read it against the drivetrain code above:

```python
from XRPLib.reflectance import Reflectance            # 1 · import the class
reflectance = Reflectance.get_default_reflectance()   # 2 · make an instance
reflectance.get_left()                                # 3 · use it
```

And the **rangefinder**, later on:

```python
from XRPLib.rangefinder import Rangefinder            # 1 · import the class
rangefinder = Rangefinder.get_default_rangefinder()   # 2 · make an instance
rangefinder.distance()                                # 3 · use it
```

Line them up beside the drivetrain and only the names differ. That's the whole
trick: when a new device shows up, you already know two thirds of the code before
anyone explains it.

<Callout kind="tip" title="Let the editor do the spelling">

Those class names are long, and Python is fussy about capitals (`Rangefinder`, not
`rangefinder`). You don't have to type them. Start typing the first few
characters — `Diff` — and the editor offers `DifferentialDrive`; press Tab or
Enter to accept it. The same works after a dot: type `drivetrain.` and it lists
everything the drivetrain can do, which is also a quick way to discover methods
nobody told you about.

If the suggestion never appears, the name you're typing probably isn't imported
yet — which is a useful hint in itself.

</Callout>

<TeacherNote title="The three steps are the spine of Modules 2–5">

Worth slowing down on, because every later module reuses it: import the class,
make an instance, call methods on the instance. Students who learn it as a
*pattern* read the reflectance and rangefinder lessons as variations; students who
memorise these particular three lines meet each new device as a fresh mystery.

A good board exercise: write the three rows of the table with the device column
filled in and the rest blank, and have students complete the reflectance row from
the drivetrain one before they've seen any sensor code. Most can.

Note the capital/lowercase convention while you're here — `Rangefinder` is the
class, `rangefinder` is their variable — and point out that the editor's
autocomplete gets the capitals right for them.

</TeacherNote>

<TeacherNote title="Frame it as 'the next level,' not 'harder'">

The mindset that makes this lesson land: Python isn't harder than Blockly, it's
the *same ideas written differently*. Put a Blockly program and its Python next to
each other and let students match them up. The one genuinely new thing is
**syntax** — the punctuation rules — so name that explicitly and normalize making
mistakes with it.

</TeacherNote>

## The five syntax rules

Blockly never let you make a spelling mistake. Python will, so five rules matter.
Here are the three you need today:

1. **Lowercase** — `print` is not `Print`. Names are case-sensitive.
2. **Parentheses** — they're what tells Python "this name is a **function call** —
   go run it." `print` on its own just names the function; `print()` runs it. Inside
   the parentheses go the **arguments**: the values you're handing the function to
   work with. Some functions need one (`print("hello")`), some need several
   (`drivetrain.straight(30)`), and some need none at all — but the parentheses go
   in either way, empty or not.
3. **Quotes** — text goes in quotes: `print("hello")`.

The other two are about writing code that spans *several* lines, and every program
in this lesson is a straight list of one-line instructions. You'll meet them in
Lesson 1-10, at the moment you need them.

<TeacherNote title="Why three now and two later">

The two held back — colons and indentation — only make sense once there is a
*block* of code to belong to, and the first one arrives in Lesson 1-10's `for`
loop. Introducing them here means five rules memorized and three practiced, with
the other two half-forgotten by the time they matter.

Don't let it read as something skipped. The lesson promises two more by name, and
Lesson 1-10 opens by collecting on that promise — students should recognize it as
a debt being paid, not a surprise.

</TeacherNote>

## Activity · Write your first Python program

Same tool, different file. Python lives in **XRP Code**, exactly where your
blocks did — `File → New File`, then choose **MICROPYTHON** instead of Blockly.
The window is the one you already know: your robot's files down the left, the
editor in the middle, and the **shell** along the bottom, which is where
`print()` output shows up.

Create a file called `lesson_1_8_first_drive.py` — the lesson number, then what
the program does — and type this in. Typing, not pasting; it builds muscle memory.
Then press **RUN**:

```python
from XRPLib.differential_drive import DifferentialDrive
from XRPLib.board import Board

drivetrain = DifferentialDrive.get_default_differential_drive()
board = Board.get_default_board()

board.wait_for_button()

print("Driving forward...")
drivetrain.straight(30)

print("Driving backward...")
drivetrain.straight(-30)

print("Done!")
```

`board.wait_for_button()` is the **Wait for button press** block you used all
through Blockly, in text. It matters more here than it looks: pressing RUN starts
the program immediately, so without that line the robot drives off the moment you
upload it — usually off the desk. Put the robot on the floor, press RUN, *then*
press the button on the robot.

Watch the shell at the bottom: your `print()` messages appear there as the robot
runs, so you can see exactly where it is in the program.

<TeacherNote title="print() is a debugging superpower">

Encourage *liberal* use of `print()` — a message before and after each action
turns an invisible program into a visible one. This is the habit that makes the
Python lessons debuggable. Let students hit real syntax errors and practice reading
the messages; that's the skill, and the errors here are the easy kind — one line,
one mistake. (Indentation is the #1 stumble overall, but it can't happen yet:
nothing in this lesson is indented. It arrives with the `for` loop in Lesson 1-10,
where a whitespace-visible editor and auto-indent earn their keep.)

</TeacherNote>
