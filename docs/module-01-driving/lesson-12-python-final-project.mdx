## Activity · Plan before you code

Professionals design before they build. On paper first:

1. **Problem statement** — one or two sentences: what will your robot do?
2. **Function inventory** — list the functions you'll need, with their parameters
   (e.g. `polygon(sides, side_length)`, `navigate_segment(distance, angle)`).
3. **Pseudocode** — the flow in plain English, not Python:

```text
Program:
    set up the robot
    for each shape in my design:
        draw the shape
        move to the next spot
    announce "done"
```

## A clean program structure

Good Python programs have a shape: a docstring at the top saying what this is,
then the imports and setup, then your functions, and finally the handful of lines
that actually run the show. Use this as your skeleton:

```python
"""
Module 1 Final Project: <your project name>
Team: <names>
Description: <two-sentence overview>
"""

from XRPLib.differential_drive import DifferentialDrive
from XRPLib.board import Board
import time

drivetrain = DifferentialDrive.get_default_differential_drive()
board = Board.get_default_board()

# ===== HELPER FUNCTIONS =====
def calculate_angle(sides):
    """Return the exterior angle of a regular polygon."""
    return 360 / sides

# ===== MAIN FUNCTIONS =====
def polygon(sides, side_length):
    """Draw one regular polygon."""
    angle = calculate_angle(sides)
    for i in range(sides):
        drivetrain.straight(side_length)
        drivetrain.turn(angle)

# ===== RUN =====
board.wait_for_button()

print("Starting...")
polygon(4, 30)
time.sleep(1)
polygon(6, 25)
print("Done!")
```

Everything above the `# ===== RUN =====` line *defines* things; nothing happens
until the lines beneath it. That split is the point of the layout — someone opening
your file can read the last few lines to find out what the program does, then go
looking for the function that does it.

Order still matters, the way it has since Lesson 1-11: a function has to be defined
above the line that calls it, which is why the running code sits at the bottom
rather than the top.

### The two kinds of note in that program

Look again at the skeleton and you'll see notes written in two different ways.

The `#` lines are **comments**, the kind you met in Lesson 1-8: Python ignores
everything after the `#`. The banner lines are doing a job you'll appreciate on a
long file — dividing it into labeled regions you can find at a glance:

```python
# ===== HELPER FUNCTIONS =====
```

The triple-quoted pieces are different. A string in quotes, written on its own as
the **first thing inside** a function, a class or a file, is a **docstring** — short
for *documentation string*. Triple quotes are ordinary Python quotes with one extra
ability: the text can run across several lines, which is why the one at the top of
the file can hold a title, a team and a description:

```python
def calculate_angle(sides):
    """Return the exterior angle of a regular polygon."""
    return 360 / sides
```

The practical difference is that a docstring doesn't vanish the way a comment does.
Python keeps it, attached to the thing it describes, so tools can read it back —
`help(calculate_angle)` prints that sentence, and your editor shows it when you
hover over a call. A `#` comment above the `def` would look almost identical on
screen and be gone the moment the file is loaded.

So: **docstring for what a function is for, comment for why a line is the way it
is.** One sentence, present tense, saying what the caller gets — "Return the
exterior angle of a regular polygon", not "This function calculates…".

<Callout kind="tip" title="Write them for the person who opens this in six months">

That person is usually you. The comment worth writing is the one that records
something the code can't say on its own — why the effort is `0.5` and not `0.8`,
which surface you measured the turn on, what you already tried that didn't work.
A comment that just renames the line beneath it (`# turn 90 degrees` above
`drivetrain.turn(90)`) is noise, and worse, it's a lie waiting to happen: change
the code and the comment quietly goes stale.

</Callout>

<TeacherNote title="The comment conversation worth having">

Students arrive with one of two habits: comment nothing, or comment every line
because a previous class graded on it. Neither survives contact with a real
program. The line that lands is that a comment is **a message to a future
reader**, and the test is whether it says something the code cannot.

A demonstration that takes two minutes: put `# turn 90 degrees` above a
`drivetrain.turn(90)`, then change the call to `turn(120)` and ask what the
comment is now. Stale comments are worse than none, because people believe them.

Don't grade docstrings on wording. One clear sentence per function is the whole
ask at this stage; `help()` in the shell is a nice payoff to demonstrate once, so
they see the docstring come back out of a function they wrote themselves.

</TeacherNote>

## Activity · Build, test, and polish

Work the same loop engineers use:

1. **Build** one function; **test** it on its own with a few inputs.
2. **Integrate** — call it from the run section alongside the others; test the flow.
3. **Instrument** — sprinkle `print()` messages so you can see what's happening.
4. **Polish** — add a one-line docstring to each function, add comments where a
   line needs a *why*, remove leftover debug prints, and make your names clear.

<TeacherNote title="Running the capstone">

Treat this as a multi-day arc: **plan → build → test → document → present.** Have
teams turn in a short written plan (problem, function list, pseudocode) before
they code, and enforce test-in-pieces. A simple rubric weights design/planning,
implementation, testing evidence, documentation, and a short reflection roughly
equally — reward process and debugging, not just a flawless demo. Teams of 2–3
with rotating roles (programmer / tester / documenter) work well; a five-minute
showcase at the end lets everyone see the range of solutions.

</TeacherNote>
