You have a weight. Now the program needs it. This lesson starts a new section of
`robot.py` with a list of slow segments next to the blocked list, a `weight()` function
that answers "what does this edge cost?", and a `path_cost()` that adds a route up —
and then adds *cost* to the Module 5 harness as one more thing it checks. BFS,
unchanged, fails that check. On paper, with the path printed, before any robot is
involved. That failure is the reason the next lesson exists.

<Objectives>

By the end of this lesson you will be able to:

- Store slow segments as `(a, b, cost)` entries and add one with `add_slow_edge()`
- Write `weight(a, b)` so it returns the slow cost in either direction and 1 otherwise
- Write `path_cost(position, path)` by walking the path and summing weights
- Write `check_cost()`, the cost check, and explain what its FAIL line means
- State BFS's limitation precisely: it minimizes steps, and cost is not steps

## A second list, next to `BLOCKED`

Module 5 kept the things the planner needs to know about the grid in one list,
`BLOCKED`, fed through `add_blocked()` and emptied by `clear_blocked()`. Slow segments
get the same treatment: `SLOW_EDGES`, fed through `add_slow_edge()`, emptied by
`clear_slow_edges()`. Both of those are one-liners shaped like their Module 5 twins.

A slow segment is a property of the *edge* between two intersections, not of either
intersection, so each entry holds both ends and the weight you measured:
`add_slow_edge((0, 1), (0, 2), 5)` appends the tuple `((0, 1), (0, 2), 5)`.

Then one function answers the question every planner will ask: `weight(a, b)`. It
loops over `SLOW_EDGES` looking for the pair, and returns 1 if it never finds it. Read
the docstring's "in either order" carefully. The robot might drive the segment from
(0, 1) to (0, 2) or from (0, 2) to (0, 1), and it's slow both ways, so the test inside
the loop has to match the pair *either* way round — that's an `or` of two comparisons.
Anything not in the list costs 1: a normal block.

## Adding up a route

A path from the planner is a list of intersections to drive to, not including the
start. Its cost is the weight of every segment driven: from the start to the first
step, from that step to the next, and so on.

So `path_cost()` keeps a running total and a `here` that starts at the robot's
position and moves forward one step each pass — the same shape as `drive_path()`'s
`position = next_pos`. For `[(0, 1), (0, 2), (0, 3)]` from (0, 0), with the slow edge
at 5, that's 1 + 5 + 1 = 7.

## The sixth property

The Module 5 harness checks five properties of a path. Add a sixth: the path's cost
equals the cheapest possible. For now you work out the cheapest by hand — trace the
routes on the grid and add them up — and type the number in; the next lesson writes
the planner that finds it.

`check_cost()` is shaped like Lesson 5-6's `run_no_path_test()`: it prints a PASS
line or a FAIL line in the same format and returns `True` on a pass, so that the
harness can count it. The one difference is that it is handed the *path*, not the
planner, so you can point it at any planner's answer. A PASS line and a FAIL line as
they should look:

```text
  PASS  open grid  [(0, 1), (0, 2), (0, 3)]  cost: 3
  FAIL  slow grid  [(0, 1), (0, 2), (0, 3)]  cost: 7
          - the cheapest route costs 5
```

### Step 3 · `check_cost()`, against BFS

Write `check_cost()`. Then a second test — `test_cost_check()` — that runs it against
BFS twice. First on the open grid: clear the blocked list *and* the slow list, plan
`(0, 0)` to `(0, 3)` with `compute_bfs_path()`, and check it against a cost of 3.
Then add the slow segment at weight 5, plan the same trip, and check it against 5 —
the cost of the detour you added up in Lesson 6-1. Set the run line to it:

```text
  PASS  open grid  [(0, 1), (0, 2), (0, 3)]  cost: 3
  FAIL  slow grid  [(0, 1), (0, 2), (0, 3)]  cost: 7
          - the cheapest route costs 5
```

There it is. Not a crash, not a wrong turn on the floor: a FAIL line with the path
printed, and you can see exactly what BFS did. It drove the slow road, because it
counts steps and 3 is less than 5.

If you built the `BFS` class, the plan comes from `planner.compute_path()` and the
blocked list is cleared with `planner.clear_blocked()`; the slow list is this section's
own, so `add_slow_edge()` and `clear_slow_edges()` are called as written.

<Reveal title="Check your five functions" hint="run both tests first">

```python
def add_slow_edge(a, b, cost):
    """Record the segment between a and b as costing cost."""
    SLOW_EDGES.append((a, b, cost))

def clear_slow_edges():
    """Empty SLOW_EDGES in place, as clear_blocked() does."""
    while len(SLOW_EDGES) > 0:
        SLOW_EDGES.pop()

def weight(a, b):
    """Cost of driving from a to b: the slow cost if that
    segment is in SLOW_EDGES, in either order; otherwise 1."""
    for (end1, end2, cost) in SLOW_EDGES:
        if (a == end1 and b == end2) or (a == end2 and b == end1):
            return cost
    return 1

def path_cost(position, path):
    """Total cost of driving path from position: the weight
    of every segment, starting with position to path[0]."""
    total = 0
    here = position
    for step in path:
        total = total + weight(here, step)
        here = step
    return total

def check_cost(test_name, position, destination, path, expected_cost):
    """Print PASS if path costs expected_cost, else FAIL with
    the cost and the path; return True on a pass."""
    cost = path_cost(position, path)
    if cost == expected_cost:
        print("  PASS ", test_name, "", path, " cost:", cost)
        return True
    print("  FAIL ", test_name, "", path, " cost:", cost)
    print("          - the cheapest route costs", expected_cost)
    return False
```

The `for` line unpacks each three-part entry into the segment's two ends, `end1` and
`end2`, and its `cost` as the loop goes: the unpacking from Lesson 4-2, done once per
pass. The parentheses around the three names are optional; Python reads the line the
same way without them. (They are not called `x` and `y`: those are the two numbers
*inside* one intersection, and each end here is a whole intersection.) If yours differs and
both tests give the numbers above, keep yours.

</Reveal>

<TeacherNote title="On paper, with the path printed — that is the pedagogy">

This is Lesson 5-6's idea doing its job: the failure is a FAIL line with the offending
path, found at a desk, not a robot taking the long way while everyone wonders. Make
students write the expected cost by hand before they run the check; if they let the
program tell them what to expect, the test tests nothing (Lesson 4-6's point).

Two things to watch. The `or` in `weight()` is easy to drop, and then the check passes
or fails depending on which way the robot happens to drive the segment — a good bug to
plant. And `path_cost()` must start from `position`, not from `path[0]`; students who
start at `path[0]` miss the first segment and get costs one too small (step 2 of the
activity is written to catch exactly that).

`check_cost()` prints in the 5-6 harness's format and returns `True` on a pass for a
reason: next lesson it becomes the seventh case inside `run_all_tests()` (the sixth
property, checked on the slow grid), and the count line becomes "of 7". `clear_slow_edges()` exists for the same reason — the
harness has to run its open-grid cases with no slow edges, or Dijkstra's five-step
detour would fail the step-count property.

Name the limitation exactly: *BFS minimizes steps; it never looks at a weight.* Don't
say BFS is wrong. Next lesson keeps 90% of it.

</TeacherNote>
