BFS fails the cost check because it never looks at a weight. The fix is not a new
algorithm written from scratch. It is your BFS, copied, renamed, and changed in two
places in the middle. Everything else — the graph, `add_blocked()`, the `previous`
dictionary, the walk-back — stays exactly as you wrote it in Module 5. The result is
**Dijkstra's algorithm**, and by the end of the lesson you'll have three planners
running through one harness.

<Objectives>

By the end of this lesson you will be able to:

- Add the cost check to `run_all_tests()` as its seventh case
- Duplicate `compute_bfs_path()` as `compute_dijkstra_path()` and keep the parts that don't change
- Make change 1: take the **closest** intersection off `to_visit`, not the oldest
- Make change 2: add the segment's **weight**, and keep the cheaper total when an intersection is reached again
- Read a `print_grid()` of costs and explain each number
- Run Manhattan, BFS and Dijkstra through the same harness and say where they agree and disagree

</Objectives>

## Change 1 · Closest first, not oldest first

BFS takes intersections off `to_visit` in the order they went on — `to_visit.pop(0)`
— and that works because every step costs the same: the oldest entry is always one of
the closest. With weights that's no longer true. An intersection reached by a cheap
detour may be closer, in cost, than one that went on the list earlier by a slow road.

So Dijkstra keeps a second dictionary, `distance`, holding the cheapest cost found so
far to each intersection — it starts as `{position: 0}`, because the start costs
nothing to reach — and each time round the loop it takes the waiting intersection with
the smallest value. That lookup is `closest(to_visit, distance)`: start by assuming the
first entry is best, loop over the rest, and keep any entry whose `distance` is smaller
— the same pattern as finding the biggest number in a list in Module 1, with the
comparison turned round. `pop(0)` did two jobs, choosing *and* removing; `closest()`
only chooses, so the line after it has to `remove()` the chosen one from `to_visit`.

## Change 2 · Add the weight, and keep the cheaper way

BFS marks a neighbor the first time it sees it and never reconsiders; the first way to
reach it is always a shortest way, in steps. Dijkstra adds the edge's weight to get the
cost of reaching the neighbor *this* way, and if that beats what it already had, it
updates. Compare the pencil versions of the two neighbor loops:

<SideBySide left="BFS (Module 5)" right="Dijkstra">
<div>

```python
# for each neighbor of current:
#     only if it has no entry yet:
#         write where it came from
#         put it on the END of the list
```

</div>
<div>

```python
# for each neighbor of current:
#     this way costs: current's cost
#         + weight(current, neighbor)
#     if no cost yet, OR this is cheaper:
#         write the cost
#         write where it came from
#         put it on the list, if not on it
```

</div>
</SideBySide>

Three things to notice. "Has no entry yet" was `not in previous` in BFS; now it's
`not in distance`, because `distance` is the dictionary that says whether a cost has
been found. The *or* is the whole of change 2: a neighbor that already has a cost gets
reconsidered, and loses its old cost and its old came-from if this way is cheaper.
And "if not on it" matters now, where it didn't in BFS: a neighbor can be reached a
second time while it is still waiting on `to_visit`, and it must not be listed twice.

`previous[neighbor] = current` is still how the path gets remembered, and the walk-back
at the end of the function is untouched. The only new idea is that `previous` can be
*overwritten* when a cheaper way turns up.

## The cost grid

Dijkstra's `distance` dictionary is a map of how far everything is, in cost, from the
start. `dijkstra_distances()` is to `compute_dijkstra_path()` what `bfs_rings()` was
to `compute_bfs_path()` in Lesson 5-5: the setup and the search with no `break` and no
walk-back, returning `distance` itself. Write it, then add one line to
`test_cost_grid()`:

```python
print_grid(ROWS, COLS, BLOCKED, dijkstra_distances((0, 0)))
```

```text
 3 |   5  4  5  6
 2 |   4  3  4  5
 1 |   1  2  3  4
 0 |   0  1  2  3
    -------------
       0  1  2  3
```

Read up the left edge, x = 0: (0, 1) costs 1, then (0, 2) costs **4**, not 2. The slow
segment would make it 1 + 5 = 6; going over to (1, 1), up to (1, 2) and back left costs
1 + 1 + 1 + 1 = 4, so 4 is what gets kept. That one cell is change 2 doing its job. Everywhere
else, the numbers are Module 5's BFS rings.

```python
def closest(intersections, distance):
    """Return the entry of intersections with the smallest
    value in distance: a plain find-the-minimum loop."""
    best = intersections[0]
    for node in intersections:
        if distance[node] < distance[best]:
            best = node
    return best

def compute_dijkstra_path(position, destination):
    """Cheapest path from position to destination around
    BLOCKED, by weight(), as the intersections to drive to."""
    graph = build_graph(ROWS, COLS, BLOCKED)
    if position not in graph or destination not in graph:
        return []
    previous = {position: None}
    distance = {position: 0}                   # NEW
    to_visit = [position]

    while len(to_visit) > 0:
        current = closest(to_visit, distance)  # CHANGE 1: was pop(0)
        to_visit.remove(current)
        if current == destination:
            break
        for neighbor in graph[current]:
            new_distance = distance[current] + weight(current, neighbor)   # CHANGE 2
            if neighbor not in distance or new_distance < distance[neighbor]:
                distance[neighbor] = new_distance
                previous[neighbor] = current
                if neighbor not in to_visit:
                    to_visit.append(neighbor)

    if destination not in previous:
        return []
    path = []
    current = destination
    while current != position:
        path.append(current)
        current = previous[current]
    path.reverse()
    return path

def dijkstra_distances(position):
    """Cheapest cost to every reachable intersection, as a
    dictionary -- the search with no break, like bfs_rings()."""
    graph = build_graph(ROWS, COLS, BLOCKED)
    if position not in graph:
        return {}
    distance = {position: 0}
    to_visit = [position]
    while len(to_visit) > 0:
        current = closest(to_visit, distance)
        to_visit.remove(current)
        for neighbor in graph[current]:
            new_distance = distance[current] + weight(current, neighbor)
            if neighbor not in distance or new_distance < distance[neighbor]:
                distance[neighbor] = new_distance
                if neighbor not in to_visit:
                    to_visit.append(neighbor)
    return distance
```

Everything outside the two `CHANGE` regions is your BFS, line for line. If yours
passes 7 of 7 and draws the grid above, keep yours.

<TeacherNote title="Copy first, change second — and stop at two changes">

The lesson's shape is the point: a working thing, copied, changed in two marked places,
tested after each. Students who try to write Dijkstra fresh get lost in `to_visit`
bookkeeping; students who copy BFS and change two lines have it working in twenty
minutes and can explain both changes. That is why the outline in the skeleton is only
the two changes and the walk-back is "unchanged": the BFS body goes in first, and the
comments are a checklist, not a second algorithm.

The harness edit comes *first*, deliberately: a copy that fails 6 of 7 exactly as BFS
does is the proof that the copy is faithful, and watching the seventh case flip to PASS
at step 2 is the lesson's payoff. The "if not on it" check is the line students skip —
without it the open-grid cases still pass but `to_visit` fills with duplicates, so ask
them why BFS never needed it.

`closest()` is a linear scan. Real implementations use a priority queue, and the old
version of this material taught one; don't. For a 4×4 grid the scan is instant, and
the queue is machinery that obscures the two ideas. If a student asks, "a priority
queue is a faster way to do what `closest()` does" is the whole answer.

The cost grid is where the understanding shows. Ask students to point at the one cell
that differs from BFS and say why before they look at the explanation.

</TeacherNote>
