## One name changes

`SLOW_SEGMENT` is one tuple holding the two ends and the weight, so it can be typed in
once and handed to `add_slow_edge()` as `SLOW_SEGMENT[0]`, `SLOW_SEGMENT[1]`,
`SLOW_SEGMENT[2]` — the same indexing as Lesson 4-2's tuples. Then the test chooses
its planner by name:

```python
    if PLANNER_NAME == "Dijkstra":
        planner = compute_dijkstra_path
    else:
        planner = compute_bfs_path
```

`planner = compute_dijkstra_path` is the Lesson 5-6 swap: a function handed around by
name, with no parentheses. From that line on, `planner(position, destination)` is
whichever one was chosen, and `drive_path()` is handed the list it returns with no idea
which planner produced it.

Before the button, the test calls `compare()` — so both plans, with their step counts
and costs, are on the screen before either run happens:

```text
  BFS       steps: 3  cost: 7   [(0, 1), (0, 2), (0, 3)]
  Dijkstra  steps: 5  cost: 5   [(1, 0), (1, 1), (1, 2), (0, 2), (0, 3)]
```

Then the usual two presses: the one in `RUN` starts the test and prints the plans; the
one in the test is *go*. The timing is `time.time()` just before `drive_path()` and
just after, the difference being the seconds the drive took — a check on the stopwatch.

## Activity · Two runs, one stopwatch

1. Write `test_drive_slow_grid()` from the outline. Type your measured slow segment
   into `SLOW_SEGMENT`, set the run line to the test, and run it with the robot on the
   desk: read the two printed plans and check the costs match what you worked out on
   paper in Lesson 6-1. Don't press the second button yet. Don't go on until the
   printed costs are right.
2. `PLANNER_NAME = "BFS"`. Robot at (0, 0) facing North on the slow grid. Run, read
   the printed path, press the button, start a stopwatch with the robot. Record the
   time. Watch it take the slow road.
3. `PLANNER_NAME = "Dijkstra"`. Same start, same destination. Record the time. Watch
   it go round.
4. Fill in the table:

```text
Planner    steps   cost   seconds
BFS         ___    ___     ___
Dijkstra    ___    ___     ___
```

The program's own elapsed time is a check on your stopwatch. The two should tell the
same story: more steps, fewer seconds.

```python
def test_drive_slow_grid():
    clear_slow_edges()
    add_slow_edge(SLOW_SEGMENT[0], SLOW_SEGMENT[1], SLOW_SEGMENT[2])

    else:
        planner = compute_bfs_path

    compare(position, destination)
    path = planner(position, destination)
    board.wait_for_button()

    start_time = time.time()
    position, heading = drive_path(path, position, heading)
    elapsed = time.time() - start_time
    print(PLANNER_NAME, "took", round(elapsed, 1), "seconds for", len(path), "steps")
```

<TeacherNote title="Make it a class event">

Run the two trips back to back with the whole class watching and one student on a
stopwatch. The robot visibly choosing the long way round and arriving sooner is the
module's payoff; let it land before the discussion.

Before the button, have students read both printed plans aloud and predict the two
times from the costs and the per-block time they measured in 6-1. Then compare.
Discrepancies are a good conversation: turns cost time too (the detour has more of
them), which is why the predicted gap is usually a little bigger than the measured
one. That is also a fair place to mention what the course left out — a planner that
weights turns needs to know the heading, and that is a bigger change than two lines.

If the two plans match, the slow segment is missing or too light. Fix the setup, not
the code.

</TeacherNote>
