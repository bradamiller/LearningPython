## How the robot "sees" a line

Flip an XRP over and you'll find two small reflectance sensors underneath. Each one
is a pair of parts sitting side by side: an **LED** that shines light down at the
surface, and a **phototransistor** right next to it that measures how much of that
light comes back.

<Figure
  src="/img/lesson-m2-01/reflectance-sensor.svg"
  alt="Two diagrams of a reflectance sensor. In each, an LED and a phototransistor point down from a sensor board. Over white, the light from the LED bounces strongly into the phototransistor and the reading is about 0.2. Over black tape, most of the light is absorbed, only a faint amount returns, and the reading is about 0.8."
  caption="The LED shines, the phototransistor listens. White bounces most of the light back — a low reading; black tape soaks it up — a high reading."
/>

Nothing in there measures color. The sensor only knows *how much light came back*,
which is why anything dark reads like a line and anything light reads like the
floor.

- **White surface** → most light bounces back → a **low** value (around `0.1–0.3`).
- **Black line** → light is absorbed → a **high** value (around `0.7–0.9`).

The XRP has a **left** and a **right** sensor, each with its own reading — which is
how the robot can tell *which side* of a line it's on.

## Read the sensors in Python

Reading a sensor is just importing its class and calling a method:

```python
from XRPLib.reflectance import Reflectance
from XRPLib.board import Board

reflectance = Reflectance.get_default_reflectance()
board = Board.get_default_board()

board.wait_for_button()

left = reflectance.get_left()
right = reflectance.get_right()
print("Left sensor:", left)
print("Right sensor:", right)
```

Run it and you get two numbers. Then the program ends.

That's worth sitting with for a second, because it's the first thing that will
frustrate you. Those two `get_left()` and `get_right()` calls happen **once**, at
the instant you press the button — they are a snapshot, not a live feed. Python
reaches the bottom of the file and the program is over, so sliding the robot across
the tape afterwards changes nothing on screen. The numbers you're looking at are
from wherever the robot was sitting when you pressed the button, and they'll stay
that way until you press RUN again.

Which is a problem, because what you actually want to know is how the readings
*change* as the robot moves. To see that, the reading has to happen over and over
— so it goes in a loop. Before you write that loop, though, there's one new tool
you'll need.

### Pausing a program with `time.sleep()`

A loop with nothing slowing it down runs *fast*. Fifty sensor readings would print
in a fraction of a second — long before you could move the robot — and then the
loop would be over. You need the program to take a short breath between readings.

Python comes with a built-in module called `time` for exactly this. It isn't part
of XRPLib; it ships with Python itself (and with MicroPython, the version of Python
running on the XRP). Like any module, you bring it into your program with an
`import` at the top:

```python
import time
```

That one line gives you access to everything in the module. The piece you want is
`sleep()`, and you reach it with a dot — `time.sleep()` means "the `sleep`
function that lives in the `time` module," the same way `reflectance.get_left()`
means "the `get_left` method that belongs to the reflectance sensor."

`time.sleep()` takes one number: **how many seconds to pause**. Whole numbers and
decimals both work:

- `time.sleep(1)` — wait one second
- `time.sleep(0.5)` — wait half a second
- `time.sleep(0.1)` — wait a tenth of a second

While it's sleeping, your program simply stops at that line and does nothing until
the time is up; then it carries on with the next line. (Anything already in motion
keeps going, though — if the motors were running when the program went to sleep,
they're still running.)

## One file, for the rest of the course

The loop you're about to write is the first piece of code you'll *keep*. Until now
every lesson started a new program. From here on you have **one file**, and each
lesson adds to it: the sensor functions through this module, the driving functions,
grid driving in Module 3, and so on to the end. Create it now — call it `robot.py` —
and paste in this start:

```python
from XRPLib.reflectance import Reflectance
from XRPLib.differential_drive import DifferentialDrive
from XRPLib.board import Board
import time

reflectance = Reflectance.get_default_reflectance()
drivetrain = DifferentialDrive.get_default_differential_drive()
board = Board.get_default_board()


# ===== RUN =====
board.wait_for_button()
# call ONE test function here
```

Two rules keep it working all year. **New code goes above the `RUN` block, never
below it.** Python runs a file top to bottom, so the run block has to be the last
thing, and everything it calls has to be defined above it. Each lesson gives you a
**skeleton** to paste in there: a banner comment naming the section, a few lines
saying what the section does, the settings it needs, the outlines of the functions
you're going to write, and a **test function** that exercises them. Then the one
line under `RUN` calls whichever test you're working on. **One test at a time** —
change the call, don't stack them. If you ever lose the file or join partway
through, the [robot.py templates](/templates) page has it as it stands after
every lesson, skeletons pasted and nothing written.

### Your first two functions

Here is this lesson's skeleton. Paste it above `RUN`.

```python
# ===== LINE SENSOR =====
# Reads the two reflectance sensors and answers questions
# about them. Starts here with the two raw readings; over this
# module it grows to answer "how far off the line am I?" and
# "am I on a line? on a cross?" Nothing in here drives.
# Everything that drives asks these functions instead of the
# hardware.

def get_left():
    # return the left reflectance reading
    pass

def get_right():
    # return the right reflectance reading
    pass

def test_sensors():
    # prints both readings 50 times, a tenth of a second apart
    for i in range(50):
        print("Left:", get_left(), "  Right:", get_right())
        time.sleep(0.1)
```

`get_left()` and `get_right()` are one line each: they `return` the reading from
`reflectance`. You wrote functions with `return` in Lesson 1-11, and the only new
thing here is that these use `reflectance` without being handed it — it was created at
the top of the file, outside any function, so every function below can see it, the
same way `polygon()` used `drivetrain` in Module 1.

**Where the returned value goes.** Think of a function call as a question and `return`
as its answer. When `test_sensors()` reaches its `print` line, Python stops at
`get_left()`, runs your function, and the value after its `return` takes the place of
the call. By the time `print` runs, it is as if you had typed the number itself,
say `0.23`, where `get_left()` was. Every program from here on
works that way: you ask `get_left()`, and you get a number back to print, compare or
do arithmetic with.

**Two things with the same name.** Your `get_left()` reads the sensor with
`reflectance.get_left()`, and that second one is *not* your function calling itself.
The `reflectance.` in front makes it the sensor's own method, the one you met above.
Yours is a plain function in your file that asks the sensor and passes its answer on.

**If it prints `None`, the `return` is missing.** A body that reads the sensor but
doesn't `return` the reading takes the reading and throws it away. A function that
ends without a `return` hands back `None`, which is Python's word for "nothing", so
`test_sensors()` prints `Left: None  Right: None` however you move the robot. The
sensor is fine; the number just never left the function.

Why wrap one line in a function? Because from now on **every** program you write
asks for a sensor reading by *this* name, and only this one place knows how the
hardware is read. In six lessons these two will be the bottom of a toolkit of
functions, and they will not have changed. `pass` means "nothing here yet" — it holds
the place of the body so the file runs before you've written one; delete it when the
real line goes in.

Write the two bodies, set the run line to `test_sensors()`, and run. Same two
readings as before; they just happen fifty times now, a tenth of a second apart,
which gives you about five seconds to slide the robot across the tape and watch the
numbers follow it. That shift — from *read it once* to *keep reading* — is the whole
idea behind the `while` loop in the next lesson, where the robot reads its sensors for
as long as it's driving.

<TeacherNote title="Setup that makes or breaks the readings">

Press the black tape down flat (no bubbles), keep the sensors a few millimeters
off the surface, and watch out for direct sunlight or bright overhead lights —
they shift the values (calibration handles this). Emphasize `print()` as the
number-one debugging tool all module. Have students **save their calibration data**;
they'll reuse it in Lessons 2-2 through 2-8.

**This is also where `robot.py` is born.** Make the two file rules a ritual today —
new code above `RUN`, one test call — because they're what keeps Module 5's file
readable. The two wrapper functions are deliberately trivial: the point is that
students call `get_left()` from here to the end of the course, and that when the
sensor toolkit is finished in Lesson 2-7 these two have been in use for six lessons.

</TeacherNote>

## Activity · Calibrate and pick a threshold

Every surface and every roll of tape is a little different, so you **calibrate** —
measure your own values — instead of trusting a textbook number. Run
`test_sensors()` and record readings in three positions: both sensors on white, both
on the black line, and one on the edge.

Then pick a **threshold** halfway between your highest white reading and your lowest
black reading. That's the number your programs will use to decide "on the line" vs.
"off."

> threshold = (highest white value + lowest black value) ÷ 2

<TeacherNote title="Why calibrate instead of just using 0.5?">

0.5 is a fine starting guess, but a glossy surface, a faded line, or bright room
lighting can push the real edge value well off 0.5. Students who calibrate get
line-following that actually works in Lessons 2-5 and 2-6; students who guess spend those
lessons fighting a bad threshold. Frame calibration as the professional habit it
is — real robots calibrate their sensors on startup.

</TeacherNote>
