## `for` vs. `while`

In Module 1 the `for` loop repeated a **fixed** number of times — `for i in
range(4)` draws four sides. But "drive until you hit the line" has no fixed count;
you don't know how many steps it'll take. That's a job for `while`, which repeats as
long as a condition stays true:

```python
while left < THRESHOLD:
    # this runs over and over while the sensor is on white
    # the moment left >= THRESHOLD, the loop stops
```

A `while` loop needs a **condition** — a test that's either `True` or `False`. We
build those with comparison operators:

```python
0.3 < 0.5    # True  (less than)
0.8 > 0.5    # True  (greater than)
0.5 == 0.5   # True  (equal to)
0.9 != 0.5   # True  (not equal to)
```

## Driving inside a loop: `set_effort()`

One more tool before you write the program. Every drive so far has been
`straight()` or `turn()`, and both **block**: they finish their distance before the
next line runs, so you can't watch a sensor while they're going. `set_effort(left,
right)` is different — it sets the motor power and returns *immediately*. The robot
keeps rolling while your program goes on to the next line, which means a loop can
drive and check a sensor on every pass:

```python
drivetrain.set_effort(0.3, 0.3)    # both motors at 30%, and come straight back
```

The motors stay on until something changes them — `drivetrain.stop()` turns them off.

<TeacherNote title="set_effort vs. straight()">

Worth stating outright: `straight()` **blocks** — it finishes its distance before
the next line runs, so you can't watch a sensor during it. `set_effort()` sets
motor power and returns instantly, which is exactly what a sensor loop needs. Keep
the speed low (`0.3` or less); momentum at higher speeds carries the robot past the
line before it can stop.

</TeacherNote>

### Step 1 · Write it and run it

Turn the comments into code and set the run line to `test_drive_to_line()`. Start the
robot inside the taped circle pointing at an edge, press the button, and watch it stop
at the line. If it stops as soon as you press the button, the sensor was already
reading "black" — check your threshold. If it never stops, read on.

### Step 2 · Either sensor

Switch to `get_right()` and make sure it still works. Then make the loop keep going
only while **both** sensors are still on white, so the robot stops when *either* one
hits the line — you'll need `and` between two conditions, and a second sensor read
inside the loop. (More on `and` and `or` next lesson.)

### Step 3 · Tidy it

Once step 2 works, try reading the sensors *in the condition itself*:

```python
while get_left() < THRESHOLD and get_right() < THRESHOLD:
```

Now there's no variable to remember to update — the sensors are read fresh every
time the condition is checked, which is every pass. Your loop body shrinks to one
line, and the two reads before the loop go away. Most sensor loops in this course
are written this way.

## The infinite-loop trap

Did your robot drive forever in step 1? Then your loop is missing its most important
line. If the sensor is read once *before* the loop and never again, the variable in the
condition never changes — so the condition never becomes false, and the robot drives
until you catch it. That's an **infinite loop**, and it is the most common bug in
every sensor program you'll ever write.

> The rule: always update the variable your `while` loop is checking, inside the loop —
> or put the sensor call in the condition, so there's no variable to forget.

Step 1, with a variable:

```python
def test_drive_to_line():
    left = get_left()
    while left < THRESHOLD:
        drivetrain.set_effort(0.3, 0.3)
        left = get_left()            # <- read again every pass!
    drivetrain.stop()
    print("Line detected! Sensor value:", left)
```

Step 3, with the reads in the condition:

```python
def test_drive_to_line():
    while get_left() < THRESHOLD and get_right() < THRESHOLD:
        drivetrain.set_effort(0.3, 0.3)
    drivetrain.stop()
    print("Line detected!")
```

<TeacherNote title="Solution (teacher copy)">

`robot.py` at the end of this lesson, in its step 3 form. The file is
`lesson-02-drive-to-the-edge.py` in the Module 2 solutions. This lesson used to hand
students the whole program; now the setup is the file they already have, and the loop
is theirs, because they have every piece by this point. Expect a third of the room to
write the infinite loop on the first try — that is the lesson, and the section below
the activity is written to be read *after* it happens. The variable version (step 1)
is the one that *can* fall into the trap, which is why students write it first; the
condition-read version is where they end up.

```python
from XRPLib.reflectance import Reflectance
from XRPLib.differential_drive import DifferentialDrive
from XRPLib.board import Board
import time

reflectance = Reflectance.get_default_reflectance()
drivetrain = DifferentialDrive.get_default_differential_drive()
board = Board.get_default_board()

# ===== LINE SENSOR =====
# Reads the two reflectance sensors and answers questions
# about them. Starts here with the two raw readings; over this
# module it grows to answer "how far off the line am I?" and
# "am I on a line? on a cross?" Nothing in here drives.
# Everything that drives asks these functions instead of the
# hardware.
THRESHOLD = 0.5

def get_left():
    return reflectance.get_left()

def get_right():
    return reflectance.get_right()

def test_sensors():
    for i in range(50):
        print("Left:", get_left(), "  Right:", get_right())
        time.sleep(0.1)

def test_drive_to_line():
    while get_left() < THRESHOLD and get_right() < THRESHOLD:
        drivetrain.set_effort(0.3, 0.3)
    drivetrain.stop()
    print("Line detected!")

# ===== RUN =====
board.wait_for_button()
test_drive_to_line()
```

</TeacherNote>

<TeacherNote title="Differentiation">

**More support:** start with a non-robot counting loop (`count = 0; while count <
5: ...`) so the loop mechanics are clear before sensors enter, and give the first
line (`left = get_left()`) of the body. Use effort `0.2` so there's time
to observe. **More challenge:** count the loop iterations before the line is found,
or flash the LED on detection.

</TeacherNote>
