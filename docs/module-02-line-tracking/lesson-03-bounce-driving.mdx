Stopping at the line is fine — but what if the robot should keep going, bouncing off
each edge like a ball in a box? To do that, the robot has to make a **decision** every
moment: *if* I see the line, turn around; *otherwise*, keep driving. That's the
`if/else` statement.

## Making a decision with `if/else`

An `if/else` runs one block when a condition is true and a different block when it's
false — never both:

```python
if condition:
    # runs when the condition is True
else:
    # runs when the condition is False
```

A non-robot example makes the shape clear:

```python
temperature = 85
if temperature > 80:
    print("It's hot outside!")
else:
    print("It's comfortable.")
```

## The bounce algorithm

The behavior in plain English:

```text
loop forever:
    read the sensor
    if the sensor sees the line:
        stop, then turn around
    else:
        keep driving forward
```

"Loop forever" is `while True:` — a loop whose condition is always true, so it runs
until you power the robot off. That's completely normal in robotics; real robots run
a loop like this the whole time they're on.

<KnowledgeCheck

    {text: 'Runs the loop only if a sensor is True'},

  explanation="The condition True is always true, so the loop repeats endlessly — the standard pattern for continuous robot control."

<TeacherNote title="while True is normal — and safe to stop">

Students sometimes think `while True` will "crash" the program — reassure them it's
the standard control-loop pattern, and the way to stop it is the robot's stop button
or power. Also note `drivetrain.stop()` before `turn(180)` just makes for a cleaner
pivot. On real hardware the 180° won't be exact — that's expected, and Lesson 2-4
turns it into a feature.

</TeacherNote>

## Combining conditions — and the function that asks

One sensor can miss the line if the robot hits it at an angle. Checking **both** is
safer — and that's where `or` comes in: it's true if *either* side is true, so
`get_left() > THRESHOLD or get_right() > THRESHOLD` means *at least one sensor sees
the line*.

The three logical operators: `and` (both must be true — you used it in Lesson 2-2),
`or` (at least one true), `not` (flips true/false).

That `or` question — *is either sensor on a line?* — is going to be asked by the
bounce, by next lesson's random bounce, and by the turns in Lesson 2-9. So it becomes
the next function in your LINE SENSOR section. It returns `True` or `False`: a
Boolean is a value like any other, and `return` can hand one back just as it handed
back a number in Lesson 1-11. The name starts with `is_` because it answers a yes/no
question — a convention you'll see in every function like it from here on.

## Activity · Build the bounce

### Step 1 · One sensor

Turn the comments in `test_bounce()` into code, with `get_left() > THRESHOLD` as the

### Step 2 · Either sensor

### Step 3 · Challenge — count the bounces

Add a `bounce_count` variable that goes up by one each bounce, and print it. You'll

def test_bounce():
    bounce_count = 0
    while True:
        if is_either_on_line():
            drivetrain.stop()
            bounce_count = bounce_count + 1
            print("Bounce", bounce_count)
