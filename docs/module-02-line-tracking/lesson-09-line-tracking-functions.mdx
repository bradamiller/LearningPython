Your sensor functions answer questions. Now the robot has to *act* on the answers. This
lesson builds a second toolkit — four driving functions that follow the line to an
intersection, park on it, and turn until a sensor finds the next line — on top of the
five from Lesson 2-8. These four functions drive every robot program for the rest of
the course, so the names you learn today are the ones you'll be using in Module 5.

## Two toolkits, one file

The driving functions need the sensor functions, so both live in the same file. The
sensor toolkit sits at the top exactly as you wrote it; the driving toolkit goes under
it, with its own settings:

```python
# --- sensor toolkit (Lesson 2-8), unchanged ---
reflectance = Reflectance.get_default_reflectance()
THRESHOLD = 0.5
# get_left, get_right, get_error, is_at_cross, is_either_on_line ...

# --- driving toolkit (this lesson) ---
drivetrain = DifferentialDrive.get_default_differential_drive()
BASE_EFFORT = 0.4
KP = 0.5
TURN_EFFORT = 0.25
```

`BASE_EFFORT` is 0.4 here where Lessons 2-5 to 2-7 used 0.3. Now that the steering is
tuned, the robot can go a little faster; if yours weaves at 0.4, drop it back. `KP` is
the gain from Lesson 2-5, in capitals now because it's a file-level setting like the
others.

## Four functions, and what ends each one

You're going to write four functions this lesson. For each one, this page tells you
what it does, what makes it *stop*, and gives you the outline — the design is the
lesson; the typing is yours. Each outline ends in `pass`, which means "nothing here
yet." It holds the place of a body you haven't written, so the whole file still runs
while you fill in one function at a time. Delete it when the real body goes in.

### Following the line, cleanly

The core function is the control loop you've been writing since Lesson 2-5, with
`is_at_cross()` as the exit condition. Read it as a sentence: *until you're at a cross,
steer toward the line; then stop.*

```python
def track_to_intersection():
    # until is_at_cross():
    #     read the error and scale it by KP
    #     steer with arcade(BASE_EFFORT, ...)
    # then stop the motors
    pass
```

All the sensor arithmetic is behind `get_error()` and `is_at_cross()`, and nothing in
this function reads the hardware directly. Watch the sign on the correction — it's the
same one you settled in Lesson 2-6.

### The wrinkle: the sensors get there first

When `track_to_intersection()` stops, both sensors are over the cross. But the sensors
are mounted in *front* of the wheels, and the robot pivots about its wheels. Turn now
and it swings around a point short of the intersection, and the sensors come down off
the new line.

So after every track, the robot drives forward a fixed distance to put the wheels over
the cross:

```python
def drive_past_intersection():
    # drive straight forward by exactly the sensor-to-axle distance
    pass
```

On an XRP that distance is **8.75 cm**: the wheels end up exactly where the sensors
were. That one call does two jobs. It parks the robot so a turn pivots on the
intersection, and it carries the sensors past the cross so the next
`track_to_intersection()` doesn't see the same tape and stop instantly.

It's a distance, not a `time.sleep()`, on purpose. Eight and three-quarter centimeters
is the same with a full battery or a flat one; half a second is not. You know the
drivetrain call that drives a distance — you've used it since Lesson 1-8.

<KnowledgeCheck

### Turning until a sensor says stop

How far is a 90° turn? You could time it — and it would be right until the battery
dropped. Instead, turn until the sensors *find the next line*. That takes three moves:

```python
def turn_clockwise():
    # 1. blind turn, about 60 degrees, to get BOTH sensors off this line
    # 2. keep spinning in place (no forward speed, only turn)
    # 3. wait until a sensor sees the cross street
    # 4. stop
    pass

def turn_counterclockwise():
    # the mirror image: same four moves, opposite direction
    pass
```

The **blind turn** of about 60° gets both sensors off the line the robot was
following — without it, `is_either_on_line()` is already `True` before the turn has
started and the loop ends instantly. Then the robot keeps spinning with `arcade()`
given no forward speed and only a turn value, and a **while loop waits** until a sensor
sees the cross street.

That waiting loop has nothing to *do* on each pass — the motors are already running
from the line above; the loop's only job is to keep checking the sensor. Python needs
*something* in a loop body, so you write `pass`: the same word as in the outlines, with
the same meaning, nothing to do here.

Why 60° and not 90°? Because the sensor is what finishes the turn. The blind part only
has to be big enough to clear the old line; the sensor does the rest, and does it the
same way whether the battery is full or flat. The two functions are mirror images:
swap the sign on both the blind turn and the spin, and the direction swaps.

<TeacherNote title="Sensors end turns; timers don't">

This is the lesson where the course's rule about timing becomes a habit: nothing
here stops because a clock ran out. `track_to_intersection()` stops on a cross,
`drive_past_intersection()` on a distance, and the turns on a sensor. Say the rule out
loud: *timing is never good for programs like this; sensors always work.*

The build-and-test-in-order sequence is now the student activity below, one function
per step, so expect the class to spread out: some pairs will be tuning a turn while
others are still watching the first follow. That's fine — nothing in step 3 depends on
a neighbor's step 2. The 8.75 cm is sensor-to-axle on an XRP; measure it if the
robot's mounting differs.

The cross line must be clearly perpendicular to the circle, or `is_at_cross()` fires
unreliably and the turn finds the new line at an angle.

</TeacherNote>

## Activity · Build the toolkit, one function at a time

Put the four outlines above into your file under the sensor toolkit, with the settings
block from the top of this lesson. The file runs as it is — every body is `pass` — and
you'll replace them one at a time, testing each before the next. For every step, the
robot starts on the circle-with-cross from Lesson 2-8.

### Step 1 · track_to_intersection()

Write the body and test it alone: put the robot on the circle, pointed along it, and
have the program call `track_to_intersection()` once after the button. It should
follow the line and stop with both sensors on the cross. If it drives straight through
the cross, check what your loop is waiting for; if it weaves, drop `BASE_EFFORT` back
to 0.3.

### Step 2 · drive_past_intersection()

Write the body — one line — and add a call after step 1's. The robot should end with
its *wheels* on the cross. Put a finger on the tape beside the robot and check: the
axle should sit over the line, and the sensors should be past it.

### Step 3 · turn_clockwise()

Write the four moves, with `TURN_EFFORT` at 0.25 to start. Test from where step 2
left you: call it once after the other two. Watch the two halves — the blind part
should carry both sensors clear of the circle, and then the spin should stop the
moment a sensor meets the cross street. Two things to tune if it doesn't:

- **The turn stops at once, barely moving.** The blind part was too small — a sensor
  was still on the old line when the loop started. Increase the 60°.
- **The robot spins past the cross street and keeps going.** The blind part was too
  big — it carried the sensors past the new line. Decrease it.

### Step 4 · turn_counterclockwise()

Mirror step 3: same four moves, both signs flipped. Test it the same way, from the
cross, and confirm it finds the cross street on the *other* side.

### Step 5 · Four lines to drive a course

With all four working, the part of the program that actually *drives* is short:

```python
from XRPLib.reflectance import Reflectance
from XRPLib.differential_drive import DifferentialDrive
from XRPLib.board import Board

# --- sensor toolkit (Lesson 2-8) ---
# --- driving toolkit (this lesson) ---

# --- the program ---
board = Board.get_default_board()

board.wait_for_button()

track_to_intersection()
drive_past_intersection()
turn_clockwise()
track_to_intersection()
print("Done!")
```

That bottom section is the point of the lesson. All the sensor reading and motor
control lives in the toolkits, so the program reads as a list of intentions. Compare it
to the wall of code this was back in Lesson 2-7.

**Challenge:** write `turn_around()` that calls `turn_clockwise()` twice. Does the
second call need a blind turn? (Yes — after the first, a sensor is on the new line.)

<Reveal title="Check your four functions" hint="write and test all four first">

```python
def track_to_intersection():
    while not is_at_cross():
        error = get_error()
        correction = error * KP
        drivetrain.arcade(BASE_EFFORT, -correction)
    drivetrain.stop()

def drive_past_intersection():
    drivetrain.straight(8.75, 0.5)

def turn_clockwise():
    drivetrain.turn(-60, TURN_EFFORT)          # 1. blind: both sensors off this line
    drivetrain.arcade(0, -TURN_EFFORT)         # 2. keep spinning...
    while not is_either_on_line():
        pass                                   # 3. ...until a sensor sees the cross street
    drivetrain.stop()                          # 4.

def turn_counterclockwise():
    drivetrain.turn(60, TURN_EFFORT)
    drivetrain.arcade(0, TURN_EFFORT)
    while not is_either_on_line():
        pass
    drivetrain.stop()
```

If yours differs and still works, keep yours. If it differs and doesn't, the first
things to compare are the sign on the correction in the follow loop and the two signs
in each turn.

<TeacherNote title="Solution (teacher copy)">

The complete file, as `lesson-09-line-tracking-functions.py` in the Module 2
solutions. Students see only the outlines above and the four bodies behind the
"Check your four functions" reveal, which is closed by default and not printed.

```python
from XRPLib.reflectance import Reflectance
from XRPLib.differential_drive import DifferentialDrive
from XRPLib.board import Board

# --- sensor toolkit (Lesson 2-8), unchanged ---
reflectance = Reflectance.get_default_reflectance()
THRESHOLD = 0.5

def get_left():
    return reflectance.get_left()

def get_right():
    return reflectance.get_right()

def get_error():
    return get_left() - get_right()

def is_at_cross():
    return get_left() > THRESHOLD and get_right() > THRESHOLD

def is_either_on_line():
    return get_left() > THRESHOLD or get_right() > THRESHOLD

# --- driving toolkit (this lesson) ---
drivetrain = DifferentialDrive.get_default_differential_drive()
BASE_EFFORT = 0.4
KP = 0.5
TURN_EFFORT = 0.25

def track_to_intersection():
    while not is_at_cross():
        error = get_error()
        correction = error * KP
        drivetrain.arcade(BASE_EFFORT, -correction)
    drivetrain.stop()

def drive_past_intersection():
    drivetrain.straight(8.75, 0.5)

def turn_clockwise():
    drivetrain.turn(-60, TURN_EFFORT)
    drivetrain.arcade(0, -TURN_EFFORT)
    while not is_either_on_line():
        pass
    drivetrain.stop()

def turn_counterclockwise():
    drivetrain.turn(60, TURN_EFFORT)
    drivetrain.arcade(0, TURN_EFFORT)
    while not is_either_on_line():
        pass
    drivetrain.stop()

def turn_around():
    turn_clockwise()
    turn_clockwise()

# --- the program ---
board = Board.get_default_board()

board.wait_for_button()

track_to_intersection()
drive_past_intersection()
turn_clockwise()
track_to_intersection()
print("Done!")
```

## Wrap-up

- What ends each of the four driving functions? (A cross, a distance, a line, a line.)
- Why `drive_past_intersection()` after every track? (The sensors reach the cross before the wheels do.)
- Why the blind 60° at the start of a turn? (To get the sensors off the old line so the loop can end on the new one.)

<OptionalExtension title="The LineTrack class: one object holding another">

If you built the `LineSensor` class in Lesson 2-8, the driving toolkit can become a
class too — and this one shows something new: a class that **contains** another. A car
*has an* engine. `LineTrack` **has a** `LineSensor` for sensing and **has a** drivetrain
for driving, and coordinates them. One object holding another is called
**composition**.

```python
class LineTrack:
    def __init__(self):
        self.sensor = LineSensor()                                     # has-a LineSensor
        self.drivetrain = DifferentialDrive.get_default_differential_drive()
        self.base_effort = 0.4
        self.kp = 0.5
        self.turn_effort = 0.25

    def track_to_intersection(self):
        # your function, with self. in front of the sensor, the drivetrain and the settings
        pass

    def drive_past_intersection(self):
        pass

    def turn_clockwise(self):
        pass

    def turn_counterclockwise(self):
        pass
```

`__init__` is the new idea, so it's given: the object builds its own `LineSensor` and
keeps the three settings as attributes. The four methods are *your* four functions —
move each body in, then put `self.` in front of every sensor call, every drivetrain
call and every setting. Where a function said `get_error()`, the method says
`self.sensor.get_error()`; where it said `KP`, the method says `self.kp`. That
translation, done four times, is the whole extension.

<Reveal title="Check your LineTrack" hint="translate all four methods first">

```python
    def track_to_intersection(self):
        while not self.sensor.is_at_cross():
            error = self.sensor.get_error()
            correction = error * self.kp
            self.drivetrain.arcade(self.base_effort, -correction)
        self.drivetrain.stop()

    def drive_past_intersection(self):
        self.drivetrain.straight(8.75, 0.5)

    def turn_clockwise(self):
        self.drivetrain.turn(-60, self.turn_effort)
        self.drivetrain.arcade(0, -self.turn_effort)
        while not self.sensor.is_either_on_line():
            pass
        self.drivetrain.stop()

    def turn_counterclockwise(self):
        self.drivetrain.turn(60, self.turn_effort)
        self.drivetrain.arcade(0, self.turn_effort)
        while not self.sensor.is_either_on_line():
            pass
        self.drivetrain.stop()
```

When you create a `LineTrack`, it builds its *own* `LineSensor` inside `__init__` —
you don't make one separately — and asks it questions with `self.sensor.get_error()`
and `self.sensor.is_at_cross()`. The functions are the same four, with the same names;
the settings moved from file-level capitals into `self.` attributes. The file is
`lesson-09-linetrack-class-addon.py` in the Module 2 solutions.

**From here on, use your class.** You now have the whole Module 2 toolkit as objects,
and the point of building it that way is lost if it sits in a drawer. The lessons ahead
are written with the function names, because that is what every student has — and
yours are the same names with `tracker.` in front. When Lesson 3-1 says
`track_to_intersection()`, you write `tracker.track_to_intersection()`. Nothing else
changes, and the lessons that offer a class extension will meet you with the next
object to build on this one.
