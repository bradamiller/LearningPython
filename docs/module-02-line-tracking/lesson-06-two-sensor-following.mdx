## The difference *is* the error

With two sensors straddling the line, you don't need a setpoint anymore. Just
subtract one reading from the other:

> error = left − right

When both sensors read the same, the difference is zero and the robot drives
straight. When one drifts onto the line, the difference tells you exactly how much
and which way:

Work out the direction from the readings rather than memorising the table. A high
reading means *that sensor* is over the line. If the **left** sensor is the one on
the line, the line is off to the robot's left — which means the **robot** has
wandered to the **right** of it. The sensor that finds the line points back toward
where the robot should be.

| Position | left | right | error = L − R | Which way to steer |
|---|---|---|---|---|
| Centered | 0.5 | 0.5 | `0.0` | drive straight |
| Drifted right | 0.8 | 0.2 | `+0.6` | steer left, back toward the line |
| Drifted left | 0.2 | 0.8 | `−0.6` | steer right, back toward the line |
| Both on white | 0.1 | 0.1 | `0.0` | straight (lost line) |
| Both on black | 0.9 | 0.9 | `0.0` | straight (an intersection!) |

## The control loop (and that negative sign)

<Todo kind="blocked">
Check on a real robot before teaching this. The minus sign in the follower below may be
backwards for the current XRPLib. Its arcade documents a positive turn as skewing the
robot LEFT (left wheel gets straight minus turn, right wheel straight plus turn), and its
own line_track example, with error = left minus right, sets the left wheel to base minus
error times KP and the right to base plus error times KP. That is arcade with a plus
correction, not a minus. With a positive error meaning the robot drifted right, a minus
sign would steer it further right, away from the line, unless the reflectance board's
left and right are swapped relative to the robot. Test: put the robot just right of a
line so the left sensor reads high and watch which way the follower turns. If it turns
away, drop the minus here and in every follower after it (2-7 through the capstones),
rewrite this section's explanation and knowledge check, fix 2-5's arcade example, and
regenerate the templates. Raised 2026-10-25.
</Todo>

Here is the payoff for putting the error behind a function last lesson. The follower
in `test_follow()` reads `get_error()`, scales it, steers. Switching to two sensors
means **rewriting `get_error()`** — and the loop that calls it barely notices. Two
changes to `robot.py`, both in place:

**In the LINE SENSOR section**, replace the body of `get_error()` so it returns
`get_left() - get_right()`, and delete `SETPOINT` — two sensors don't need one. The
comment outline for the new body:

```python
def get_error():
    # return the left reading minus the right reading
    pass
```

**In `test_follow()`**, the correction goes into `arcade()` with a **minus sign** in
front of it. That's the only change to the loop.

Why the minus? A **positive** error means the robot drifted **right** of the line,
so it must steer **left** to get back — and in `arcade()` a *negative* turn steers
left. Negating the correction lines the math up with reality.

## Activity · Feel the sign, then follow the circle

### Step 1 · Explore the error by hand

Rewrite `get_error()` first, and test it before anything drives: add
`" Error:", round(get_error(), 2)` to the print in `test_sensors()`, set the run line
to `test_sensors()`, and slide the robot across the line by hand. Watch the printed
error go positive, then zero, then negative, and say out loud which way the robot has
drifted each time. Check yourself against the table above.

### Step 2 · Run the follower

Put the minus sign into `test_follow()` and set the run line back to it. Put the
robot with the line running *between* the sensors, press the button, and watch it
track the circle. If it steers *away* from the line as soon as it drifts, you have the
sign backwards — go back to step 1 and work out which way a positive error should
steer. Notice what you did **not** have to change: the loop is the same three lines
it was with one sensor. The function changed; its caller didn't.

### Step 3 · Compare with one sensor

Temporarily put the one-sensor `get_error()` back (and the `SETPOINT`), without the
minus sign, and run `test_follow()` again right after. Which is smoother? Which
handles the curves and higher speeds better? Then restore the two-sensor version —
that's the one the rest of the course uses.

### Step 4 · Challenge — push the speed

Turn `BASE_EFFORT` up to 0.4–0.5 for both versions and watch what happens to each.
Which one degrades first, and what does that tell you about how much information one
sensor gives the robot?

def get_error():

```python
def test_follow():
    while True:
        error = get_error()
        correction = error * KP
        drivetrain.arcade(BASE_EFFORT, -correction)   # note the minus sign

```

## Wrap-up

- What's the two-sensor error formula, and why no setpoint? (`left − right`; equal readings already mean zero.)
- Positive error means the robot drifted which way? (Right — the left sensor found the line, so the line is left of the robot.)
- Why the negative sign on the correction? (A positive error needs a left steer, which is a negative turn in `arcade()`.)
