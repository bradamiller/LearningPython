Bouncing kept the robot *inside* the circle, but it never actually **followed** the
line. This lesson is the real thing: the robot smoothly tracks the edge of the line
by making tiny, constant steering adjustments — the same way you'd steer a car around
a gentle curve. It's your first **control loop**, and one of the most important ideas
in the whole course.

<Objectives>

By the end of this lesson you will be able to:

- Explain a **setpoint** and why the line's edge (~0.5) is ours
- Compute **error** as `setpoint − sensor_reading`, and read its sign
- Turn error into a steering **correction** with a gain `Kp`
- Write `get_error()` and the control loop from the two formulas and `arcade()`, in your `robot.py`
- Tune `Kp` by watching the robot and adjusting

## Steer while you drive: `arcade()`

Bounce driving *reacted* after hitting the line. Following means *constantly*
adjusting so you never leave it — like nudging the wheel around a curve instead of
stopping to turn.

For that you need to steer without stopping. `arcade(speed, turn)` does exactly this
— it sets a forward speed and a steering amount in one non-blocking call:

```python
drivetrain.arcade(speed, turn)
# is the same as:
drivetrain.set_effort(speed + turn, speed - turn)
```

So `arcade(0.3, 0.15)` speeds up the left wheel and slows the right — the robot
curves. A positive `turn` steers one way, negative the other, and zero drives
straight.

## Setpoint and error

The **setpoint** is the reading we want the sensor to hold. Following the *edge* of
the line, that's about `0.5` — halfway between white and black. **Error** is how far
off we are:

> error = setpoint − sensor_reading

The sign tells us which way we've drifted; the size tells us how far:

| Where the robot is | reading | error = 0.5 − reading | Meaning |
|---|---|---|---|
| On the edge (perfect) | 0.5 | `0.0` | no correction |
| Drifted onto white | 0.2 | `+0.3` | steer toward the line |
| Drifted onto black | 0.8 | `−0.3` | steer back off the line |
| Far onto white | 0.1 | `+0.4` | steer hard toward the line |

## From error to steering: the gain `Kp`

We don't feed raw error to the motors — we scale it by a **proportional gain**,
`Kp`, to set how strongly the robot reacts:

> correction = error × Kp

<Callout kind="note" title="Why this one variable starts with a capital">

Lesson 1-9 gave you the Python rule: `lowercase_with_underscores` for your variables,
`Capitalized` for classes. `Kp` breaks it, on purpose.

This value isn't really ours to name. Every control-systems textbook, datasheet and
engineering paper writes the proportional gain as **K<sub>p</sub>** — a capital K for
"gain", a small p for "proportional" — and a student who searches for PID tuning will
meet it that way everywhere. Writing `kp` in the code would be more Pythonic and would
quietly cut the connection to every other thing they will ever read about control.

So the rule with the exception attached: **name your own variables the Python way, and
when a name comes from the engineering world rather than from you, keep the engineering
spelling.** `Kp` is the only name in this course that gets the exception. In
`robot.py` it's a file-level setting, and settings are written in capitals like
`THRESHOLD` — so there it's `KP`; in these pages, when we talk about it, it's `Kp`.

</Callout>

With `Kp = 0.5`, an error of `+0.3` gives a correction of `+0.15`. Then we steer with
that correction:

```python
drivetrain.arcade(BASE_EFFORT, correction)
```

Bigger error → bigger correction → sharper steer. When the robot is right on the edge
(error 0), the correction is 0 and it drives straight. Notice there's **no
`if/else`** — the math handles left vs. right on its own, through the sign.

## This lesson's additions to `robot.py`

Every pass of the control loop: read the sensor, compute error, compute correction,
steer. Hundreds of times a second. Two of those steps become part of your file.

**In the LINE SENSOR section**, the error becomes a function. It's a sensor question —
*how far off the edge am I?* — so it lives with the sensor functions, and the setpoint
is its setting. Add both under `THRESHOLD`:

```python
SETPOINT = 0.5           # the reading at the edge of the line

def get_error():
    # return SETPOINT minus the left reading
    pass
```

**A new section** starts here, for everything that drives on the line. Paste it above
`RUN`. The test is the exercise: the loop's outline is inside it.

```python
# ===== LINE TRACKING =====
# Drives the robot along the line using the LINE SENSOR functions above.
# Starts with the proportional follower: read the error, scale it by KP,
# steer with arcade(). Grows over the module into following to a cross,
# parking on it, and turning to the next line.
BASE_EFFORT = 0.3        # forward speed while following
KP = 0.5                 # proportional gain -- tune this!

def test_follow():
    # loop forever:
    #     error = get_error()
    #     correction = error times KP
    #     steer: arcade() with BASE_EFFORT and the correction
    #     time.sleep(0.01), so the loop doesn't flood the processor
    pass
```

Three lines in the loop and a pause — and no `if/else` anywhere. The sign of the error
does the deciding. You have every piece: `get_error()` is one subtraction, and
`arcade()` was the first thing in this lesson.

<TeacherNote title="This is a big conceptual leap">

Going from "do this, then that" to "constantly read and adjust" is the hardest shift
in the module — lean on the car-steering analogy hard. Two things to hammer: the
setpoint is the *edge* (~0.5), **not** white (0.0) — the robot rides the boundary;
and proportional control needs **no if/else**, because the sign of the error already
encodes direction. The `time.sleep(0.01)` just keeps the loop from flooding the
processor. Encourage students to use their Lesson 2-1 edge value rather than assuming
exactly 0.5. `test_sweep()` (in the tuning section) is the moment to make the sign
flip physical: motors off, robot in hand, the printed error crossing zero as the
sensor crosses the edge.

</TeacherNote>

## Activity · Follow the line, then tune it

### Step 1 · Write the loop and run it

Write `get_error()` and turn the comments in `test_follow()` into code; set the run
line to `test_follow()`. Put the robot so the left sensor sits on the edge of the
line, press the button, and watch. It should hold the edge, nudging left and
right as the line curves. If it drives straight off, check the sign of your error
calculation against the table above; if it spins in place, check the order of the
two arguments to `arcade()`.

### Step 2 · Tune Kp

`Kp` is yours to tune by watching the robot. Run the test three times — with `KP` at
0.2, at 0.5 and at 1.0 — and write down, for each, what the robot does on a curve.
Then decide: which of the three is too high, which too low, and what does each one
*look* like?

<Reveal title="What too high and too low look like" hint="try all three values first">

- **Too high** → the robot over-corrects and **oscillates**, weaving rapidly.
- **Too low** → it reacts sluggishly and **drifts off** the line.
- **Just right** → smooth tracking with small corrections.

Where "just right" falls depends on your surface, your tape and your speed — there
is no single correct number, only the relationship.

</Reveal>

### Watch the numbers while you tune

Tuning by eye tells you *that* something is wrong. Printing tells you *what*. The
problem is that your control loop runs hundreds of times a second, so printing every
pass produces a waterfall nobody can read. Print every **50th** pass instead.

"Every 50th" needs one arithmetic operator you haven't used yet. `%` is the
**remainder** operator: `a % b` is what's left over after dividing `a` by `b` as whole
numbers. (It has nothing to do with percent — the symbol is the same, the meaning isn't.)

```python
7 % 3        # 1   (3 goes into 7 twice, remainder 1)
10 % 5       # 0   (5 goes into 10 exactly)
50 % 50      # 0
51 % 50      # 1
100 % 50     # 0
149 % 50     # 49
150 % 50     # 0
```

Look at the last five. The remainder is `0` exactly when the number is a multiple of
50 — so `i % 50 == 0` is a test that is true on pass 0, pass 50, pass 100, and false
on every pass in between. Put that in an `if` around the `print`, and you get one line
out of every fifty.

<KnowledgeCheck
  question="What is 120 % 50, and would a print inside `if i % 50 == 0:` happen on pass 120?"
  options={[
    {text: '2.4, and yes'},
    {text: '20, and no — the remainder is not zero, so 120 is not a multiple of 50', correct: true},
    {text: '0, and yes'},
    {text: '70, and no'},
  ]}
  explanation="50 goes into 120 twice (100) with 20 left over, so 120 % 50 is 20. Only passes whose remainder is 0 — multiples of 50 — print."
/>

Here's the technique with the real sensor and **no motors** — one more test to paste
above `RUN`. It reads the error 500 times over about ten seconds and prints one line
in fifty:

```python
def test_sweep():
    # no motors: sweep the robot across the line BY HAND while this
    # runs, and watch error and correction change sign at the edge
    for i in range(500):
        error = get_error()
        correction = error * KP
        if i % 50 == 0:
            print(f"i={i}  error={error:.2f}  correction={correction:.2f}")
        time.sleep(0.02)
```

Set the run line to `test_sweep()`, press the button, and slide the robot slowly
sideways so the left sensor starts on white, crosses the edge, and ends on black.
Five hundred passes, ten lines of output, something like:

```text
i=0  error=0.30  correction=0.15
i=50  error=0.28  correction=0.14
i=100  error=0.21  correction=0.11
i=150  error=0.09  correction=0.04
i=200  error=0.01  correction=0.00
i=250  error=-0.12  correction=-0.06
i=300  error=-0.24  correction=-0.12
i=350  error=-0.31  correction=-0.16
i=400  error=-0.33  correction=-0.17
i=450  error=-0.33  correction=-0.17
```

Your numbers will differ; the *shape* won't. The output is worth reading as more than
a formatting demo. As the sensor reaches the edge the error falls to zero and then goes
**negative**, and the correction follows it. That sign flip is the steering changing
direction, with no `if/else` anywhere — exactly the claim made earlier in the lesson,
now in numbers, from your sensor. (If the error never changes sign, the sensor didn't
cross the edge — sweep farther — or `SETPOINT` isn't your edge value from Lesson 2-1.)

### Step 3 · Put it in your own loop

`test_sweep()` had a `for` loop, so `i` was there to count with. Your tracking loop is
a `while True:`, which has no `i`, so make your own counter — the same
`count = count + 1` pattern from Lesson 1-9. Three additions to `test_follow()`: a counter set to zero *before* the loop; a line at the end of the
loop body that adds one to it; and an `if` that prints the error and correction only
when the counter is a multiple of 50. Run it and tune `KP` again, this time reading
the numbers: a too-high gain shows up as a correction that flips sign on nearly every
printed line.

<Reveal title="Check your function and test" hint="run yours on the robot first">

```python
def get_error():
    return SETPOINT - get_left()
```

Step 1:

```python
def test_follow():

```

Step 3 adds the counter:

```python
def test_follow():
    loop_count = 0
    while True:
        error = get_error()
        correction = error * KP
        drivetrain.arcade(BASE_EFFORT, correction)

        loop_count = loop_count + 1
        if loop_count % 50 == 0:
            print(f"error={error:.2f} correction={correction:.2f}")

        time.sleep(0.01)
```

</Reveal>

<TeacherNote title="Solution (teacher copy)">

The additions to `robot.py` this lesson, in their step 3 form; the rest of the file
is as the Lesson 2-4 teacher copy left it. The file is
`lesson-05-proportional-control.py` in the Module 2 solutions. What students have to
produce themselves is the one-line `get_error()`, the three-line loop body from the
two formulas, the three tuning observations, and the counter. Note `get_error()` is
*one-sensor* here — next lesson rewrites it for two sensors, and the loop in
`test_follow()` barely changes. That is the point of putting the error behind a
function today.

```python
# in the LINE SENSOR section, under THRESHOLD:
SETPOINT = 0.5

def get_error():
    return SETPOINT - get_left()

# above RUN:
# ===== LINE TRACKING =====
# Drives the robot along the line using the LINE SENSOR functions above.
# Starts with the proportional follower: read the error, scale it by KP,
# steer with arcade(). Grows over the module into following to a cross,
# parking on it, and turning to the next line.
BASE_EFFORT = 0.3
KP = 0.5

def test_follow():
    loop_count = 0
    while True:
        error = get_error()
        correction = error * KP
        drivetrain.arcade(BASE_EFFORT, correction)

        loop_count = loop_count + 1
        if loop_count % 50 == 0:
            print(f"error={error:.2f} correction={correction:.2f}")

        time.sleep(0.01)

def test_sweep():
    for i in range(500):
        error = get_error()
        correction = error * KP
        if i % 50 == 0:
            print(f"i={i}  error={error:.2f}  correction={correction:.2f}")
        time.sleep(0.02)

# ===== RUN =====
board.wait_for_button()
test_follow()
```

</TeacherNote>

<TeacherNote title="Tuning is the fun part">

There's no single "right" `Kp` — it depends on the surface, the tape, and the base
speed. The goal isn't a magic number but understanding the *relationship*: higher Kp
= stronger reaction = risk of oscillation. Let students run the tuning table from the
worksheet and feel it. Start everyone at `BASE_EFFORT = 0.3` or lower so the robot is
observable; speed can come once tracking is stable.

</TeacherNote>
