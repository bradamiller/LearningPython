Your line follower works — but the sensor reading, the threshold test and the control
math are all tangled together in one loop, and the next three lessons need to ask the
sensors more questions, not fewer. In Module 1 you tidied repeated driving code into
`polygon()`. This lesson does the same for the sensors: five small, well-named
functions, each written and **tested before the next one**, so that when the robot
starts driving on them you already know every one is right. Nothing here is new syntax.
The one new idea is functions that **share** a sensor and a threshold without being
handed them every call.

## The goal: code that reads like English

Here is where this is going. Next lesson the robot follows the line *until it reaches a
crossing line*, and with the sensor logic in functions, that loop reads as a sentence:

```python
while not is_at_cross():
    correction = get_error() * Kp
    drivetrain.arcade(base_effort, -correction)
```

`is_at_cross()` is far clearer than `left > 0.5 and right > 0.5` scattered through the
program, and `get_error()` says what the subtraction *means*. Every driving function in
Lessons 2-8 and 2-9 is built on exactly these five — so this is the lesson to get them
right.

## One file, for the rest of the course

Until now every lesson started a new program. From here on you have **one file**, and
each lesson adds to it: the sensor functions today, the driving functions over the next
two lessons, grid driving in Module 3, and so on to the end. Create it now — call it
`robot.py` — and paste in this start:

```python
from XRPLib.reflectance import Reflectance
from XRPLib.differential_drive import DifferentialDrive
from XRPLib.board import Board
import time

reflectance = Reflectance.get_default_reflectance()
drivetrain = DifferentialDrive.get_default_differential_drive()
board = Board.get_default_board()


# ===== RUN =====
board.wait_for_button()
# call ONE test function here
```

Two rules keep it working all year. **New code goes above the `RUN` block, never
below it.** Python runs a file top to bottom, so the run block has to be the last
thing, and everything it calls has to be defined above it. Each lesson gives you a
**skeleton** to paste in there: a banner comment naming the section, the settings it
needs, the outlines of the functions you're going to write, and a **test function**
that exercises them. Then the one line under `RUN` calls whichever test you're working
on. **One test at a time** — change the call, don't stack them.

Every banner is followed by a short comment saying what the section does and how it
leans on the sections before it. By Module 5 those comments are the table of contents
of your robot — read them before you read the code.

## Shared, not passed: global variables

The functions need the same two things: the reflectance sensor, and the threshold. You
could pass both into every function as parameters. Instead, create them **once, at the
top of the file**, outside any function:

```python
from XRPLib.reflectance import Reflectance

reflectance = Reflectance.get_default_reflectance()
THRESHOLD = 0.5
```

A variable created outside every function is a **global variable**: every function
below it in the file can read it without being handed it. You've been doing this since
Module 1 — `drivetrain` is a global that `polygon()` used without a parameter.

`THRESHOLD` is in capitals by convention. That spelling says *this is a setting, not a
value that changes as the program runs*. Python doesn't enforce it; readers rely on it.

## The five functions

Here is this lesson's skeleton. Copy it and paste it into `robot.py` above the `RUN`
block. Each function is an outline — the `def` line, a comment saying what it returns,
and `pass`, which means "nothing here yet" and holds the place of a body so the file
still runs while you fill them in one at a time.

```python
# ===== LINE SENSOR (Lesson 2-7) =====
# Reads the two reflectance sensors and answers questions
# about them: how far off the line we are (get_error) and
# whether we are on a cross or on a line at all. Nothing in
# here drives. Everything that drives, from the next lesson
# on, asks these functions instead of the hardware.
THRESHOLD = 0.5          # use YOUR edge value from Lesson 2-1

def get_left():
    # return the left reflectance reading
    pass

def get_right():
    # return the right reflectance reading
    pass

def get_error():
    # return left minus right -- call your two functions
    # above, not the hardware
    pass

def is_at_cross():
    # return True when BOTH readings are above THRESHOLD
    pass

def is_either_on_line():
    # return True when AT LEAST ONE reading is above THRESHOLD
    pass

def test_sensors():
    # prints the readings twice a second while you slide the
    # robot by hand
    while True:
        print("Left:", round(get_left(), 2),
              " Right:", round(get_right(), 2))
        time.sleep(0.5)
```

(`reflectance` and `THRESHOLD` sit at the top of the file and the top of the section,
so the functions can use them — that was the previous section's point.)

Two things to notice about the design. First, `get_error()` should not read the sensor
itself — it calls `get_left()` and `get_right()`. One place knows how to read the
hardware; everything else goes through it. Second, the last two start with `is_`
because they answer a yes/no question and return `True` or `False` — a Boolean is a
value like any other, and `return` can hand one back just as it handed back a number
in Lesson 1-11.

What are they asking? During normal following, one sensor is darker than the other.
Where a second taped line **crosses** the one you're following, *both* sensors sit on
black at once — that's what `is_at_cross()` detects, and `and` is the right word
because both must be true (`or`, which you met in Lesson 2-3, would fire during
normal following). `is_either_on_line()` is the looser question, *at least one* dark:
that's the test a turn will need in Lesson 2-9, to know when the robot has swung
around far enough to find the next line.

## When `global` is needed — and when it isn't

Every function above *reads* `THRESHOLD`, and none of them needed anything special.
Reading a global is free. **Assigning** to one is different. Try a function that
changes the threshold:

```python
def set_threshold(new_value):
    THRESHOLD = new_value        # looks right; does nothing useful
```

Call `set_threshold(0.3)` and then print `THRESHOLD` — still `0.5`. Inside a
function, assigning to a name creates a **new local variable** with that name, which
vanishes when the function returns. The global was never touched. To tell Python you
mean the one at the top of the file:

```python
def set_threshold(new_value):
    global THRESHOLD
    THRESHOLD = new_value
```

That's the whole rule: **read a global freely; to assign to it, declare `global` first.**
You'll need this rarely — settings in capitals aren't supposed to change — but when
you do, the silent failure without it is the kind of bug that costs an afternoon.

## Activity · Write one, test one

Under `RUN`, make the call `test_sensors()`. It prints whatever you ask it to, twice a
second, while you slide the robot over the tape by hand — so each function gets tested
the moment it exists, with nothing else in the way. Before you start, add a straight
strip of tape **across** your circle so that it crosses the line in two places —
that's the cross the last two functions are about, and it stays on the floor for the
rest of the module.

### Step 1 · get_left() and get_right()

Write both bodies and run. Slide the robot so one sensor, then the other, crosses the
tape. Each number should jump from your Lesson 2-1 floor reading to your tape reading
— and the *right* number should move when the *right* sensor is on tape. If they're
swapped, you've found it now instead of in a driving program.

### Step 2 · get_error()

Write it so it calls the two functions from step 1. Add `" Error:", round(get_error(), 2)`
to the print line in `test_sensors()`. Centered on the line the error is near zero;
drifted to one side it goes positive, to the other negative. Check that the sign
matches Lesson 2-6.

### Step 3 · is_at_cross()

Write it and add `" Cross:", is_at_cross()` to the print. Slide the robot along the
circle: `False` all the way around, then `True` only when both sensors sit on the
crossing strip. If it's `True` on the plain circle, the threshold is too low; if it
never goes `True` on the cross, too high.

### Step 4 · is_either_on_line()

Write it and add `" On line:", is_either_on_line()`. Now check four positions and
write down what you see: centered on the line (`False`, `True`), off to one side
(`False`, `True`), completely off the line (`False`, `False`), and on the cross
(`True`, `True`).

### Step 5 · set_threshold()

Add `set_threshold()` to the section *without* `global`, call `set_threshold(0.9)` as
the first line of `test_sensors()`, and slide over the cross: `is_at_cross()` still
fires, because the real `THRESHOLD` never changed. Add the `global` line and run again
— now nothing reads as tape. Take the call out again when you're done; the function
can stay. Next lesson starts from this file exactly as you leave it.

<OptionalExtension title="The LineSensor class">

The five functions work, but their parts are spread out: two globals at the top, five
functions below, and every one of them depends on both globals. A **class** keeps the
data and the functions that use it together as one unit. This is the first class in
the course, and it is small on purpose.

**What a class is**

A class is a blueprint that groups related **data** and **actions** together.

<Figure
  src="/img/lesson-m2-07/class-and-objects.svg"
  alt="An architect's blueprint of a house labeled 'class House:' with four arrows leading down to four built houses. All four have the same shape, roof, door and windows, but one is red, one is yellow with a chimney, one is blue with a dark door, and one is green with flower boxes. Under each house is the code that built it: House('red'), House('yellow'), House('blue'), House('green')."
  caption="One plan, many houses. The class is the drawing; each object is a house built from it. They all follow the plan, and each one can still be a little different."
/>

- **The class is just a definition.** Writing `class House:` is like drawing the plan.
  Nothing gets built. You can't live in a blueprint, and you can't call `get_error()`
  on the `LineSensor` class itself.
- **An object is one thing built from it.** `House("red")` builds one house;
  `LineSensor()` builds one sensor object. The parentheses are what build it. The word
  for a built object is an **instance**.
- **You can build as many as you want from one plan,** and each can be a little
  different, depending on what you pass to the **constructor** when you build it.

You've used classes all along — `DifferentialDrive`, `Reflectance` and `Board` are
classes. Now you'll write one.

**`__init__` and `self`**

```python
class LineSensor:
    def __init__(self):
        self.reflectance = Reflectance.get_default_reflectance()
        self.threshold = 0.5
```

- `class LineSensor:` defines a new type (capitalized by convention).
- `def __init__(self):` is the **constructor** — Python runs it automatically when you
  write `LineSensor()`.
- `self` is the object itself. `self.threshold = 0.5` means "*this* object's threshold
  is 0.5", and it sticks around as long as the object does.

```python
sensor = LineSensor()     # __init__ runs now
print(sensor.threshold)   # 0.5
```

**Methods**

A **method** is a function that lives inside a class and takes `self` as its first
parameter — that's how it reaches the object's own data.

Here are two of your functions next to the same two as methods:

</div>

Compare them line by line. Only four things change, and they're the same four every
time:

- The functions move inside `class LineSensor:`, and each gets `self` as its first
  parameter.
- `reflectance` and `THRESHOLD` stop being globals. They become the object's own data,
  set up once in `__init__` as `self.reflectance` and `self.threshold`.
- Inside the methods, those values and calls to sibling methods get `self.` in front.
- Calls from outside go through the object: `get_error()` becomes `sensor.get_error()`.
  You never pass `self` yourself; Python supplies it.

So what does the class buy? `LineSensor()` brings everything with it — copy the class
into a new program and nothing is forgotten. And because each object has its own
`self.threshold`, two sensor objects can have two different thresholds, which one
global `THRESHOLD` can't do — and no `global` keyword anywhere, because a method
assigns to `self.threshold` like any attribute.

**Build it.** This is the class-track skeleton for the section. Paste it in place of
the LINE SENSOR functions (keep `THRESHOLD` out — it's `self.threshold` now), and
translate your five bodies into the five methods. The object is created right under
its class, and `test_sensors()` changes to call `sensor.get_left()` and so on.
