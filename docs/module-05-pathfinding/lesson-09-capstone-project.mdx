## The mission

Your robot is an autonomous delivery vehicle. It must visit four or more grid destinations
in sequence, and for each leg: plan a path, drive it while watching for obstacles, and
reroute whenever the rangefinder finds one. Everything you need already exists — the
planner (Lessons 5-4 and 5-5) and its paper tests (5-6), detection (5-7), the
drive-until-you-arrive loop and carrying knowledge between runs (5-8). Today you
connect them.

You'll demonstrate with **two runs**: Run 1 starts with an empty blocked list, discovers
obstacles the hard way, and prints what it found; Run 2 starts with that list typed in, so
it plans around them and reroutes less. The drop in step count between runs *is* the
learning.

## Program structure

The whole program has a clear skeleton:

```
1. Hand KNOWN_OBSTACLES to add_blocked() -- empty on Run 1, last run's list on Run 2
2. Define destinations
3. Print the plan for leg 1, wait for the button
4. For each destination:
     navigate_with_detection() -- plan, follow, re-plan until arrived (Lesson 5-8)
     add its steps and reroutes to the totals
5. Print the blocked list -- this is what you type in for the next run
6. Print results (steps, reroutes)
```

The **blocked list is the thread** tying it together: step 1 fills it, the planner
reads it on every call, detection adds to it, and step 5 hands it to the next run. And
every one of those goes through `add_blocked()` — the planner never knows which.

## The destination loop

Lesson 5-8's `navigate_with_detection()` already handles one trip — plan, follow,
re-plan until arrival — and returns where the robot ended up. The capstone's new code
is the loop that calls it once per destination, feeding each trip's end position and
heading into the next:

```python
position = (0, 0)
heading = 0                      # 0 = N, 1 = E, 2 = S, 3 = W, as in Module 4
destinations = [(1, 3), (3, 3), (3, 0), (0, 0)]

print("Planned path for leg 1:", compute_bfs_path(position, destinations[0]))
board.wait_for_button()

total_steps = 0
total_reroutes = 0

for i in range(len(destinations)):
    dest = destinations[i]
    print("--- Leg", i + 1, ": Heading to", dest, "---")

    position, heading, steps, reroutes = navigate_with_detection(
        position, heading, dest, rangefinder, OBSTACLE_CM
    )

    total_steps = total_steps + steps
    total_reroutes = total_reroutes + reroutes
    print("  Arrived at", dest)

print("=== FINAL REPORT ===")
print("Total steps:", total_steps)
print("Total reroutes:", total_reroutes)
print("Obstacles discovered:", BLOCKED)
```

Two details are easy to get wrong. `position` and `heading` must be **assigned from the
return value** — forget the `position, heading, ... =` part and the second leg plans from
(0, 0) while the robot sits somewhere else. And only the *first* leg is printed before
the button, because later legs are planned from wherever the robot actually ends up,
including around obstacles it hasn't found yet.

## Activity · Simulate, then drive

Get the whole thing working with a **simulated** rangefinder before the robot — verify
paths compute, obstacles register, the blocked list grows across all four legs, and the
list printed at the end is the one you'd want to start the next run with. Then swap in
the real sensor.

```python
ACTUAL_OBSTACLES = [(1, 0), (2, 2), (1, 3)]
def simulate_rangefinder(next_pos):
    return 8.0 if next_pos in ACTUAL_OBSTACLES else 50.0
```

Watch for the classic integration bugs: the blocked list getting reset between
destinations (one `BLOCKED` for the whole run — never call `clear_blocked()` between
legs), `position` and `heading` not assigned from the return value, and a destination
that is itself in `KNOWN_OBSTACLES` (the planner returns `[]` and the leg is skipped
with "No path").

## The rubric and demo

You're graded on the integrated system, component by component:

| Category | Points | What it takes |
|---|---|---|
| BFS pathfinding | 10 | Correct shortest paths; the Lesson 5-6 tests pass |
| Driving integration | 10 | Robot physically drives the computed paths, leg after leg |
| Obstacle detection | 10 | Rangefinder detects and `add_blocked()` updates the list |
| Re-planning | 10 | Reroutes correctly around discovered obstacles |
| Experience | 10 | Run 1 prints what it found; Run 2 starts from that list |
| Demonstration | 5 | Run 1 discovers & reroutes; Run 2 avoids known obstacles |
| Code quality | 5 | Readable, uses functions, meaningful comments |

For the demo, run twice and have your numbers ready: "Run 1 took X steps with Y reroutes;
Run 2 took A steps with B reroutes." **Finished early?** Try an extension — visiting the
nearest destination next, obstacle expiration (re-check old obstacles after a few runs),
a `print_grid()` map of the route after each leg, or — if you did the class extensions —
a `Navigator` object that owns `position` and `heading` so the destination loop has
nothing to pass back and forth.

<TeacherNote title="Integration is the hard part — simulate first, celebrate the journey">

Students underestimate how hard connecting working parts is. The recurring bugs: not
assigning `position, heading` from the return value, clearing `BLOCKED` between legs, and
a destination that sits on a known obstacle. Insist everyone gets the simulation version
working before the robot — logic first, hardware second. Use the rubric as a
self-assessment checklist; each row maps to a lesson. At the demo, ask *why* Run 2 is
better and listen for "better data," not "the robot is smarter." For 50-minute periods
this spans 2–3 days (assembly/simulation, robot testing, demos). Finally: take a moment
to mark how far students have come — from "Hello, World" to an autonomous robot that
navigates, senses, and learns. That's a real accomplishment.

**The full program** is `lesson-09-capstone.py` in the module's solutions folder; the
student starter has the destination loop and `KNOWN_OBSTACLES` as TODOs, with the
toolkit functions already in place. Students who did the class extensions should run
the capstone with their `Navigator` and `BFS` objects rather than the functions —
that is the version of the course they have been building since Lesson 2-9. Nothing
in the rubric changes.

</TeacherNote>
