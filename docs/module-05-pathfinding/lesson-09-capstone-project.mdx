## The mission

Your robot is an autonomous delivery vehicle. It must visit four or more grid destinations
in sequence, and for each leg: plan a path, drive it while watching for obstacles, and
reroute whenever the rangefinder finds one. Everything you need already exists in
`robot.py` — the planner (Lessons 5-4 and 5-5) and its paper tests (5-6), detection
(5-7), the drive-until-you-arrive function and carrying knowledge between runs (5-8).
Today you connect them.

You'll demonstrate with **two runs**: Run 1 starts with an empty blocked list, discovers
obstacles the hard way, and prints what it found; Run 2 starts with that list typed in, so
it plans around them and reroutes less. The drop in step count between runs *is* the
learning.

```python
    # with its step count, and move position on to that
    # destination for the next leg
    pass

def test_capstone():

    #    (empty on Run 1, last run's list on Run 2)
    # 2. position (0, 0), heading 0; both totals at 0
    # 3. print the plan for leg 1; wait for the button
    # 4. for each destination, with its leg number:
    #        navigate_with_detection() -- plan, follow,

    #        ... keeping position and heading up to date
    #        add its steps and reroutes to the totals

    # 6. print the totals: steps, reroutes

```

The name is `CAPSTONE_DESTINATIONS` because `DESTINATIONS` is already in the file —
Lesson 4-9's delivery run still reads it, and a finished section is not edited from
another one.

The **blocked list is the thread** tying it together: step 1 fills it, the planner
reads it on every call, detection adds to it, and step 5 hands it to the next run. And
every one of those goes through `add_blocked()` — the planner never knows which.

## The destination loop

Lesson 5-8's `navigate_with_detection()` already handles one trip — plan, follow,
re-plan until arrival — and returns where the robot ended up. The capstone's new code
is the loop that calls it once per destination, feeding each trip's end position and
heading into the next. The call inside the loop is the one from your Lesson 5-8 test,
with the leg's destination in place of a fixed one:

```python
        position, heading, steps, reroutes = navigate_with_detection(
            position, heading, dest, rangefinder, OBSTACLE_CM
        )
```

Two details are easy to get wrong. `position` and `heading` must be **assigned from the
return value** — forget the `position, heading, ... =` part and the second leg plans from
(0, 0) while the robot sits somewhere else. And only the *first* leg is printed before
the button, because later legs are planned from wherever the robot actually ends up,
including around obstacles it hasn't found yet.

If you built the `Navigator` class, there is no `position, heading, ... =` line to get
wrong: `navigate_with_detection()` is a method that updates `navigator.position` and
`navigator.heading` itself and returns the two counts. With the `BFS` class, the
planner calls are `planner.compute_path()` and `planner.add_blocked()`, and the list
you print at the end is `planner.blocked`.

## Activity · Test in three levels

Do **not** jump straight to the full run on the robot. If something breaks, you won't
know which piece. Build up, one test on the run line at a time:

1. **Planner alone (no robot).** Write `test_capstone_paper()` from its outline and
   set the run line to it. It is Lesson 4-9's paper test on today's destinations with
   the BFS planner: the four paths on screen, with their step counts, planned around
   whatever is in `KNOWN_OBSTACLES`. On Run 1 that list is empty; type in a pretend
   one and run it again to see the legs bend around it. Count the steps.
2. **Dry run on the grid.** Write `test_capstone()` from its outline, with the
   simulated sensor in `navigate_with_detection()`'s look-ahead line (Lesson 5-8,
   step 1) and `SIMULATED_OBSTACLES` set to three intersections the paper test's
   paths cross — `[(1, 0), (2, 2), (3, 1)]` works with the destinations above. No
   boxes on the grid. Verify that paths compute, pretend obstacles register, the
   blocked list grows across all four legs, and the list printed at the end is the one
   you'd want to start the next run with.
3. **The real thing.** Put the look-ahead line back to `rangefinder.distance()`, put
   boxes on the grid, and run twice: Run 1 with `KNOWN_OBSTACLES = []`, then Run 2
   with the printed list typed in.

Watch for the classic integration bugs: the blocked list getting reset between
destinations (one `BLOCKED` for the whole run — never call `clear_blocked()` between
legs), `position` and `heading` not assigned from the return value, and a destination
that is itself in `KNOWN_OBSTACLES` (the planner returns `[]` and the leg is skipped
with "No path").

<Reveal title="Check your paper test" hint="write and run it first">

```python
def test_capstone_paper():
    for intersection in KNOWN_OBSTACLES:
        add_blocked(intersection)
    position = (0, 0)
    for dest in CAPSTONE_DESTINATIONS:
        path = compute_bfs_path(position, dest)
        print("To", dest, ":", path, " steps:", len(path))
        position = dest
```

`position = dest` is the paper stand-in for the position `navigate_with_detection()`
hands back — on paper the robot always arrives. With nothing blocked the four legs
are 4, 2, 3 and 3 steps.

</Reveal>

This lesson's addition to the OBSTACLES section of `robot.py`, plus the run block;
the rest of the file is as the Lesson 5-8 teacher copy left it. The file is
`lesson-09-capstone.py` in the Module 5 solutions. `test_capstone()` is the graded

```python
# --- Lesson 5-9: capstone, the delivery run ---
# The module project: visit CAPSTONE_DESTINATIONS in order,
# each leg with navigate_with_detection(), starting from what
# the last run found (KNOWN_OBSTACLES) and printing what this
# run found for the next one. Nothing new is defined; the
# sections above did the work, and this test connects them.
CAPSTONE_DESTINATIONS = [(1, 3), (3, 3), (3, 0), (0, 0)]

def test_capstone_paper():
    for intersection in KNOWN_OBSTACLES:
        add_blocked(intersection)
    position = (0, 0)
    for dest in CAPSTONE_DESTINATIONS:
        path = compute_bfs_path(position, dest)
        print("To", dest, ":", path, " steps:", len(path))
        position = dest

def test_capstone():
    for intersection in KNOWN_OBSTACLES:
        add_blocked(intersection)
    position = (0, 0)
    heading = 0                      # 0 = N, 1 = E, 2 = S, 3 = W
    total_steps = 0
    total_reroutes = 0

    print("Planned path for leg 1:",
          compute_bfs_path(position, CAPSTONE_DESTINATIONS[0]))
    board.wait_for_button()

    for i in range(len(CAPSTONE_DESTINATIONS)):
        dest = CAPSTONE_DESTINATIONS[i]
        print("--- Leg", i + 1, ": Heading to", dest, "---")

        position, heading, steps, reroutes = navigate_with_detection(
            position, heading, dest, rangefinder, OBSTACLE_CM
        )

        total_steps = total_steps + steps
        total_reroutes = total_reroutes + reroutes
        print("  Arrived at", dest)

    print("=== FINAL REPORT ===")
    print("Total steps:", total_steps)
    print("Total reroutes:", total_reroutes)
    print("Obstacles discovered:", BLOCKED)

# ===== RUN =====
board.wait_for_button()
test_capstone()
```

With the simulated sensor and `SIMULATED_OBSTACLES = [(1, 0), (2, 2), (3, 1)]`, Run 1
prints 20 steps and 3 reroutes and discovers all three; Run 2 with that list typed
into `KNOWN_OBSTACLES` prints 18 steps and 0 reroutes. Useful numbers to have in your
pocket when a team's dry run looks off.

**Class track:** the loop body is `steps, reroutes =
navigator.navigate_with_detection(dest, rangefinder, OBSTACLE_CM)` and the final
line prints `planner.blocked`; there is no `position, heading` to drop.

</TeacherNote>

<TeacherNote title="Integration is the hard part — simulate first, celebrate the journey">

Students underestimate how hard connecting working parts is. The recurring bugs: not
assigning `position, heading` from the return value, clearing `BLOCKED` between legs, and
a destination that sits on a known obstacle. Insist everyone gets the dry-run version
working before a box touches the grid — logic first, hardware second. Use the rubric as a
self-assessment checklist; each row maps to a lesson. At the demo, ask *why* Run 2 is
better and listen for "better data," not "the robot is smarter." For 50-minute periods
this spans 2–3 days (assembly/simulation, robot testing, demos). Finally: take a moment
to mark how far students have come — from "Hello, World" to an autonomous robot that
navigates, senses, and learns. That's a real accomplishment.
