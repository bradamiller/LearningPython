## The mission

Your robot is an autonomous delivery vehicle. It visits four or more grid destinations
in order. For each leg it plans a path, drives it while watching for obstacles, and
reroutes whenever the rangefinder finds one. Everything you need is already in
`robot.py`, from Lessons 5-4 to 5-8. Today you connect them.

You'll demonstrate with **two runs**:

- **Run 1** starts with an empty blocked list, discovers obstacles the hard way, and
  prints what it found.
- **Run 2** starts with that list typed in, so it plans around them and reroutes less.

The drop in steps between runs *is* the learning.

## This lesson's skeleton

Paste this at the end of the OBSTACLES section, above `RUN`. Nothing new is defined:
one setting, a paper test that prints every leg's path without moving the robot, and the
project itself, which is a test function like every program in this course.

```python
# --- Lesson 5-9: capstone, the delivery run ---
# The module project: visit CAPSTONE_DESTINATIONS in order,
# each leg with navigate_with_detection(), starting from what
# the last run found (KNOWN_OBSTACLES) and printing what this
# run found for the next one. Nothing new is defined; the
# sections above did the work, and this test connects them.
CAPSTONE_DESTINATIONS = [(1, 3), (3, 3), (3, 0), (0, 0)]

def test_capstone_paper():
    # no robot: hand KNOWN_OBSTACLES to add_blocked(), then
    # from (0, 0) plan each leg with the BFS planner, print it
    # with its step count, and move position on to that
    # destination for the next leg
    pass

def test_capstone():
    # 1. hand KNOWN_OBSTACLES to add_blocked()
    #    (empty on Run 1, last run's list on Run 2)
    # 2. position (0, 0), heading 0; both totals at 0
    # 3. print the plan for leg 1; wait for the button
    # 4. for each destination, with its leg number:
    #        navigate_with_detection() -- plan, follow,
    #        re-plan until arrived (Lesson 5-8)
    #        ... keeping position and heading up to date
    #        add its steps and reroutes to the totals
    # 5. print the blocked list -- what you type in next run
    # 6. print the totals: steps, reroutes
    pass
```

The name is `CAPSTONE_DESTINATIONS` because Module 4's `test_delivery()` still reads
`DELIVERY_STOPS`, and a finished section is not edited from another one.

The **blocked list is the thread** tying it together: step 1 fills it, the planner
reads it on every call, detection adds to it, and step 5 hands it to the next run. Every
addition goes through `add_blocked()`, so the planner never knows which source it came
from.

## The destination loop

`navigate_with_detection()` (Lesson 5-8) already handles one trip. The new code is a
loop that calls it once per destination, feeding each trip's end pose into the next.
The call is the one from your Lesson 5-8 test, with the leg's destination:

```python
        position, heading, steps, reroutes = navigate_with_detection(
            position, heading, dest, rangefinder, OBSTACLE_CM
        )
```

Two details are easy to get wrong:

- **Assign the pose (`position` and `heading`) from the return value.** Forget the
  `position, heading, ... =` part and leg 2 plans from (0, 0) while the robot sits
  somewhere else.
- **Print only the *first* leg before the button.** Later legs are planned from wherever
  the robot actually ends up, around obstacles it hasn't found yet.

With the `Navigator` class there is no `position, heading, ... =` line: the method
updates `navigator.position` and `navigator.heading` itself and returns the two counts.
With the `BFS` class, the planner calls are `planner.compute_path()` and
`planner.add_blocked()`, and you print `planner.blocked` at the end.

## Activity · Test in three levels

Do **not** jump straight to the full run: if something breaks, you won't know which
piece. Build up, one test on the run line at a time:

1. **Planner alone (no robot).** Write `test_capstone_paper()` from its outline and
   set the run line to it. It is Module 4's on-screen run on today's destinations with
   the BFS planner: the four paths on screen, with their step counts, planned around
   whatever is in `KNOWN_OBSTACLES`. On Run 1 that list is empty; type in a pretend
   one and run again to see the legs bend around it.
2. **Dry run on the grid.** Write `test_capstone()` from its outline. Put the simulated
   sensor in `navigate_with_detection()`'s look-ahead line (Lesson 5-8, step 1) and
   set `SIMULATED_OBSTACLES = [(1, 0), (2, 2), (3, 1)]`, three intersections the paper
   paths cross. No obstacles on the grid. Check that paths compute, pretend obstacles
   register, the blocked list grows across all four legs, and the final list is the one
   to start the next run with.
3. **The real thing.** Put the look-ahead line back to `rangefinder.distance()`, put
   obstacles on the grid, and run twice: Run 1 with `KNOWN_OBSTACLES = []`, then Run 2
   with the printed list typed in.

Watch for the classic integration bugs:

- The blocked list reset between destinations. One `BLOCKED` serves the whole run: never
  call `clear_blocked()` between legs.
- `position` and `heading` not assigned from the return value.
- A destination that is itself in `KNOWN_OBSTACLES`: the planner returns `[]` and the leg
  is skipped with "No path".

<Reveal title="Check your paper test" hint="write and run it first">

```python
def test_capstone_paper():
    for intersection in KNOWN_OBSTACLES:
        add_blocked(intersection)
    position = (0, 0)
    for dest in CAPSTONE_DESTINATIONS:
        path = compute_bfs_path(position, dest)
        print("To", dest, ":", path, " steps:", len(path))
        position = dest
```

`position = dest` stands in for the position `navigate_with_detection()` hands back:
on paper the robot always arrives. With nothing blocked the four legs are 4, 2, 3 and 3
steps.

</Reveal>

<TeacherNote title="Solution (teacher copy)">

This lesson's addition to the OBSTACLES section of `robot.py`, plus the run block;
the rest of the file is as the Lesson 5-8 teacher copy left it. The whole file is
in the [Module 5 sample programs](/teacher-guide/sample-programs/module-5). `test_capstone()` is the graded
work, and there is no student reveal for it; the paper test has one.

```python
# --- Lesson 5-9: capstone, the delivery run ---
# The module project: visit CAPSTONE_DESTINATIONS in order,
# each leg with navigate_with_detection(), starting from what
# the last run found (KNOWN_OBSTACLES) and printing what this
# run found for the next one. Nothing new is defined; the
# sections above did the work, and this test connects them.
CAPSTONE_DESTINATIONS = [(1, 3), (3, 3), (3, 0), (0, 0)]

def test_capstone_paper():
    for intersection in KNOWN_OBSTACLES:
        add_blocked(intersection)
    position = (0, 0)
    for dest in CAPSTONE_DESTINATIONS:
        path = compute_bfs_path(position, dest)
        print("To", dest, ":", path, " steps:", len(path))
        position = dest

def test_capstone():
    for intersection in KNOWN_OBSTACLES:
        add_blocked(intersection)
    position = (0, 0)
    heading = 0                      # 0 = N, 1 = E, 2 = S, 3 = W
    total_steps = 0
    total_reroutes = 0

    print("Planned path for leg 1:",
          compute_bfs_path(position, CAPSTONE_DESTINATIONS[0]))
    board.wait_for_button()

    for i in range(len(CAPSTONE_DESTINATIONS)):
        dest = CAPSTONE_DESTINATIONS[i]
        print("--- Leg", i + 1, ": Heading to", dest, "---")

        position, heading, steps, reroutes = navigate_with_detection(
            position, heading, dest, rangefinder, OBSTACLE_CM
        )

        total_steps = total_steps + steps
        total_reroutes = total_reroutes + reroutes
        print("  Arrived at", dest)

    print("=== FINAL REPORT ===")
    print("Total steps:", total_steps)
    print("Total reroutes:", total_reroutes)
    print("Obstacles discovered:", BLOCKED)

# ===== RUN =====
board.wait_for_button()
test_capstone()
```

With the simulated sensor and `SIMULATED_OBSTACLES = [(1, 0), (2, 2), (3, 1)]`, Run 1
prints 20 steps and 3 reroutes and discovers all three; Run 2 with that list typed
into `KNOWN_OBSTACLES` prints 18 steps and 0 reroutes. Useful numbers to have in your
pocket when a team's dry run looks off.

**Class track:** the loop body is `steps, reroutes =
navigator.navigate_with_detection(dest, rangefinder, OBSTACLE_CM)` and the final
line prints `planner.blocked`; there is no `position, heading` to drop.

</TeacherNote>

## The rubric and demo

You're graded on the integrated system, component by component:

| Category | Points | What it takes |
|---|---|---|
| BFS pathfinding | 10 | Correct shortest paths; the Lesson 5-6 tests pass |
| Driving integration | 10 | Robot physically drives the computed paths, leg after leg |
| Obstacle detection | 10 | Rangefinder detects and `add_blocked()` updates the list |
| Re-planning | 10 | Reroutes correctly around discovered obstacles |
| Experience | 10 | Run 1 prints what it found; Run 2 starts from that list |
| Demonstration | 5 | Run 1 discovers & reroutes; Run 2 avoids known obstacles |
| Code quality | 5 | Readable, uses functions, meaningful comments |

For the demo, run twice and have your numbers ready: "Run 1 took X steps with Y reroutes;
Run 2 took A steps with B reroutes."

**Finished early?** Try an extension:

- Visit the nearest destination next.
- Obstacle expiration: re-check old obstacles after a few runs.
- A `print_grid()` map of the rings after each leg.
- If you did the class extensions: a `Navigator` object that owns `position` and
  `heading`, so the destination loop has nothing to pass back and forth.

<TeacherNote title="Integration is the hard part — simulate first, celebrate the journey">

Students underestimate how hard connecting working parts is. The recurring bugs: not
assigning `position, heading` from the return value, clearing `BLOCKED` between legs, and
a destination that sits on a known obstacle. Insist everyone gets the dry-run version
working before an obstacle touches the grid — logic first, hardware second. Use the rubric as a
self-assessment checklist; each row maps to a lesson. At the demo, ask *why* Run 2 is
better and listen for "better data," not "the robot is smarter." For 50-minute periods
this spans 2–3 days (assembly/simulation, robot testing, demos). Finally: take a moment
to mark how far students have come — from "Hello, World" to an autonomous robot that
navigates, senses, and learns. That's a real accomplishment.
