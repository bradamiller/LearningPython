## Where does the robot keep what it has learned?

Three lessons from now the robot will see an obstacle with its rangefinder while driving,
and have to plan around it. Where does it write down that the obstacle is there?

"Pass the blocked list to the function" is half right. The robot learns about obstacles
*one at a time, while driving*, so the list has to last between one path and the next.
It goes at the top of the section, where every function can see it, like `ROWS` and
`COLS`:

```python
BLOCKED = []     # intersections the robot must not drive through
```

Capitals, like `THRESHOLD`, because it is a setting. It grows only through one
function.

## Two rules we will never break

Every planner in this course follows these two rules.

**Rule 1 — the planner is told where the robot is.** Every planner looks like
`compute_something_path(start, destination)` and never remembers the position. The
driving code owns it. A second copy in the planner could disagree, and the planner
would plan from the wrong place. One owner.

**Rule 2 — the path is the list of intersections to drive *to*.** The start is not
in it, so `len(path)` is the number of steps and "already there" is `[]`.

Module 4's planner already follows both: `compute_manhattan_path((0, 0), (0, 2))`
returns `[(0, 1), (0, 2)]`, two steps, no start.

## Activity · Build the toolkit

### Step 1 · `add_blocked()`

The one way to tell the planner about an obstacle: an `if` and an `append` that add
the intersection to `BLOCKED` *only if it isn't already there*. The robot may see the
same wall twice.

Does this need `global BLOCKED`? In Lesson 2-7, `set_threshold()` needed
`global THRESHOLD`. The difference is what each function does to the name:

```python
    THRESHOLD = new_value              # Lesson 2-7: REASSIGNS the name -- needs global
    BLOCKED.append(intersection)       # today: CHANGES the list -- no global needed
```

`global` is only for *reassigning* a module-level name. `append` changes the list
`BLOCKED` already names. `clear_blocked()` empties the list *in place*, with `pop()`
until `len(BLOCKED)` is zero, so tests can start fresh. `BLOCKED = []` inside it would
reassign the name and need `global`.

<Figure
  src="/img/lesson-m5-04/append-vs-assign.svg"
  alt="Left, BLOCKED.append((1, 1)): the name BLOCKED still points at the same list, which now has one more item, so no global is needed. Right, BLOCKED = [] inside a function: this makes a new local name pointing at a new empty list, gone when the function returns, while the real BLOCKED list is untouched; that is the case that needs global."
  caption="append changes the list the name points at. = points a name at something else, and inside a function that name is a new local."
/>

Write both bodies. Step 2 gives you the test.

### Step 2 · `build_graph()` — the graph learns about blocked intersections

In Lesson 5-3, `build_grid_graph()` built the open grid. Now it has to leave the
blocked intersections out, both halves of blocking a node: not a key, and not anyone's
neighbor. In GRID GRAPH, change the `def` line to

```python
def build_graph(rows, cols, blocked):
    """Return the grid as a dictionary, leaving out every
    intersection in blocked: not a key, not anyone's neighbor."""
```

and make two changes to the body:

1. If `(x, y)` is in `blocked`, skip it. It never becomes a key.
2. Each of the four neighbor checks also needs the neighbor *not* in `blocked`. This
   keeps a blocked intersection out of every *other* intersection's neighbor list. Miss
   it and the graph still has edges into the wall.

Keep the directions in the order left, right, down, up: the order Lesson 5-1's trace
checked neighbors, which is why its printed path matched the table.

The old name is gone, the way `SETPOINT` disappeared in Lesson 2-6, so fix
`test_grid_graph()` to build with `build_graph(ROWS, COLS, BLOCKED)` and set the run
line to it. With nothing blocked, the output matches Lesson 5-3: 16, four neighbors,
two neighbors. Don't go on until it does.

### Step 3 · The placeholder, and a test with a wall in it

The placeholder `compute_bfs_path()` builds the graph *itself*, from `BLOCKED`, on
every call. Why not once at the top of the file? Because a wall found at step 3 must be
gone from the graph that plans step 4. Rebuilding every call makes that automatic: no
"forgot to rebuild" bug. On a 4×4 grid it takes no time worth measuring.

Now write `test_blocked_graph()` to exercise all three functions, and set the run line
to it:

1. Block `(1, 1)` with `add_blocked()` and build the graph.
2. Print the blocked list, the number of intersections, whether `(1, 1)` is in the
   graph, and the neighbors of `(0, 1)`.
3. Call `add_blocked((1, 1))` again and print the list.
4. Print what `compute_bfs_path((0, 0), (3, 3))` returns.

It should show:

```text
Blocked: [(1, 1)]
Number of intersections: 15
(1,1) in graph? False
Neighbors of (0,1): [(0, 0), (0, 2)]
Blocked after adding (1,1) again: [(1, 1)]
compute_bfs_path is not written yet!
Path: []
```

Check: fifteen keys, `(1, 1)` not one of them and gone from `(0, 1)`'s neighbors,
and the list still one entry long after the second `add_blocked()`. The empty path is
the placeholder's.

Before you leave, write down (don't run) what these should return once Lesson 5-5
is done, with nothing blocked:

- `compute_bfs_path((0, 0), (0, 2))`
- `compute_bfs_path((2, 2), (2, 2))`

<Reveal title="Check your three functions" hint="run test_blocked_graph() first">

```python
def build_graph(rows, cols, blocked):
    """Return the grid as a dictionary, leaving out every
    intersection in blocked: not a key, not anyone's neighbor."""
    graph = {}
    for x in range(cols):
        for y in range(rows):
            if (x, y) in blocked:
                continue
            neighbors = []
            for dx, dy in [(-1, 0), (1, 0), (0, -1), (0, 1)]:
                nx, ny = x + dx, y + dy
                if 0 <= nx < cols and 0 <= ny < rows and (nx, ny) not in blocked:
                    neighbors.append((nx, ny))
            graph[(x, y)] = neighbors
    return graph

def add_blocked(intersection):
    """Record intersection in BLOCKED, once, even if told twice."""
    if intersection not in BLOCKED:
        BLOCKED.append(intersection)

def clear_blocked():
    """Empty BLOCKED in place, so a test can start fresh."""
    while len(BLOCKED) > 0:
        BLOCKED.pop()
```

This version differs from Lesson 5-3's: one loop over a list of `(dx, dy)` changes
does the four checks, and `continue` skips a blocked intersection. The `for dx, dy
in` line unpacks as it loops (Lesson 4-7): each item in the list is a two-number tuple,
and every pass splits it into `dx` and `dy`. The line under it assigns two at once the
same way: the right side makes a tuple, and `nx, ny` unpacks it. Keeping four `if`
lines, each with its own `not in blocked` check added, is the same function. Compare
the output.

</Reveal>

<TeacherNote title="Solution (teacher copy)">

The GRID GRAPH section as this lesson leaves it (rewritten in place: `build_graph()`
where `build_grid_graph()` was), the new BFS PLANNER section, and the run block. The
rest of the file is as the Lesson 5-3 teacher copy left it. The whole file at the end of the module is in the
[Module 5 sample programs](/teacher-guide/sample-programs/module-5).

```python
# ===== GRID GRAPH =====
# The grid as a graph, in a dictionary: every intersection is
# a key, and its value is the list of neighbors it is joined
# to. The BFS PLANNER searches this graph. Starts with the
# open grid; Lesson 5-4 adds the blocked list, so a blocked
# intersection is neither a key nor anyone's neighbor.
ROWS = 4                 # the grid is ROWS x COLS intersections
COLS = 4

def build_graph(rows, cols, blocked):
    """Return the grid as a dictionary, leaving out every
    intersection in blocked: not a key, not anyone's neighbor."""
    graph = {}
    for x in range(cols):
        for y in range(rows):
            if (x, y) in blocked:
                continue
            neighbors = []
            for dx, dy in [(-1, 0), (1, 0), (0, -1), (0, 1)]:
                nx, ny = x + dx, y + dy
                if 0 <= nx < cols and 0 <= ny < rows and (nx, ny) not in blocked:
                    neighbors.append((nx, ny))
            graph[(x, y)] = neighbors
    return graph

def test_grid_graph():
    graph = build_graph(ROWS, COLS, BLOCKED)
    print("Intersections:", len(graph))          # 16
    print("Neighbors of (1, 1):", graph[(1, 1)])  # 4 of them
    print("Neighbors of (0, 0):", graph[(0, 0)])  # 2: a corner

# --- Lesson 5-4: the blocked list ---
# BLOCKED is the one record of where the robot must not go.
# add_blocked() is the one way in: tests, the rangefinder and
# you all use it. build_graph() builds AROUND the list, so a
# blocked intersection is never a key and never a neighbor.
BLOCKED = []             # intersections the robot must not drive through

def add_blocked(intersection):
    """Record intersection in BLOCKED, once, even if told twice."""
    if intersection not in BLOCKED:
        BLOCKED.append(intersection)

def clear_blocked():
    """Empty BLOCKED in place, so a test can start fresh."""
    while len(BLOCKED) > 0:
        BLOCKED.pop()

def test_blocked_graph():
    add_blocked((1, 1))
    graph = build_graph(ROWS, COLS, BLOCKED)
    print("Blocked:", BLOCKED)
    print("Number of intersections:", len(graph))     # 15
    print("(1,1) in graph?", (1, 1) in graph)          # False
    print("Neighbors of (0,1):", graph[(0, 1)])        # (1,1) gone
    add_blocked((1, 1))
    print("Blocked after adding (1,1) again:", BLOCKED)
    print("Path:", compute_bfs_path((0, 0), (3, 3)))


# ===== BFS PLANNER =====
# The second planner. compute_bfs_path(start, destination)
# has the same shape as the MANHATTAN PLANNER's function and
# keeps the same two promises (told the position; the path
# leaves the start out), but it numbers the GRID GRAPH as a
# wave from the destination, so it routes AROUND whatever is in BLOCKED. Pure
# dictionary work: every test here runs with the robot still.

def compute_bfs_path(start, destination):
    """Shortest path from start to destination around
    BLOCKED, as the list of intersections to drive to."""
    graph = build_graph(ROWS, COLS, BLOCKED)      # rebuilt every call
    print("compute_bfs_path is not written yet!")
    return []

# ===== RUN =====
board.wait_for_button()
test_blocked_graph()
```

Note that `BLOCKED` is defined *below* `build_graph()` and above the test that uses
it; that is fine, because `build_graph()` takes the list as a parameter and never
reads the global. Python only needs a name to exist by the time a line *runs*, and
the run block is last.

</TeacherNote>

<TeacherNote title="Answers, and what to listen for">

`[(0, 1), (0, 2)]` and `[]` — Rule 2 both times. The exit ticket is the `global`
question above; students who can explain reassign-vs-change-in-place have the whole
idea. The other thing to listen for during the activity is the second `in blocked`
check: a `build_graph` that drops blocked keys but still lists them as neighbors is
the single most common bug, and it only shows up as a search that walks into a wall
in Lesson 5-5. Catch it here — `test_blocked_graph()`'s neighbors-of-(0,1) line is
the one that shows it.

**Challenge for students who finish early:** `add_blocked((1, 0))`,
`add_blocked((1, 1))`, rebuild, and print the whole graph. Which intersections in the
left column (x = 0) can still reach the column at x = 2, and through what? Then: "Using only `build_graph` and the
wave idea, write `is_reachable(a, b)`." They'll write most of Lesson 5-5 a day
early, which is fine.

</TeacherNote>
