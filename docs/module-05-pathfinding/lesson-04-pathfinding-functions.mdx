## Where does the robot keep what it has learned?

Three lessons from now the robot will be driving, see a box in the way with its
rangefinder, and have to plan a new route around it. So: where does it write down
that the box is there?

"Pass the blocked list to the function" is the first answer most people give, and
it's half right. The problem is *when* the robot learns about obstacles: one at a
time, in the middle of driving. Something has to keep the list between one path and
the next. That something is a variable at the top of the section that every function
can see — exactly the way `reflectance` and `THRESHOLD` sit at the top of the
LINE SENSOR section of `robot.py`, and the way `ROWS` and `COLS` already sit at the
top of GRID GRAPH:

```python
BLOCKED = []     # intersections the robot must not drive through
```

Capital letters, like `THRESHOLD`, because it is a setting rather than something
that changes in the middle of a calculation. `BLOCKED` does grow — but only through
one function.

## Two rules we will never break

Before any code, two rules that every planner in this course follows, and that
nothing later ever breaks. Keep them in view all module.

**Rule 1 — the planner is told where the robot is.** Every planner looks like
`compute_something_path(position, destination)`. It never remembers the position
between calls. The driving code already knows where the robot is; if the planner
kept its own copy, the two could disagree, and a planner that believes the robot is
somewhere it isn't will plan from the wrong place. One owner.

**Rule 2 — the path is the list of intersections to drive *to*.** The start is not
in it. So `len(path)` is the number of steps, and "already there" is `[]`.

`compute_manhattan_path` from Module 4 already follows both. Check:
`compute_manhattan_path((0, 0), (0, 2))` returns `[(0, 1), (0, 2)]` — two steps,
no start.

## Activity · Build the toolkit

### Step 1 · `add_blocked()`

The one way anyone tells the planner about an obstacle. Its body is an `if` and an
`append`: add the intersection to `BLOCKED` *only if it isn't already there*.

Why the `if`? The robot may see the same wall twice. A list with `(2, 0)` in it
twice is harmless but untidy, and it would make the printed grid confusing.

Now the question that catches people: does this need `global BLOCKED`? In Lesson
2-7, `set_threshold()` needed `global THRESHOLD`. The difference is what each
function does to the name:

```python
    THRESHOLD = new_value              # Lesson 2-7: REASSIGNS the name -- needs global
    BLOCKED.append(intersection)       # today: CHANGES the list -- no global needed
```

`global` is for *reassigning* a module-level name. `append` doesn't reassign
anything — `BLOCKED` still names the same list; the list just has one more thing in
it. `clear_blocked()` is the same idea the other way: it empties the list *in place*
— `pop()` until `len(BLOCKED)` is zero — so that tests can start fresh. Writing
`BLOCKED = []` inside it would reassign the name and need `global`; popping doesn't.

<Figure
  src="/img/lesson-m5-04/append-vs-assign.svg"
  alt="Left, BLOCKED.append((1, 1)): the name BLOCKED still points at the same list, which now has one more item, so no global is needed. Right, BLOCKED = [] inside a function: this makes a new local name pointing at a new empty list, gone when the function returns, while the real BLOCKED list is untouched; that is the case that needs global."
  caption="append changes the list the name points at. = points a name at something else, and inside a function that name is a new local."
/>

Write both bodies. There's nothing to run yet — step 2 gives you the test.

### Step 2 · `build_graph()` — Lesson 5-2's two functions become one

In Lesson 5-2 you built the graph with `build_grid_graph()` and then took blocked
intersections out with `remove_blocked()`. Today one function does both: while
building, skip anything blocked. In the GRID GRAPH section, change the `def` line to

```python
def build_graph(rows, cols, blocked):
    """Return the grid as a dictionary, leaving out every
    intersection in blocked: not a key, not anyone's neighbor."""
```

and make two changes to the body you already have. First, if `(x, y)` itself is
in `blocked`, skip it entirely — it never becomes a key. Second, each of the four
neighbor checks gets one more condition: the neighbor must not be in `blocked` either.
Both `in blocked` checks are needed. The first keeps a blocked intersection from
becoming a key. The second keeps it out of every *other* intersection's neighbor list.
Miss the second and the graph still has edges leading into the wall.

Keep the four directions in the order left, right, down, up. That's the order
Lesson 5-3's trace checked neighbors, which is why its printed path matched the
table.

Then delete `remove_blocked()` and its test — the new function has absorbed them, the
way `SETPOINT` disappeared in Lesson 2-6 — and fix `test_grid_graph()`, which still
calls a function that no longer exists: it should build with
`build_graph(ROWS, COLS, BLOCKED)` now. Set the run line to it. With nothing blocked,
the output is exactly what it was in Lesson 5-2: 16, four neighbors, two neighbors.
Don't go on until it is.

### Step 3 · The placeholder, and a test with a wall in it

Look at the placeholder `compute_bfs_path()` again. It builds the graph *itself*, from
`BLOCKED`, every time it's called. Why not build the graph once at the top of the
file? Because a wall the robot finds at step 3 has to be gone from the graph it plans
step 4 on. Rebuilding on every call makes that automatic; there is no "forgot to
rebuild" bug to have. On a 4×4 grid the rebuild visits sixteen intersections and takes
no time worth measuring.

Now write a test — say `test_blocked_graph()` — that exercises all three functions:
block `(1, 1)` with `add_blocked()`, build the graph, and print the blocked list, the
number of intersections, whether `(1, 1)` is in the graph, and the neighbors of
`(0, 1)`. Then call `add_blocked((1, 1))` a second time and print the list again.
Finally print what `compute_bfs_path((0, 0), (3, 3))` returns. Set the run line to it.
Here is what it should show:

```text
Blocked: [(1, 1)]
Number of intersections: 15
(1,1) in graph? False
Neighbors of (0,1): [(0, 0), (0, 2)]
Blocked after adding (1,1) again: [(1, 1)]
compute_bfs_path is not written yet!
Path: []
```

Three things to check against the list of what `build_graph` promises: fifteen
keys, `(1, 1)` is not one of them, and `(1, 1)` is gone from `(0, 1)`'s neighbors.
The list is still one entry long after the second `add_blocked()`. Then the
placeholder's empty path — which is, for now, the right answer to nothing.

Before you leave, write down (don't run) what these should return once Lesson 5-5
is finished, with nothing blocked:

- `compute_bfs_path((0, 0), (0, 2))`
- `compute_bfs_path((2, 2), (2, 2))`

<Reveal title="Check your three functions" hint="run test_blocked_graph() first">

```python
def build_graph(rows, cols, blocked):
    """Return the grid as a dictionary, leaving out every
    intersection in blocked: not a key, not anyone's neighbor."""
    graph = {}
    for x in range(cols):
        for y in range(rows):
            if (x, y) in blocked:
                continue
            neighbors = []
            for dx, dy in [(-1, 0), (1, 0), (0, -1), (0, 1)]:
                nx, ny = x + dx, y + dy
                if 0 <= nx < cols and 0 <= ny < rows and (nx, ny) not in blocked:
                    neighbors.append((nx, ny))
            graph[(x, y)] = neighbors
    return graph

def add_blocked(intersection):
    """Record intersection in BLOCKED, once, even if told twice."""
    if intersection not in BLOCKED:
        BLOCKED.append(intersection)

def clear_blocked():
    """Empty BLOCKED in place, so a test can start fresh."""
    while len(BLOCKED) > 0:
        BLOCKED.pop()
```

This `build_graph()` is written a little differently from the Lesson 5-2 version: the
four directions are a list of `(dx, dy)` changes and one loop does the four checks,
and `continue` skips to the next intersection when this one is blocked. The `for dx, dy
in` line unpacks as it loops (Lesson 4-2): each item in the list is a two-number tuple,
and every pass splits it into `dx` and `dy`. The line under it assigns two at once the
same way: the right side makes a tuple, and `nx, ny` unpacks it. If you kept
your four `if` lines and added `and (x - 1, y) not in blocked` to each, that is
the same function and it is fine. The thing to compare is the output.

</Reveal>

<TeacherNote title="Solution (teacher copy)">

The GRID GRAPH section as this lesson leaves it (rewritten in place: `build_graph()`
where `build_grid_graph()` was, `remove_blocked()` and its test gone), the new BFS
PLANNER section, and the run block. The rest of the file is as the Lesson 5-2 teacher
copy left it. The file is `lesson-04-pathfinding-functions.py` in the Module 5
solutions.

```python
# ===== GRID GRAPH =====
# The grid as a graph, in a dictionary: every intersection is
# a key, and its value is the list of neighbors it is joined
# to. The BFS PLANNER searches this graph. Starts with the
# open grid; Lesson 5-4 adds the blocked list, so a blocked
# intersection is neither a key nor anyone's neighbor.
ROWS = 4                 # the grid is ROWS x COLS intersections
COLS = 4

def build_graph(rows, cols, blocked):
    """Return the grid as a dictionary, leaving out every
    intersection in blocked: not a key, not anyone's neighbor."""
    graph = {}
    for x in range(cols):
        for y in range(rows):
            if (x, y) in blocked:
                continue
            neighbors = []
            for dx, dy in [(-1, 0), (1, 0), (0, -1), (0, 1)]:
                nx, ny = x + dx, y + dy
                if 0 <= nx < cols and 0 <= ny < rows and (nx, ny) not in blocked:
                    neighbors.append((nx, ny))
            graph[(x, y)] = neighbors
    return graph

def test_grid_graph():
    graph = build_graph(ROWS, COLS, BLOCKED)
    print("Intersections:", len(graph))          # 16
    print("Neighbors of (1, 1):", graph[(1, 1)])  # 4 of them
    print("Neighbors of (0, 0):", graph[(0, 0)])  # 2: a corner

# --- Lesson 5-4: the blocked list ---
# BLOCKED is the one record of where the robot must not go.
# add_blocked() is the one way in: tests, the rangefinder and
# you all use it. build_graph() builds AROUND the list, so a
# blocked intersection is never a key and never a neighbor.
BLOCKED = []             # intersections the robot must not drive through

def add_blocked(intersection):
    """Record intersection in BLOCKED, once, even if told twice."""
    if intersection not in BLOCKED:
        BLOCKED.append(intersection)

def clear_blocked():
    """Empty BLOCKED in place, so a test can start fresh."""
    while len(BLOCKED) > 0:
        BLOCKED.pop()

def test_blocked_graph():
    add_blocked((1, 1))
    graph = build_graph(ROWS, COLS, BLOCKED)
    print("Blocked:", BLOCKED)
    print("Number of intersections:", len(graph))     # 15
    print("(1,1) in graph?", (1, 1) in graph)          # False
    print("Neighbors of (0,1):", graph[(0, 1)])        # (1,1) gone
    add_blocked((1, 1))
    print("Blocked after adding (1,1) again:", BLOCKED)
    print("Path:", compute_bfs_path((0, 0), (3, 3)))


# ===== BFS PLANNER =====
# The second planner. compute_bfs_path(position, destination)
# has the same shape as the MANHATTAN PLANNER's function and
# keeps the same two promises (told the position; the path
# leaves the start out), but it searches the GRID GRAPH ring
# by ring, so it routes AROUND whatever is in BLOCKED. Pure
# dictionary work: every test here runs with the robot still.

def compute_bfs_path(position, destination):
    """Shortest path from position to destination around
    BLOCKED, as the list of intersections to drive to."""
    graph = build_graph(ROWS, COLS, BLOCKED)      # rebuilt every call
    print("compute_bfs_path is not written yet!")
    return []

# ===== RUN =====
board.wait_for_button()
test_blocked_graph()
```

Note that `BLOCKED` is defined *below* `build_graph()` and above the test that uses
it; that is fine, because `build_graph()` takes the list as a parameter and never
reads the global. Python only needs a name to exist by the time a line *runs*, and
the run block is last.

</TeacherNote>

<TeacherNote title="Answers, and what to listen for">

`[(0, 1), (0, 2)]` and `[]` — Rule 2 both times. The exit ticket is the `global`
question above; students who can explain reassign-vs-change-in-place have the whole
idea. The other thing to listen for during the activity is the second `in blocked`
check: a `build_graph` that drops blocked keys but still lists them as neighbors is
the single most common bug, and it only shows up as a search that walks into a wall
in Lesson 5-5. Catch it here — `test_blocked_graph()`'s neighbors-of-(0,1) line is
the one that shows it.

**Challenge for students who finish early:** `add_blocked((1, 0))`,
`add_blocked((1, 1))`, rebuild, and print the whole graph. Which intersections in the
left column (x = 0) can still reach the column at x = 2, and through what? Then: "Using only `build_graph` and the
ripples idea, write `is_reachable(a, b)`." They'll write most of Lesson 5-5 a day
early, which is fine.

</TeacherNote>
