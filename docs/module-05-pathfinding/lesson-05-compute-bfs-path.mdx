## Every line is a pencil step

Here is the search loop from the end of Lesson 5-3, with the pencil step beside each
line:

```python
previous = {position: None}        # the first row of the came-from table
to_visit = [position]              # the list beside the grid, with the start on it

while len(to_visit) > 0:
    current = to_visit.pop(0)              # take the OLDEST one off the front
    if current == destination:
        break                              # it got its number -- stop
    for neighbor in graph[current]:        # look at each neighbor
        if neighbor not in previous:       # only if it has no number yet
            previous[neighbor] = current   # write "came from"
            to_visit.append(neighbor)      # add it to the END of the list
```

Two things worth noticing before you type anything. `previous` does double duty:
it records where each intersection came from, *and* — because an intersection
only gets an entry when it's reached — "is a key in `previous`" means "has a number."
That's why `if neighbor not in previous` is the whole numbered-once rule. And the
list is used as a **queue**: things go on the end and come off the front, so a ring
is always finished before the next one starts.

## Activity · Build it in three stages

Open `lesson-05-compute-bfs-path.py`. The toolkit from Lesson 5-4 is already there;
`compute_bfs_path()` is the part to fill in. Build it in the three stages below and
run after each one.

### Step 1 · Setup and the guard

```python
def compute_bfs_path(position, destination):
    graph = build_graph(ROWS, COLS, BLOCKED)
    if position not in graph or destination not in graph:
        return []
    previous = {position: None}
    to_visit = [position]
```

The guard covers a start or destination that is itself blocked: it isn't in the
graph, so there is nothing to search. Return `[]` at once.

### Step 2 · The search

Add the loop from the top of the page. Then, temporarily, put `print(previous)`
right after it and run on the 3×3 with `(1, 1)` blocked, `(0, 0)` to `(2, 2)`. The
printed dictionary should match your Lesson 5-3 came-from table exactly, keys in
the same order.

Ask yourself what happens to `to_visit` if the destination is walled off. It empties
out, the `while` ends, and `destination` never appears in `previous`. Keep that in
mind for the last stage.

### Step 3 · The walk-back

```python
    if destination not in previous:
        return []
    path = []
    current = destination
    while current != position:
        path.append(current)
        current = previous[current]
    path.reverse()
    return path
```

Why `while current != position` and not `while current is not None`? Both would
end the loop, but stopping *at* the start means the start is never appended — which
is Rule 2 from Lesson 5-4 with no trimming needed afterwards. And it gives you
"already there" for free: when `position == destination`, the loop never runs and
the path is `[]`.

Tests 3 and 5 both return `[]`, for different reasons: one because the walk-back
loop never ran, the other because the destination was never reached. Next lesson
the test harness tells those two apart.

## Activity · Break it on purpose

Once all five pass, break the function two ways and watch what happens. Put each
back before the next.

1. **Change `pop(0)` to `pop()`.** Run Test 1 and count the steps. It's longer. With
   `pop()` the search takes the *newest* intersection, so it dives down one path
   before finishing the ring; the first route it finds isn't necessarily shortest.
   That has a name — depth-first search — and it's a fine algorithm for other jobs,
   but not this one.
2. **Delete `if neighbor not in previous:`** (keep the two lines under it, one indent
   level out). Run Test 1. Intersections get their "came from" overwritten by later,
   longer routes, and the walk-back can chase its own tail forever. If it hangs,
   stop it with Ctrl-C. That one line is the numbered-once rule, and without it
   nothing works.

<OptionalExtension title="The BFS class">

Two reasons to wrap the toolkit in a class, and it's worth saying both. `BFS` is a
class because it has setup to hold: the grid size and the blocked list. `Manhattan`
gets a class too, but *only* so that it has the same shape as `BFS` — then one main
program and one test harness (next lesson) work with either by changing one name.
That second reason is the swap, and it's the point.

Neither class remembers where the robot is. Rule 1 holds for classes too.

<SideBySide left="Functions — what you have" right="Class — the extension">

```python
ROWS = 4
COLS = 4
BLOCKED = []

def add_blocked(intersection):
    if intersection not in BLOCKED:
        BLOCKED.append(intersection)

def compute_bfs_path(position, destination):
    graph = build_graph(ROWS, COLS, BLOCKED)
    ...   # the function body


add_blocked((1, 1))
path = compute_bfs_path((0, 0), (3, 3))
```

```python
class BFS:
    def __init__(self, rows=4, cols=4):
        self.rows = rows
        self.cols = cols
        self.blocked = []

    def add_blocked(self, intersection):
        if intersection not in self.blocked:
            self.blocked.append(intersection)

    def compute_path(self, position, destination):
        graph = build_graph(self.rows, self.cols, self.blocked)
        ...   # the function body, unchanged

planner = BFS()
planner.add_blocked((1, 1))
path = planner.compute_path((0, 0), (3, 3))
```

</SideBySide>

The same four changes as every extension so far: the functions move inside
`class BFS:` and gain `self`; the shared variables move into `__init__` as
`self.rows`, `self.cols`, `self.blocked`; inside the methods they gain `self.`;
from outside, calls go through the object.

`Manhattan` gets the matching shape, with an `add_blocked()` that deliberately does
nothing:

```python
class Manhattan:
    def __init__(self):
        pass        # no setup -- it is a class only to match BFS

    def add_blocked(self, intersection):
        # Manhattan cannot route around obstacles. This exists so every
        # planner can be tested the same way. It deliberately does nothing.
        pass

    def compute_path(self, position, destination):
        ...   # compute_manhattan_path, unchanged
```

Why give `Manhattan` a method that does nothing? Because next lesson's harness calls
`planner.add_blocked(...)` on whatever planner it's handed. If `Manhattan` didn't
have one, the harness would need to know which planner it had — and the whole point
of the swap is that it doesn't.

`lesson-05-bfs-class-addon.py` runs the wall test against both objects. `BFS` goes
around; `Manhattan` drives straight through — the same calls, different objects.

## Wrap-up

- Which line is "take the oldest one"? (`to_visit.pop(0)`.) What would `pop()` do? (Newest first — depth-first, not shortest.)
- Which line is "numbered once"? (`if neighbor not in previous`.)
- Why does the walk-back stop at `position`? (So the start is never appended — Rule 2.)
- Two cases return `[]`. What are they? (Already there; walled off.)
