In Lesson 5-7 the robot detected one obstacle and re-planned once, then the loop
stopped with a `break`. Two things are missing. First, the robot should *keep going*:
follow the new path, and if it finds another wall, re-plan again, until it arrives.
Second, it rediscovers every obstacle from scratch each run — like being surprised
by the same construction zone every morning. This lesson fixes both: a function that
re-plans until arrival, and a way to start Run 2 knowing what Run 1 found out.

- Compare Run 1 and Run 2 with metrics (steps, reroutes)

## From `break` to "until you arrive"

Lesson 5-7's loop broke out as soon as it re-planned. Put that whole `for` loop inside a
`while`, and have the `while` end only when the `for` loop ran all the way through
without a reroute. That is the outline above.

Read the shape, not the lines: **plan, follow, and if something got in the way, plan
again from here.** The inner `for` is Lesson 5-7 unchanged, except that the re-plan
happens at the top of the `while` instead of inside the `if` — the `break` only has
to get out of the `for`. The `rerouted` flag is how the `while` finds out whether the
`for` finished or broke out early: set it `False` before the `for`, set it `True` in
the obstacle branch, and after the `for`, "not rerouted" means "drove the whole path"
— which means arrived. And the function returns the robot's new `position` and
`heading`, because the caller will need them to plan the *next* trip — Lesson 5-9
strings several of these together.

Two of the parameters look odd: `rangefinder` and `obstacle_cm` are already in the
file as a global and a setting. Passing them in means the function *says* what it
depends on — read the `def` line and you know it needs a sensor and a cutoff — and a
test can hand in a different cutoff without editing the function. (The simulated
sensor is a function of `next_pos`, not an object with a `distance()` method, so for
the dry run you swap the one look-ahead line, as in Lesson 5-7.)

The empty-path check matters now in a way it didn't on paper. If the robot gets
boxed in, `compute_bfs_path()` returns `[]` (Lesson 5-5). Without the check, the
`for` loop would run zero times, `rerouted` would stay `False`, and the robot would
declare itself arrived at the wrong intersection.

## Why memory matters

The BFS planner doesn't change between runs. The driving functions don't change. Only
the **input** changes — the blocked list starts with more information:

```
Run 1: empty blocked list  -> discover obstacles the hard way -> many reroutes
Run 2: pre-loaded list     -> plan around known obstacles      -> few or no reroutes
```

**Better data leads to better performance.** The robot isn't running a smarter algorithm on
Run 2 — it's running the *same* algorithm on better information.

<Reveal title="Check your navigate_with_detection()" hint="dry run first, then boxes">

```python
def navigate_with_detection(position, heading, destination, rangefinder, obstacle_cm):
    """Drive from position (facing heading) to destination,
    re-planning around every obstacle the rangefinder finds;
    return (position, heading, step_count, reroute_count)."""
    step_count = 0
    reroute_count = 0

    arrived = False
    while not arrived:
        path = compute_bfs_path(position, destination)
        print("  Path from", position, ":", path)

        if len(path) == 0:
            print("No path to", destination, "!")
            return position, heading, step_count, reroute_count

        rerouted = False
        for next_pos in path:
            needed = desired_heading(position, next_pos)
            heading = turn_to(heading, needed)

            distance = rangefinder.distance()          # look before driving
            if distance < obstacle_cm:
                add_blocked(next_pos)
                print("  OBSTACLE at", next_pos, "! Rerouting...")
                reroute_count = reroute_count + 1
                rerouted = True
                break
            else:
                track_to_intersection()
                drive_past_intersection()
                position = next_pos
                step_count = step_count + 1

        if not rerouted:
            arrived = True

    return position, heading, step_count, reroute_count
```

## Activity · Carry what you learned into the next run

Within one program run, `BLOCKED` persists between function calls — that's why the
`while` loop above works. But close the program and it's gone; Python variables don't
survive a restart. So how does Run 2 begin already knowing what Run 1 found out?

You tell it. Your test already prints the list at the end of the run:

```text
All known obstacles: [(1, 2), (2, 2), (3, 0)]
```

Type that list into `KNOWN_OBSTACLES` at the top of the Lesson 5-8 part of the file,
and the first two lines of your test hand each intersection to the planner the same
way everything else reaches it:

```python
KNOWN_OBSTACLES = [(1, 2), (2, 2), (3, 0)]      # what Run 1 discovered
```

Run it again. The robot plans around all three from its very first path and never
reroutes for them — and if it finds a fourth, the printed list at the end has four
entries, ready to carry across to Run 3.

That's the whole lesson in two lines of typing: **you are the memory.** The robot
found the obstacles, you carried them from one run to the next, and the algorithm
never changed. Notice too that the planner has now been told about walls three
different ways — by a test in 5-6, by the rangefinder in 5-7, and by you here —
and every one of them was a call to `add_blocked()`. A real system would write the
list somewhere and read it back itself rather than waiting for a person, but *what*
gets carried across, and what it's worth, is exactly what you just did by hand.

## Could Run 2 still find new obstacles?

Yes. Run 2 avoids everything it *already* knows, but its smarter route may pass
intersections Run 1 never visited — and one of those could be blocked. So Run 2 can
still discover something new, and Run 3 would start with even more knowledge.
Eventually the robot knows every relevant obstacle and its paths are right from the
start — that's **convergence**.

## Wrap-up

- What turns Lesson 5-7's single reroute into "drive until you arrive"? (A `while not arrived` loop around the `for`, with a `rerouted` flag.)
- What actually changes between Run 1 and Run 2? (The data — the blocked list — not the algorithm.)
- How do you show Run 2 is better? (Measure steps and reroutes.)
- What has to happen between runs for the robot to keep what it learned? (The list has to be handed back to `add_blocked()` — a variable doesn't survive the program ending.)

<TeacherNote title="The Waze analogy lands; make Run 1 vs Run 2 dramatic">

Spend the first fifteen minutes on the `while` loop — trace the outline on the board
with a path that hits one wall, so students see the `for` break, `rerouted` go `True`,
and the `while` plan again from the new position. The `rerouted` flag is the only new
Python idea in the lesson, which is why the outline spells the loop out: the shape
is the lesson, the typing is theirs.

Then frame memory with Waze — students get it instantly ("what if Waze forgot every
traffic report when you closed the app?"). Set up the grid so Run 1 has 2–3 reroutes;
the contrast with a zero-reroute Run 2 is the "aha." The dry run in step 1 proves the
loop with Lesson 5-7's `simulate_rangefinder()` before any box goes on the grid.
Insist on recorded numbers — steps, reroutes — the quantitative comparison convinces
far more than "it felt faster."

**Carrying the list by hand is the point, not a shortcut.** Typing Run 1's discoveries
into `KNOWN_OBSTACLES` makes the "same algorithm, better data" claim something
students do with their own fingers, and it keeps the lesson about navigation instead
of about file formats. If someone asks why the robot can't save it itself — good
question, that is exactly what a real one does, and it changes nothing about *what*
is carried. Be honest about limits: what if an obstacle *moves*? Real systems need to
forget stale data, not just accumulate — good discussion for advanced students.
Connect lightly to machine learning: accumulate data, make better decisions.

</TeacherNote>
