## Two right answers, one test

Compare your Lesson 5-5 Test 1 path with a classmate's. If they're different, good.
If not, here's another correct one:

```python
[(1, 0), (2, 0), (3, 0), (3, 1), (3, 2), (3, 3)]   # yours, maybe
[(0, 1), (0, 2), (0, 3), (1, 3), (2, 3), (3, 3)]   # also six steps, also right
```

Now here's the test from Module 4's Lesson 4-6:

```python
if actual_path == expected_path:
    print("PASS")
```

One of those two correct paths gets marked FAIL. Module 4's test was fine, because
Manhattan has exactly one answer. BFS doesn't. We need a different kind of test.

## Test what must be true

Forget the exact list. What has to be true of *any* correct path from `(0, 0)` to
`(3, 3)`? Five things:

1. The first step is next to the start.
2. The last step is the destination.
3. Every step is next to the one before it.
4. No step is a blocked intersection.
5. With nothing blocked, the number of steps is the Manhattan distance.

Five one-line checks. Together they're *stricter* than an exact match — an exact
match can't tell you a path is valid, only that it's the one you expected — and they
allow every correct answer. That's a **property test**: check what must be true,
not what you happened to expect.

<KnowledgeCheck
  question="Why are the five property checks stronger than comparing with one expected path?"
  options={[
    {text: 'They check that a path is valid, and they accept every correct answer instead of just one', correct: true},

    {text: 'They do not need to know the destination'},
    {text: 'They are not stronger — an exact match is always better'},

## Activity · Build the harness

Open `lesson-06-testing.py`. The two planners and the test runner are given; the
checks are yours to write.

### Step 1 · Two helpers

```python
def manhattan_distance(a, b):
    return abs(a[0] - b[0]) + abs(a[1] - b[1])

def is_neighbor(a, b):
    return manhattan_distance(a, b) == 1
```

### Step 2 · `check_path()` returns a list of problems

One `if` per property. An empty list means the path is good:

```python
def check_path(path, position, destination):
    problems = []
    if len(path) == 0:
        if position != destination:
            problems.append("empty path, but the robot is not at the destination")
        return problems
    if not is_neighbor(position, path[0]):
        problems.append("first step " + str(path[0]) + " is not next to the start " + str(position))
    if path[-1] != destination:
        problems.append("last step " + str(path[-1]) + " is not the destination " + str(destination))
    for i in range(1, len(path)):
        if not is_neighbor(path[i - 1], path[i]):
            problems.append("step " + str(path[i]) + " is not next to " + str(path[i - 1]))
    for step in path:
        if step in BLOCKED:
            problems.append("drives through blocked intersection " + str(step))
    return problems
```

Returning *problems* rather than True/False is deliberate. A test that says only
FAIL is a test you'll ignore; "drives through blocked intersection (1, 0)" tells you
what to fix. The fifth property, the step count, is checked by `run_test()`, which
is given the expected count by the caller.

One case this function can't judge: an empty path when the destination is walled
off is *correct*, but `check_path` can't tell "walled off" from "forgot to look."
So the walled-off case gets its own small test, `run_no_path_test()`, where the only
right answer is `[]`.

### Step 3 · Hand the harness its planner

Here's the one new Python idea in the lesson:

```python
def run_test(test_name, planner, position, destination, expected_steps):
    path = planner(position, destination)
    ...

run_all_tests("Manhattan", compute_manhattan_path)
run_all_tests("BFS", compute_bfs_path)
```

Look at the last two lines. `compute_bfs_path` — no parentheses — is the function
*itself*, handed to `run_all_tests` the way you'd hand it a number or a list. Inside
`run_test`, `planner` holds that function, and `planner(position, destination)`
calls whichever one was handed in. Both planners have the same shape, so the harness
never needs to know which one it has.

Try it at the prompt before writing the harness: `f = compute_bfs_path`, then
`f((0, 0), (3, 3))`.

<Callout kind="tip" title="No parentheses when you hand it over">
`run_all_tests("BFS", compute_bfs_path)` passes the function. `run_all_tests("BFS",
compute_bfs_path())` *calls* it first, with no arguments, and passes the result —
an error. The parentheses are the difference between "here is the planner" and
"here is what the planner said."
</Callout>

## Activity · Run it against both

Run the harness. BFS should pass 6 of 6. Then read Manhattan's lines carefully:

```text
========== Manhattan ==========
  PASS  open (0, 0) to (3, 3)  [(1, 0), (2, 0), (3, 0), (3, 1), (3, 2), (3, 3)]
  PASS  open (0, 0) to (0, 3)  [(0, 1), (0, 2), (0, 3)]
  PASS  open (2, 1) to (0, 3)  [(1, 1), (0, 1), (0, 2), (0, 3)]
  PASS  open (1, 1) to (1, 1)  []
  FAIL  wall at (1,0),(1,1): (0,0) to (3,0)  [(1, 0), (2, 0), (3, 0)]
          - drives through blocked intersection (1, 0)
          - expected 7 steps, got 3
  FAIL  walled off: (0,0) to (3,0)  [(1, 0), (2, 0), (3, 0)]
          - there is no way through, so the path should be empty
Manhattan: 4 of 6 passed
```

Manhattan isn't broken. It's doing exactly what it was built to do in Module 4 —
rows, then columns — and it has no idea what a wall is. The harness just showed,
on paper, with the path printed, why this module exists.

Then the same swap in a main program. Block `(2, 0)` and run two trips with each
planner. The only thing that changes between the two blocks of code is the
planner's name:

```python
def navigate(planner, position, destination):
    path = planner(position, destination)
    print("  Path from", position, "to", destination, ":", path, " Steps:", len(path))
    return destination       # where the robot would be after driving it

position = navigate(compute_manhattan_path, (0, 0), (3, 3))   # through the wall
position = navigate(compute_bfs_path, (0, 0), (3, 3))         # around it
```

Finally, break a property on purpose and watch the harness catch it: make
`compute_bfs_path` return `path[1:]` (drop the first step), then `path + [destination]`.
Which property catches each?

<TeacherNote title="Answers, and the two things to listen for">

Dropping the first step: property 1, "first step (2, 0) is not next to the start
(0, 0)". Appending the destination again: property 3, "step (3, 3) is not next to
(3, 3)" — an intersection isn't its own neighbor — plus the step count.

Listen for two things. First, the parentheses slip in the `run_all_tests` call;
the prompt demo (`f = compute_bfs_path`) prevents most of it. Second, let students
*discover* Manhattan's FAIL lines by running it, rather than telling them in
advance. "Run it against Manhattan and read what it says" lands harder than any
explanation. Challenge for early finishers: add a sixth property, "no intersection
appears twice." Can BFS ever fail it? Could a buggy planner?

The property-versus-exact lesson generalizes far beyond this course; say so.

</TeacherNote>

<OptionalExtension title="The harness with planner objects">

With the `BFS` and `Manhattan` classes from Lesson 5-5, the harness is handed an
*object* instead of a function, and calls its methods. Everything else is identical:

<SideBySide left="Functions — what you have" right="Class — the extension">

```python
run_all_tests("Manhattan", compute_manhattan_path)
run_all_tests("BFS", compute_bfs_path)

# inside the harness:
path = planner(position, destination)
add_blocked((1, 0))
clear_blocked()
```

```python
run_all_tests("Manhattan", Manhattan())
run_all_tests("BFS", BFS())

# inside the harness:
path = planner.compute_path(position, destination)
planner.add_blocked((1, 0))
planner.clear_blocked()
```

</SideBySide>

Because both classes have `add_blocked()`, `clear_blocked()` and `compute_path()`,
the harness never needs to know which one it holds. `Manhattan.add_blocked()` does
nothing, so `Manhattan()` fails the same two tests for the same reason — which is
the correct result.

One wrinkle: property 4 needs to know what's blocked, and with objects the blocked
list lives *inside* the planner. The class harness in
`lesson-06-testing-class-addon.py` keeps its own small record — `block(planner, x)`
calls `planner.add_blocked(x)` and notes it — so the check stays honest. Why not just
read `planner.blocked` directly? `Manhattan` has no such attribute, and the harness
isn't supposed to know what's inside a planner.

<KnowledgeCheck
  question="With planner objects, why does the harness keep its own record of what it blocked instead of reading planner.blocked?"
  options={[
    {text: 'The harness is not supposed to know what is inside a planner — and Manhattan has no blocked list at all', correct: true},
    {text: 'Objects cannot have lists'},
    {text: 'planner.blocked is always empty'},
    {text: 'It does read planner.blocked — the text is wrong'},
  ]}
  explanation="The whole point of the swap is that the harness only uses the three shared methods. Reaching inside one planner would tie the harness to that planner."

## Real-world connections

<CardGrid>
  <InfoCard tag="Software" title="Property-based testing">
    Professional test tools generate thousands of random inputs and check properties, exactly as this harness checks paths — because for most real programs there is no single expected answer.
  </InfoCard>
  <InfoCard tag="Design" title="Plug-in parts">
    Handing a function (or object) to code that doesn't know which one it got is how programs are built from swappable parts: sort orders, file formats, planners.
  </InfoCard>
  <InfoCard tag="Robotics" title="Test before you drive">
    Everything the harness checks here is checked without a robot. Real robot teams test the planner on a laptop for the same reason: it's faster, and it separates "the algorithm is wrong" from "the robot drove wrong."
  </InfoCard>
</CardGrid>

## Wrap-up

- Why not compare with one expected path? (BFS has many correct answers; the properties allow all of them and check validity.)
- What are the five properties? (Starts next to the start; ends at the destination; every step a neighbor; no blocked step; Manhattan-distance length on an open grid.)
- Why does walled-off get its own test? (`check_path` can't tell it from a broken planner's `[]`.)
- What's passed in `run_all_tests("BFS", compute_bfs_path)`? (The function itself.)
