## Two right answers, one test

Compare your Lesson 5-5 Test 1 path with a classmate's. If they're different, good.
If not, here's another correct one:

```python
[(1, 0), (2, 0), (3, 0), (3, 1), (3, 2), (3, 3)]   # yours, maybe
[(0, 1), (0, 2), (0, 3), (1, 3), (2, 3), (3, 3)]   # also six steps, also right
```

Now here's the test from Module 4's Lesson 4-6, still in your file as `run_test()`:

```python
if actual == expected:
    print(test_name, "- PASS")
```

One of those two correct paths gets marked FAIL. Module 4's test was fine, because
Manhattan has exactly one answer. BFS doesn't. We need a different kind of test —
and because it *is* a different kind, it gets a different name. `run_test()` stays in
the MANHATTAN PLANNER section, doing the job it was written for.

## Test what must be true

Forget the exact list. What has to be true of *any* correct path from `(0, 0)` to
`(3, 3)`? Five things:

1. The first step is next to the start.
2. The last step is the destination.
3. Every step is next to the one before it.
4. No step is a blocked intersection.
5. With nothing blocked, the number of steps is the Manhattan distance.

Five one-line checks. Together they're *stricter* than an exact match — an exact
match can't tell you a path is valid, only that it's the one you expected — and they
allow every correct answer. That's a **property test**: check what must be true,
not what you happened to expect.

## Activity · Build the harness

### Step 1 · Two helpers

`manhattan_distance()` is the Lesson 4-2 formula — the x difference plus the
y difference, each made positive with `abs()`. `is_neighbor()` asks whether
that distance is exactly 1. Write both.

### Step 2 · `check_path()` returns a list of problems

One `if` per property, each appending a sentence to `problems` when it fails. An
empty list means the path is good. The outline's first line is the special case: an
empty path is correct when `position == destination` and a problem otherwise, and
either way there are no steps to check, so return at once.

Make the sentences specific. Returning *problems* rather than True/False is
deliberate. A test that says only FAIL is a test you'll ignore;
`"drives through blocked intersection (1, 0)"` tells you what to fix. Build each
sentence with `+` and `str()`: property 1's is `"first step " + str(path[0]) + " is not
next to the start " + str(position)`, and the others follow the same pattern — name
the step, say what's wrong with it. Property 3 is a loop from the second step to the
last, comparing each with the one before; property 4 is a loop over every step.

The fifth property, the step count, is checked by `run_path_test()`, which is given
the expected count by the caller.

One case this function can't judge: an empty path when the destination is walled
off is *correct*, but `check_path` can't tell "walled off" from "forgot to look."
So the walled-off case gets its own small test, `run_no_path_test()`, where the only
right answer is `[]`.

Here's the one new Python idea in the lesson. Look at `run_path_test()`'s first
parameter and the test you're about to write:


Look at the last two lines. `compute_bfs_path` — no parentheses — is the function
*itself*, handed to `run_all_tests` the way you'd hand it a number or a list. It
passes it straight on to `run_path_test`, where `planner` holds that function, and
`planner(position, destination)` calls whichever one was handed in. Both planners
have the same shape, so the harness never needs to know which one it has.

```python
def manhattan_distance(a, b):
    """Steps between a and b with nothing in the way."""
    return abs(a[0] - b[0]) + abs(a[1] - b[1])

def is_neighbor(a, b):
    """True when a and b are one step apart."""
    return manhattan_distance(a, b) == 1

def check_path(path, position, destination):
    """Return a list of everything wrong with path as a route
    from position to destination; [] means it is good."""
    problems = []
    if len(path) == 0:
        if position != destination:
            problems.append("empty path, but the robot is not at the destination")
        return problems
    if not is_neighbor(position, path[0]):
        problems.append("first step " + str(path[0]) + " is not next to the start " + str(position))
    if path[-1] != destination:
        problems.append("last step " + str(path[-1]) + " is not the destination " + str(destination))
    for i in range(1, len(path)):
        if not is_neighbor(path[i - 1], path[i]):
            problems.append("step " + str(path[i]) + " is not next to " + str(path[i - 1]))
    for step in path:
        if step in BLOCKED:
            problems.append("drives through blocked intersection " + str(step))
    return problems

def run_path_test(test_name, planner, position, destination, expected_steps):
    """Ask planner for a path, check the five properties, print
    PASS or FAIL with the path; return True on a pass."""
    path = planner(position, destination)
    problems = check_path(path, position, destination)
    if len(path) != expected_steps:
        problems.append("expected " + str(expected_steps) + " steps, got " + str(len(path)))
    if len(problems) == 0:
        print("  PASS ", test_name, "", path)
        return True
    print("  FAIL ", test_name, "", path)
    for problem in problems:
        print("          -", problem)
    return False

def run_no_path_test(test_name, planner, position, destination):
    """For a walled-off destination the only right answer is
    []; print PASS or FAIL and return True on a pass."""
    path = planner(position, destination)
    if len(path) == 0:
        print("  PASS ", test_name, "", path)
        return True
    print("  FAIL ", test_name, "", path)
    print("          - there is no way through, so the path should be empty")
    return False
```

`path[-1]` is the last element — a negative index counts from the end. If your
sentences are worded differently, fine; what matters is that each one names the
step that broke the property.

Because both classes have `add_blocked()`, `clear_blocked()` and `compute_path()`,
the harness never needs to know which one it holds. `Manhattan.add_blocked()` does
nothing, so `Manhattan()` fails the same two tests for the same reason — which is
the correct result.

One wrinkle: property 4 needs to know what's blocked, and with objects the blocked
list lives *inside* the planner. So the class-track harness keeps its own small
record. This is the skeleton; paste it at the top of the Lesson 5-6 part of the
file, above `manhattan_distance()`:

```python
# class track: the harness's own record of what it blocked
HARNESS_BLOCKED = []

def block(planner, intersection):
    """Tell planner about intersection AND note it in
    HARNESS_BLOCKED, so check_path() can see it."""
    pass

def clear(planner):
    """Tell planner to forget its blocks, and forget ours."""
    pass
```

Then the four edits: `run_path_test()` and `run_no_path_test()` call
`planner.compute_path(position, destination)`; `run_all_tests()` calls
`block(planner, ...)` where it called `add_blocked(...)` and `clear(planner)` where it
called `clear_blocked()`; and `check_path()`'s property 4 reads `HARNESS_BLOCKED`.
`test_harness()` hands in `Manhattan()` and `BFS()`.

Why not just read `planner.blocked` directly? `Manhattan` has no such attribute, and
the harness isn't supposed to know what's inside a planner. `test_swap()` gets the
same treatment: `navigate()` calls `planner.compute_path(...)`, and the test hands it
`Manhattan()` and your `planner`. The file is `lesson-06-testing-class-addon.py` in the
Module 5 solutions.

```python
def block(planner, intersection):
    """Tell planner about intersection AND note it in
    HARNESS_BLOCKED, so check_path() can see it."""
    planner.add_blocked(intersection)
    if intersection not in HARNESS_BLOCKED:
        HARNESS_BLOCKED.append(intersection)

def clear(planner):
    """Tell planner to forget its blocks, and forget ours."""
    planner.clear_blocked()
    while len(HARNESS_BLOCKED) > 0:
        HARNESS_BLOCKED.pop()
```
