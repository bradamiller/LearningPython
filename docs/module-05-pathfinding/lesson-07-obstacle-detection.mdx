## The robot gets eyes

The rangefinder sends out a sound pulse, too high for us to hear, and times the echo.
The round-trip time gives the distance to an object, in centimeters. Reading it takes
three lines:

```python
from XRPLib.rangefinder import Rangefinder

rangefinder = Rangefinder.get_default_rangefinder()
distance = rangefinder.distance()      # float, in cm
```

The first two lines go in the **start block** at the top of `robot.py`: the import
under the other `XRPLib` imports, the object under `board = ...`. Then every function
can use `rangefinder` the way it uses `drivetrain`.

## Choosing a threshold

Readings are noisy: they vary a little each time. So don't check for an exact distance;
use a **threshold**. Measure with the next intersection blocked (say ~12 cm) and clear
(say ~50 cm), then pick a cutoff between them:

```python
if distance < OBSTACLE_CM:
    print("OBSTACLE DETECTED")
else:
    print("Path is clear")
```

It's `OBSTACLE_CM`, not `THRESHOLD`, because the file already has a reflectance
`THRESHOLD` from Lesson 2-2. Two settings with one name is a bug waiting to happen.

<KnowledgeCheck

  explanation="Readings vary with angle, surface and noise. A threshold ('closer than 15 cm = blocked') absorbs that; an exact match would fail constantly."

## Which intersection is blocked?

A short reading means something is ahead, but *which* intersection? The one directly in
front of the robot, and the loop already knows it. Look at Module 4's `drive_path()`
loop:

```python
for next_pos in path:
    desired_heading = get_desired_heading(current_position, next_pos)
    current_heading = turn_to(current_heading, desired_heading)
    track_to_intersection()
    current_position = next_pos
```

After `turn_to()`, the robot is facing `next_pos`. So a short reading right then means
`next_pos` is blocked. The path already told you.

## The loop: Module 4's, plus one check

Today's driving test is `drive_path()`'s loop with one step added between turning and
driving: look ahead. Write it as `test_detect_once()` under the skeleton:

```python
def test_detect_once():
    # robot at (0, 0) facing North; destination (3, 3)
    # plan the path, print it, wait for the button
    # for each next_pos in path:
    #     face it: get_desired_heading(), then turn_to()
    #     NEW: look ahead -- distance = simulate_rangefinder(
    #          next_pos) for now; rangefinder.distance() later
    #     print current_position, HEADING_NAMES[current_heading], the distance
    #     if distance < OBSTACLE_CM:
    #         tell the planner: add_blocked(next_pos); say so
    #         new path from HERE: compute_bfs_path(current_position,
    #             destination); print it; then break
    #     else:
    #         arrive: track_to_intersection();
    #         current_position = next_pos
    # print the blocked list
    pass
```

And the new branch, the one piece that isn't Module 4's `drive_path()`:

```python
        if distance < OBSTACLE_CM:
            add_blocked(next_pos)
            print("Obstacle at", next_pos, "! Rerouting...")
            path = compute_bfs_path(current_position, destination)
            print("New path:", path)
            break      # Lesson 5-8 keeps going instead
```

Three things to notice.

- **`add_blocked(next_pos)` is the same call your Lesson 5-6 harness made.** The
  planner can't tell a sensor from a test script, so passing those tests means the robot
  will re-plan correctly.
- **Re-planning is one line, from where the robot is:** `compute_bfs_path(current_position,
  destination)`, Rule 1 from Lesson 5-4. The planner rebuilds its graph from `BLOCKED`
  every call, so there is no "rebuild the graph" step to forget.
- **The robot is parked when it re-plans.** Every track ends with its center on the
  cross, so it is still on the intersection it re-planned from.

The `break` ends the loop once a new path is planned: today the robot re-plans once and
stops. Lesson 5-8 replaces it with "follow the new path until you arrive."

If you built the `LineTrack` or `Navigator` class, the driving calls in the outline
are `tracker.` or `navigator.line_track.` calls, as in Lesson 4-6, and the planner
calls are `planner.add_blocked()` and `planner.compute_path()`.

## Print the plan before the button

The outline starts with a new habit: plan and *print* the path, then wait for the button
before the robot moves.

```python
    path = compute_bfs_path(position, destination)
    print("Planned path:", path)

    board.wait_for_button()
```

Read the path before you press. If it's right and the robot still goes wrong, the bug
is in the driving, not the planner. That makes two presses per driving test: the one in
`RUN` prints the plan, the one in the test is *go*.

## Activity · Read, simulate, then drive

### Step 1 · The sensor

1. Add the import and the object to the start block.
2. Write `test_rangefinder()`: print `rangefinder.distance()` fifty times, a tenth of a
   second apart, as `test_sensors()` did in Lesson 2-1. Set the run line to it.
3. Hold an obstacle in front of the robot at the distance of the next intersection, then take
   it away. Write both readings down.
4. Check that `OBSTACLE_CM` sits between them; change it if not.

### Step 2 · Simulate the sensor

1. Write `simulate_rangefinder()`, one line: `8.0` if `next_pos` is in
   `SIMULATED_OBSTACLES`, otherwise `50.0`.
2. Write `test_detect_once()` from the outline, with the simulated sensor in the
   look-ahead line.
3. Put the robot at `(0, 0)` facing North on an *empty* grid and set the run line to it.
   Before the second press, check that `(2, 0)` is on the planned path.
4. It should face East, drive to `(1, 0)`, face `(2, 0)`, "see" the pretend obstacle, print the
   new path, and stop. Check that the blocked list has grown and the new path goes around.

Only the sensor is simulated; the planner was already tested in Lesson 5-6. So a wrong
reroute here is a code bug, not a hardware bug.

### Step 3 · The real sensor

Change the look-ahead line to `rangefinder.distance()`. Put an obstacle on the printed path
(`(2, 0)` again works) and press the button. The robot should stop, print
"Rerouting..." and the new path, and stop. Taking the new path is next lesson.

<Reveal title="Check your test" hint="run it with the simulated sensor first">

```python
def simulate_rangefinder(next_pos):
    """Stand-in for rangefinder.distance(): 8.0 if next_pos is
    in SIMULATED_OBSTACLES, otherwise 50.0."""
    return 8.0 if next_pos in SIMULATED_OBSTACLES else 50.0

def test_detect_once():
    current_position = (0, 0)
    current_heading = 0
    destination = (3, 3)

    path = compute_bfs_path(current_position, destination)
    print("Planned path:", path)
    board.wait_for_button()

    for next_pos in path:
        desired_heading = get_desired_heading(current_position, next_pos)
        current_heading = turn_to(current_heading, desired_heading)

        distance = simulate_rangefinder(next_pos)     # rangefinder.distance() on the robot
        print("At", current_position, "facing", HEADING_NAMES[current_heading], "- ahead:", distance, "cm")

        if distance < OBSTACLE_CM:
            add_blocked(next_pos)
            print("Obstacle at", next_pos, "! Rerouting...")
            path = compute_bfs_path(current_position, destination)
            print("New path:", path)
            break      # Lesson 5-8 keeps going instead
        else:
            track_to_intersection()
            current_position = next_pos
            print("Drove to", current_position)
    print("All known obstacles:", BLOCKED)
```

`8.0 if ... else 50.0` is a one-line `if` that picks one of two values. A four-line
`if`/`else` with two `return`s works the same.

</Reveal>

def test_rangefinder():

## Wrap-up

- What three lines read the rangefinder? (Import, `get_default_rangefinder()`, `.distance()`.)
- Which intersection does an obstacle reading refer to? (`next_pos`: the robot just turned to face it.)
- What is the one line that tells the planner? (`add_blocked(next_pos)`, the same one the tests used.)
- Why no "rebuild the graph" step? (The planner rebuilds from `BLOCKED` on every call.)

<TeacherNote title="Calibrate the threshold ahead of class; simulate before hardware">

The right threshold depends on grid spacing, obstacle material and the sensor — test
it yourself and have a value ready. Expect variability: soft or angled surfaces read
inconsistently, which is a good real-world-sensor talking point. "Which intersection
is blocked" used to confuse students when it was computed from the heading;
demonstrate the new reasoning physically — stand on an intersection, turn to face the
next one on the path, point at it. Have everyone run the simulated-rangefinder
version of `test_detect_once()` (step 2) before touching an obstacle: the robot still
drives, but the obstacle is pretend, so a wrong reroute is a logic bug and nothing
else. Place real obstacles *on* the printed path so the reroute is visible and
dramatic.

**Hardware note:** the driving functions are Module 4's, unchanged — turns end on a
sensor, and `track_to_intersection()` parks the robot's center on each intersection. If
the robot overshoots or misses a turn here, it did in Module 4 too; tune there.

</TeacherNote>
