## The robot gets eyes

The ultrasonic rangefinder sends out a sound pulse — too high for us to hear — and times
the echo bouncing back. The round-trip time tells it how far away an object is, returned in
centimeters. Reading it takes three lines:

```python
from XRPLib.rangefinder import Rangefinder

rangefinder = Rangefinder.get_default_rangefinder()
distance = rangefinder.distance()      # float, in cm
```

The sensor does the physics internally; you just read a number. The first two lines
go in the **start block** at the top of `robot.py` — the import under the other
`XRPLib` imports, the object under `board = ...` — so that every function below can
use `rangefinder` the way they use `drivetrain`. It is the first new object in the
start block since Lesson 2-1 (the only other change was `import random` in 2-4).

## Choosing a threshold

Sensor readings have noise and vary a little each time, so you don't check for an exact
distance — you use a **threshold**. Measure with the next intersection blocked (say ~12
cm) and clear (say ~50 cm), then pick a cutoff between them:

```python
if distance < OBSTACLE_CM:
    print("OBSTACLE DETECTED")
else:
    print("Path is clear")
```

It's named `OBSTACLE_CM`, not `THRESHOLD`, because the file already has a
`THRESHOLD` — the reflectance one from Lesson 2-2 — and two settings with the same
name is a bug waiting to happen.

<KnowledgeCheck

  options={[

  explanation="Ultrasonic readings fluctuate with angle, surface, and noise. A threshold ('closer than 15 cm = blocked') absorbs that variation; an exact-match check would fail constantly."

## Which intersection is blocked?

The rangefinder says something is ahead — but *which* intersection? It's the one
directly in front of the robot. And here's the nice part: you already know which
one that is, without any new code. Look at Module 4's `drive_path()` loop:

```python
for next_pos in path:
    needed = desired_heading(position, next_pos)
    heading = turn_to(heading, needed)
    track_to_intersection()
    drive_past_intersection()
    position = next_pos
```

After `turn_to()`, the robot is facing `next_pos` — that's what turning to the needed
heading *means*. So if the rangefinder sees something right then, the blocked
intersection is `next_pos`. The path already told you.

## The loop: Module 4's, plus one check

Today's driving test is `drive_path()`'s loop with exactly one step added, between
turning and driving: look ahead. Here is its outline — write it as `test_detect_once()`
under the skeleton:

```python
def test_detect_once():
    # robot at (0, 0) facing North; destination (3, 3)
    # plan the path, print it, wait for the button
    # for each next_pos in path:
    #     face it: desired_heading(), then turn_to()
    #     NEW: look ahead -- distance = simulate_rangefinder(
    #          next_pos) for now; rangefinder.distance() later
    #     print position, HEADING_NAMES[heading], the distance
    #     if distance < OBSTACLE_CM:
    #         tell the planner: add_blocked(next_pos); say so
    #         new path from HERE: compute_bfs_path(position,
    #             destination); print it; then break
    #     else:
    #         arrive: track_to_intersection(), then
    #         drive_past_intersection(); position = next_pos
    # print the blocked list
    pass
```

And the new branch, the one piece that isn't Lesson 4-8:

```python
        if distance < OBSTACLE_CM:
            add_blocked(next_pos)
            print("Obstacle at", next_pos, "! Rerouting...")
            path = compute_bfs_path(position, destination)
            print("New path:", path)
            break      # Lesson 5-8 keeps going instead
```

Three things to notice.

**`add_blocked(next_pos)` is the same call your Lesson 5-6 harness made.** The planner
can't tell whether an obstacle came from a test script or a sensor. That's why
passing the paper tests means the robot will re-plan correctly: it's the same code,
fed the same way.

**Re-planning is one line, from where the robot is.** `compute_bfs_path(position,
destination)` — Rule 1 from Lesson 5-4. The planner rebuilds its graph from `BLOCKED`
every call, so the wall it was just told about is already gone from it. There is no
"rebuild the graph" step to forget.

**The robot is parked when it re-plans.** `drive_past_intersection()` runs after every
track, so when the loop comes back around to turn toward the new path's first step,
the wheels are still over the intersection it re-planned from. Nothing moves the
robot during a re-plan.

The `break` ends the `for` loop as soon as a new path has been planned, so today the
robot re-plans once and stops. Lesson 5-8 replaces that `break` with "follow the new
path, and keep going until you arrive."

If you built the `LineTrack` or `Navigator` class, the driving calls in the outline
are `tracker.` or `navigator.line_track.` calls, as in Lesson 4-8, and the planner
calls are `planner.add_blocked()` and `planner.compute_path()`.

## Print the plan before the button

The first two lines of the outline are the Lesson 4-8 habit: plan and *print* the
path before the robot moves.

```python
    path = compute_bfs_path(position, destination)
    print("Planned path:", path)

    board.wait_for_button()
```

Read it before you press the button. Is it what you expected? This is the Lesson 5-6
paper test built into every run, and it's your first diagnostic when something goes
wrong: if the printed path is right and the robot still goes wrong, the bug is in the
driving, not the planner. As in Module 4, that makes two presses per driving test:
the one in `RUN` starts the test and prints the plan; the one in the test is *go*.

## Activity · Read, simulate, then drive

### Step 1 · The sensor

Add the import and the object to the start block. Then write a test —
`test_rangefinder()` — that prints `rangefinder.distance()` fifty times, a tenth of
a second apart, the way `test_sensors()` did in Lesson 2-1. Set the run line to it
and hold a box in front of the robot at the distance of the next intersection, then
take it away. Write both readings down and check that `OBSTACLE_CM` sits between
them; change it if not.

### Step 2 · Simulate the sensor

Write `simulate_rangefinder()` — one line: `8.0` if `next_pos` is in
`SIMULATED_OBSTACLES`, otherwise `50.0`. Then write `test_detect_once()` from the
outline with the simulated sensor in the look-ahead line. Put the robot at `(0, 0)`
facing North on an *empty* grid, set the run line to it, and read the planned path
before the second press: `(2, 0)` is on it. The robot should drive to `(1, 0)`, turn
to face `(2, 0)`, "see" the pretend box, print the new path, and stop. Confirm two
things on screen: the blocked list has grown, and the new path goes around.

What's being simulated is only the sensor. The planner needs no simulation, because
it was already tested in Lesson 5-6. Separating software bugs from hardware bugs
saves enormous frustration.

### Step 3 · The real sensor

Change the look-ahead line to `rangefinder.distance()`. Put a box on one intersection
of the printed path — `(2, 0)` again is a good choice — and press the button. Watch the
robot stop, print "Rerouting...", print the new path, and stop. (Taking it is next
lesson.)

```python
def simulate_rangefinder(next_pos):
    """Stand-in for rangefinder.distance(): 8.0 if next_pos is
    in SIMULATED_OBSTACLES, otherwise 50.0."""
    return 8.0 if next_pos in SIMULATED_OBSTACLES else 50.0

def test_detect_once():
    position = (0, 0)
    heading = 0
    destination = (3, 3)

    path = compute_bfs_path(position, destination)
    print("Planned path:", path)
    board.wait_for_button()

    for next_pos in path:
        needed = desired_heading(position, next_pos)
        heading = turn_to(heading, needed)

        distance = simulate_rangefinder(next_pos)     # rangefinder.distance() on the robot
        print("At", position, "facing", HEADING_NAMES[heading], "- ahead:", distance, "cm")

        if distance < OBSTACLE_CM:
            add_blocked(next_pos)
            print("Obstacle at", next_pos, "! Rerouting...")
            path = compute_bfs_path(position, destination)
            print("New path:", path)
            break      # Lesson 5-8 keeps going instead
        else:
            track_to_intersection()
            drive_past_intersection()
            position = next_pos
            print("Drove to", position)
    print("All known obstacles:", BLOCKED)
```

`8.0 if ... else 50.0` is a one-line `if` — an expression that picks one of two
values. A four-line `if`/`else` with two `return`s is the same function.

## Wrap-up

- What three lines read the rangefinder? (Import, `get_default_rangefinder()`, `.distance()`.)
- Which intersection does an obstacle reading refer to? (`next_pos` — the robot just turned to face it.)
- What is the one line that tells the planner? (`add_blocked(next_pos)` — the same one the tests used.)
- Why no "rebuild the graph" step? (The planner rebuilds from `BLOCKED` on every call.)

<TeacherNote title="Calibrate the threshold ahead of class; simulate before hardware">

The right threshold depends on grid spacing, obstacle material and the sensor — test
it yourself and have a value ready. Expect variability: soft or angled surfaces read
inconsistently, which is a good real-world-sensor talking point. "Which intersection
is blocked" used to confuse students when it was computed from the heading;
demonstrate the new reasoning physically — stand on an intersection, turn to face the
next one on the path, point at it. Have everyone run the simulated-rangefinder
version of `test_detect_once()` (step 2) before touching a box: the robot still
drives, but the obstacle is pretend, so a wrong reroute is a logic bug and nothing
else. Place real obstacles *on* the printed path so the reroute is visible and
dramatic.

**Hardware note:** the driving functions are Module 4's, unchanged — turns end on a
sensor, and `drive_past_intersection()` parks the wheels over each intersection. If
the robot overshoots or misses a turn here, it did in Module 4 too; tune there.

</TeacherNote>
