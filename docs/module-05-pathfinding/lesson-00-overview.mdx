Module 4's robot plans its own routes, but always the same way, across and then up, and
it assumes nothing is in the way. Put an obstacle on its route and it drives straight at it.

We'll use small boxes on intersections to represent **obstacles**.

By the end of this module your robot will **visit several destinations on a grid with
obstacles, plan around the ones it knows about, spot new ones with its rangefinder and
re-plan, and do better on its second run**. It's the last required module: everything
you've built works together.

## Three new pieces

The driving doesn't change: your Module 4 NAVIGATOR drives any list of intersections it's
handed. What's new is *which* list it gets.

<CardGrid>
  <InfoCard tag="Map" title="The grid as a graph">
    The grid written so a program can search it: every intersection, what it connects to, and what's blocked.
  </InfoCard>
  <InfoCard tag="Planner" title="Breadth-first search">
    A planner that finds a shortest route around every blocked intersection on the map.
  </InfoCard>
  <InfoCard tag="Senses" title="Obstacle detection">
    The rangefinder checks the next intersection before the robot drives there. If something is there, it goes on the map and the robot plans again.
  </InfoCard>
</CardGrid>

If you write the BFS planner so that it returns its plan as a list of intersections, just
like the Manhattan planner, the rest of your program stays the same.

## The swap

The Manhattan planner and the new one answer **the same request**: where the robot is and
where it should go in, a list of intersections out. The navigator doesn't care which
planner made the list. So once the new planner passes its tests, you swap it in by
**changing one name**, and the route that ran into the obstacle goes around it.

That's the payoff of the decomposition in Lesson 4-0. You fixed what passes between
planner and driver before writing either, so either side can be replaced without touching
the other.

## A robot that learns

Planning around known obstacles is half the job; the other half is finding new ones. The
robot looks ahead before every block. When it finds an obstacle, it marks that intersection
blocked, re-plans from where it stands, and carries on. At the end it reports every obstacle it
found, so the next run starts knowing them: your **Run 2** should beat your **Run 1**.

<TeacherNote title="This is an advance organizer — keep it high-level">

Keep this to the destination and the three pieces. Two things the page deliberately
doesn't do: it doesn't say *how* the planner searches (students invent that themselves
in Lesson 5-1, from "I just looked" to a method a computer can follow), and its figure
uses a different grid from Lesson 5-1's detour activity, so it doesn't give that answer
away either. If students ask how the robot finds the way around, the answer is
"Lessons 5-1 and 5-2, with a pencil, before any code."

**Materials:** the 4 × 4 grid from Modules 3 and 4, and from Lesson 5-7 a few flat,
firm boxes the rangefinder can see, sized to sit on an intersection. Lessons 5-1 to 5-6
never put a robot on the floor (the code runs and prints, but nothing drives), which is
a good stretch to catch up on charging and repairs.

**Pacing:** about four weeks, with the capstone (5-9) running over more than one period.
The course is complete at the end of this module; Module 6 is optional.

</TeacherNote>

## Your roadmap

| Lesson | What happens |
|---|---|
| **5-1 · Finding a Way Around** | Find a way around a blocked intersection by eye, then turn "I just looked" into a method a computer could follow, and trace it with a pencil. No code. |
| **5-2 · The Walk Back** | Turn the pencil method's numbers into the actual route. No code. |
| **5-3 · Pencil to Program** | Write the method as steps, work out what a program must remember for each, and put the grid into Python. The GRID GRAPH section opens. |
| **5-4 · Pathfinding Functions** | Keep a shared list of blocked intersections and build the graph around it. The BFS PLANNER section opens. |
| **5-5 · compute_bfs_path()** | The pencil method, line for line, in Python, tested after every stage. |
| **5-6 · Testing and Swapping** | Test any planner without a robot, then swap Manhattan out by changing one name. |
| **5-7 · Obstacle Detection** | The rangefinder looks before each block; if something is there, plan again. The OBSTACLES section opens. |
| **5-8 · Building Experience** | Keep re-planning until the robot arrives, and start the next run knowing what this one found. |
| **5-9 · Capstone Project** | Several destinations, obstacles found and avoided, and a second run that does better. |

The capstone needs little new code: almost all of it calls sections you've already written
and tested, as in Modules 2, 3 and 4. (Lessons 5-5 and 5-6 also have optional class
versions.)

## Wrap-up

- What will the robot do by the end of the module? (Visit several destinations, plan around known obstacles, find new ones while driving, and improve on its second run.)
- Why can't the Module 4 planner handle an obstacle on its route? (It always plans across then up, and has no idea anything is blocked.)
- What are the three new pieces? (A map of the grid, a planner that searches it, and detection with the rangefinder.)
