You can do breadth-first search with a pencil. To write it as a program, two questions
come first: what are the **steps**, in order, and what does the program have to
**remember** to do each one? Answering them brings in a new way to see the grid, a
**graph**, and a new kind of Python data, the **dictionary**. By the end of the lesson
the grid is in `robot.py`.

<Objectives>

By the end of this lesson you will be able to:

- Write the pencil method as an ordered list of steps, and say what each step needs to know
- Describe the grid as a graph: nodes, edges and neighbors, and what blocking a node removes
- Create a dictionary, look up a value by key, and check for a key with `in`
- Write `build_grid_graph(rows, cols)` in a new GRID GRAPH section of `robot.py`, with a paper test

</Objectives>

## The method, step by step

Here is what you did with a pencil in Lessons 5-1 and 5-2, written as steps in order.
It's plain English, not Python yet:

```text
SETUP
  1. Mark the start as reached (it came from nowhere).
  2. Put the start on the to-visit list.
SEARCH
  3. While the to-visit list is not empty:
       take the OLDEST intersection off the FRONT
       if it is the destination: stop looking
       for each open neighbor of it:
           if that neighbor has not been reached yet:
               write where it came from
               add it to the END of the to-visit list
WALK BACK
  4. If the destination was never reached: there is no path.
  5. Start at the destination and follow came-from back to the start,
     writing each intersection down (but not the start).
  6. Turn that list around. That is the path.
```

One thing is missing on purpose: the ring numbers. You needed them to see *why* the first
path found is shortest, but the program only needs to know whether an intersection has
been reached, and the came-from mark already says that. An intersection with a came-from
entry has a number; one without hasn't been reached.

## What the program has to remember

Go through the steps and ask what each one needs to know. Every answer is something you
kept on paper:

| On paper | The question a step asks | In the program |
|---|---|---|
| The grid drawing, with X's | "Which open intersections are next to this one?" | A **graph**, this lesson |
| The X's themselves | "Which intersections are blocked?" | A list, `BLOCKED` (Lesson 5-4) |
| The came-from column | "Has this one been reached? Where from?" | A **dictionary**, `previous` (Lesson 5-5) |
| The to-visit list | "Which one is next?" | A list: add to the end, take from the front (Lesson 5-5) |

Two of these are lists, which you know from Module 4. The other two are looked up **by
intersection**: you have `(1, 2)` and want its neighbors, or where it came from. A list
finds things by *position* (`path[0]`), not by what they are. That needs something new.
First, though, the program needs the grid written down precisely.

## The grid as a graph

The step "for each open neighbor" needs to know exactly which intersections are joined.
Computer scientists write that down as a **graph**: a set of **nodes** (points) connected
by **edges** (links). A road map is one (intersections and streets), so is a social
network (people and friendships), and so is airline routes (airports and flights). A
graph captures *what connects to what*. (In computer science, "graph" never means a bar
chart.)

Our grid is a graph. Every intersection is a **node**, named by its coordinate like
`(1, 2)`. Every line between adjacent intersections is an **edge**. A node's
**neighbors** are the nodes its edges lead to.

<Figure
  src="/img/lesson-m5-01/graph-3x3-xy.svg"

  caption="Every intersection is a node; every line between neighbors is an edge. The shading counts neighbors."
/>

A **corner** has 2 neighbors, an **edge** node 3, an **interior** node 4.

On paper, an X was never numbered and never anyone's neighbor. In the graph that means a
blocked intersection is **removed**: the node *and* all its edges. Block (1,1):

<Figure
  src="/img/lesson-m5-01/graph-blocked-xy.svg"
  alt="The 3 by 3 graph with (1, 1) blocked: the node is crossed out and its four edges are removed, so the four nodes that touched it, (0, 1), (1, 0), (1, 2) and (2, 1), have each lost a neighbor."
  caption="Blocking (1, 1) removes the node and its four edges."
/>

Blocking one node changes its neighbors too: (0,1), (1,0), (1,2) and (2,1) have each lost
one. That's the second half people forget, and it matters: a search that still sees an
edge into (1,1) will happily step into the wall.

<KnowledgeCheck

  explanation="(0,1) used to connect to (0,0), (0,2), and (1,1). With (1,1) removed, only two neighbors remain."

## Dictionaries

The graph answers "what are the neighbors of `(1, 1)`?" and the came-from record answers
"where did `(2, 1)` come from?" Both start from an intersection and look something up.
Python's tool for that is the **dictionary**: it stores **key-value pairs** in curly
braces. A printed dictionary maps words to definitions; a Python dictionary maps any key
to any value.

<Figure
  src="/img/lesson-m5-02/word-dictionary.svg"
  alt="A cartoon of an open printed dictionary with four entries, each a bold word with its definition: graph, nodes and edges; motor, turns a wheel; robot, senses and acts; sensor, measures the world. Letter tabs run down the edge, and a magnifying glass hovers over the highlighted entry for sensor, where the word is labeled key and the definition is labeled value. Beside it, the same entries as a Python dictionary called glossary, with words as keys and definitions as values, and glossary of sensor giving measures the world."
  caption="The word you look up is the key; what's printed beside it is the value. Python's dictionary works the same way."
/>

<OptionalExtension title="Why a dictionary is fast" gate="Optional: open it if you have time. Nothing later depends on it.">

A printed dictionary is quick because it's in alphabetical order: you flip straight to the
right page. A Python dictionary is organized for speed too, though not alphabetically.
When you store a value, Python turns the key into a number that says where to keep it;
when you look the key up, it does the same arithmetic and goes straight there.

That trick is **hashing**. It's why a lookup is just as fast with four thousand entries as
with four, and why a key can't change: a changed key would send Python to the wrong place.

</OptionalExtension>

In code:

```python
scores = {"Alice": 95, "Bob": 87}
graph = {}                         # empty, ready to fill
graph[(0, 0)] = [(0, 1), (1, 0)]   # node (0,0) -> its neighbor list
```

For the graph, the **keys are node tuples** and the **values are lists of neighbor
tuples.** (A key must be something that can't change, like a number or a tuple.) A
blocked intersection simply isn't a key.

<Figure
  src="/img/lesson-m5-02/graph-dict-xy.svg"

Key (0, 0) maps to [(1, 0), (0, 1)]; key (0, 1) maps to [(1, 1), (0, 0), (0, 2)]; key (1, 1) maps to [(0, 1), (2, 1), (1, 0), (1, 2)]. graph[(1, 1)] jumps straight to that list."
  caption="One entry per node: the node is the key, its neighbor list is the value."
/>

Look up a value with square brackets, and check whether a key exists with `in`. The
snippets here are for trying out, not for keeping: type them in a scratch file or at the
Python prompt, as you did with tuples in Lesson 4-7.

```python
graph = {(0, 0): [(0, 1), (1, 0)], (0, 1): [(0, 0), (0, 2), (1, 1)]}

print(graph[(0, 0)])       # [(0, 1), (1, 0)]
print(len(graph[(0, 0)]))  # 2  -- number of neighbors

print((0, 0) in graph)     # True
print((2, 2) in graph)     # False -- not added
```

Looking up a *missing* key, like `graph[(9, 9)]`, raises a `KeyError`, so check with `in`
first.

The came-from record is a dictionary too. Here are the first three rows of Lesson 5-2's
table: each intersection is a key, and where it came from is the value.

```python
previous = {(0, 0): None, (1, 0): (0, 0), (0, 1): (0, 0)}

print(previous[(1, 0)])    # (0, 0) -- where (1, 0) came from
print((2, 0) in previous)  # False -- (2, 0) has not been reached yet
```

That last line is the step "if that neighbor has not been reached yet", in one `in`. You
will write `previous` in Lesson 5-5; today's job is the graph.

`ROWS` and `COLS` are the size of your taped grid. The function takes the size as
parameters, so a test can build a 3×3 while the settings say 4×4.

The outline is fuller than Module 4's: it's your first dictionary built inside a
function. It's the build-in-a-loop pattern from Lesson 4-2 — start empty, add one entry
per pass — with two loops, one inside the other, and an entry whose value is itself a
list you build. Lesson 5-4 teaches it to leave out blocked intersections; today's test
will tell you whether that change broke anything.

## Activity · Build the graph automatically

A 10×10 grid has 100 nodes, too many to type, so `build_grid_graph()` builds the graph
for any size. For each node, check left, right, down and up, and add only the neighbors
that are on the grid. That takes a **bounds check** before each `append`:

- left only if `x > 0`
- right only if `x < cols - 1`
- the same two checks for `y`, against the bottom and top rows

<Figure
  src="/img/lesson-m5-02/bounds-checks-xy.svg"
  alt="Two nodes with an arrow for each direction. The bottom-left corner (0, 0): left, x > 0, fails; down, y > 0, fails; right, x < cols - 1, passes; up, y < rows - 1, passes; so it gets 2 neighbors. The interior node (1, 1): all four checks pass, so it gets 4 neighbors."
  caption="A failed check is a neighbor that would be off the grid, so it is never appended."
/>

Check the directions in the order **left, right, down, up**: the order Lesson 5-1's
trace used, so your program's paths will match the paper ones.

Write the body, then a test, say `test_grid_graph()`, that builds the 4×4 graph and
prints how many intersections it has (`len(graph)`), the neighbors of `(1, 1)`, and the
neighbors of `(0, 0)`. Write down what each should be before you run it. Set the run line
to it; the robot stays on the desk.

<Reveal title="Check your graph" hint="run test_grid_graph() first">

```text
[(0, 1), (2, 1), (1, 0), (1, 2)]

```

```python
def build_grid_graph(rows, cols):
    """Return the open grid as a dictionary: every (x, y)
    maps to the list of its on-grid neighbors."""
    graph = {}
    for x in range(cols):
        for y in range(rows):
            neighbors = []
            if x > 0:              neighbors.append((x - 1, y))  # left
            if x < cols - 1:       neighbors.append((x + 1, y))  # right
            if y > 0:              neighbors.append((x, y - 1))  # down
            if y < rows - 1:       neighbors.append((x, y + 1))  # up
            graph[(x, y)] = neighbors
    return graph
```

If yours differs but prints the same three lines, keep yours.

</Reveal>

The GRID GRAPH section of `robot.py` as this lesson leaves it, plus the run block; the
rest of the file is as the Lesson 4-6 teacher copy left it. The whole file at the end of

```python
# ===== GRID GRAPH =====
# The grid as a graph, in a dictionary: every intersection is
# a key, and its value is the list of neighbors it is joined
# to. The BFS PLANNER searches this graph. Starts with the
# open grid; Lesson 5-4 adds the blocked list, so a blocked
# intersection is neither a key nor anyone's neighbor.
ROWS = 4                 # the grid is ROWS x COLS intersections
COLS = 4

def build_grid_graph(rows, cols):
    """Return the open grid as a dictionary: every (x, y)
    maps to the list of its on-grid neighbors."""
    graph = {}
    for x in range(cols):
        for y in range(rows):
            neighbors = []
            if x > 0:              neighbors.append((x - 1, y))  # left
            if x < cols - 1:       neighbors.append((x + 1, y))  # right
            if y > 0:              neighbors.append((x, y - 1))  # down
            if y < rows - 1:       neighbors.append((x, y + 1))  # up
            graph[(x, y)] = neighbors
    return graph

def test_grid_graph():
    graph = build_grid_graph(ROWS, COLS)
    print("Intersections:", len(graph))          # 16
    print("Neighbors of (1, 1):", graph[(1, 1)])  # 4 of them
    print("Neighbors of (0, 0):", graph[(0, 0)])  # 2: a corner

# ===== RUN =====
board.wait_for_button()
test_grid_graph()
```

## Wrap-up

- What does the program need to remember that a list can't look up easily? (Things found by intersection: its neighbors, and where it came from.)
- What are a node, an edge, and a neighbor? (A point, a link between adjacent points, and the points a node links to.)
- What does blocking a node remove? (The node and all its edges, so it is nobody's neighbor.)
- How is a dictionary different from a list? (Looked up by key, not by position.)
