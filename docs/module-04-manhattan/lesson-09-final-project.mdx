## The mission

Four destinations, visited in order, starting and (optionally) ending at home base
(0,0). The two halves do the heavy lifting: `compute_manhattan_path(position, dest)`
returns the list of intersections, and `drive_path(path, position, heading)` turns and
drives it. Your job is the **main program** that connects them — about ten lines, and
like every program in this course it is a test function at the bottom of `robot.py`.

```python
    # in turn, print it with its step count, and move
    # position on to that destination for the next leg
    pass

def test_delivery():
    # position and heading start at home, facing North
    # plan the FIRST leg and print it; wait for the button
    # for each destination:
    #     compute the path from where the robot is
    #     print it
    #     drive it
    #     ... and keep position and heading up to date
    #     print where the robot arrived
    pass
```

That second-to-last comment in `test_delivery()` is the one that decides whether the
second leg works. Think about what the main program knows after `drive_path()`
finishes, and what it doesn't — unless you ask.

```python
position, heading = drive_path(path, position, heading)
```

That is the line nearly everyone gets half right: they call `drive_path` and throw the
return value away. The failure is instructive rather than obvious — leg one works
perfectly, and every later leg is planned from (0,0) facing North. If a student's robot
drives a sensible first route and then wanders, ask what `position` is in their main
program after leg 1.

**Class track:** `test_delivery()` is handed `navigator.position` by the planner call,
drives with `navigator.drive_path(path)`, and prints `navigator.position` — there is no
`position, heading = ...` line to get half right. With the `Manhattan` class the
planner call is `planner.compute_path(...)`.

</TeacherNote>

## Only the first leg is printed before the button

Lesson 4-8's habit — plan, print, button, drive — appears here with one limit. The main
program prints the path for leg 1 before the button. It can't print legs 2, 3 and 4 yet,
because each of them is planned from wherever the previous leg actually finished.
Instead, each leg is printed as it's planned, just before the robot drives it. (In
Module 5, where obstacles can appear mid-run, this becomes the only way it *could* work.)

<KnowledgeCheck
  question="Why does the program print the plan for leg 1 before the button, but not for legs 2 to 4?"
  options={[
    {text: 'print() can only be called once before wait_for_button()'},
    {text: 'Later legs are planned from wherever the previous leg ends, which is known only once the robot gets there', correct: true},
    {text: 'Leg 1 is the only one that uses compute_manhattan_path'},
    {text: 'To save battery'},
  ]}
  explanation="Each leg is planned from the robot's current position. Leg 1 is the only one whose starting position is known before the robot moves."
/>

## The heading carries over

`heading` is not reset between legs. If the robot finished leg 1 facing East, it starts
leg 2 facing East — that's what `drive_path` returned, and that's the truth on the
floor. It's exactly why `turn_to()` has to work from the real current heading rather than
assuming North: the Lesson 4-7 `% 4` arithmetic handles any starting direction.

## Activity · Test in three levels

Do **not** jump straight to the full run on the robot. If something breaks, you won't know
which piece. Build up, one test on the run line at a time:

1. **Planner alone (no robot).** Write `test_delivery_paper()` from its outline and set
   the run line to it: loop the destinations, print each path, set `position = dest`
   between them. Confirm every path looks right on screen — this is the Lesson 4-6
   habit, run on today's destinations. Count the steps: 2, 3, 2, 3.
2. **One leg on the robot.** Set the run line to Lesson 4-8's `test_drive_path()` with
   `DESTINATIONS[0]` as its destination. Place the robot at (0,0) facing North, both
   presses. Correct turns? Wheels on the right intersection at the end?
3. **Full sequence.** Write `test_delivery()` and run it. Read the leg-1 path before the
   second press. Watch the straight-through intersections and the turns.

<TeacherNote title="Project day — short intro, incremental testing, and celebrate">

Keep the intro brief; this is a build-and-test day. The single most common bug is the
dropped return value from `drive_path` — when leg-2 paths look wrong, check that line
first; the printed path for leg 2 (planned from (0,0) again) gives it away on screen
before the robot moves. Push level-by-level testing hard; the students who write
everything at once and can't find the break are the ones who skipped planner-only
testing. Watch battery drain on long multi-turn runs and charge between attempts. When
a robot finishes the whole sequence, let the class watch — it's the payoff of nine
lessons. For 50-minute periods, plan two days: planning + desktop testing, then robot
day.

**Class track:** students who did the extensions run the project on their objects —
`navigator.drive_path(path)` on the `navigator` created under the class in Lesson 4-8,
and `planner.compute_path()` if they built `Manhattan` — not on the functions. There is
no return value to drop, which is the point of the Lesson 4-8 side-by-side, and it is
the first time the encapsulation pays off in a whole program rather than a snippet.
Same rubric.

</TeacherNote>

## The rubric and extensions

You're graded on the whole system working together:

| Category | Points | What it takes |

extension, a `Navigator` object so the main loop has nothing to pass back and forth.

## Real-world connections

The plan-then-execute structure you just built is fundamental to real autonomous systems:

<CardGrid>
  <InfoCard tag="Logistics" title="Delivery routing">
    Warehouse and delivery robots compute a route to each stop, drive it, then re-plan from the new location — exactly this loop.
  </InfoCard>
  <InfoCard tag="Rideshare" title="Multi-stop trips">
    Navigation apps chain legs together, recomputing from your current position at each waypoint.
  </InfoCard>
  <InfoCard tag="Space" title="Rover missions">
    Planetary rovers plan a path to a target, execute carefully, and re-plan — with the same separation of planning and driving.
  </InfoCard>
</CardGrid>
