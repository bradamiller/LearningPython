## The whole program — really

Here's the *entire* main program you're building toward. Seven lines:

```python
position = (0, 0)
heading = 0                      # facing North
destinations = [(2, 0), (2, 3), (0, 3)]

for dest in destinations:
    path = compute_manhattan_path(position, dest)
    print("Path:", path)
    position, heading = drive_path(path, position, heading)
```

In plain English: *start at corner (0, 0) facing North; for each destination, compute
the path from where we are, print it, drive it, and remember where we ended up.* You
don't need to understand `compute_manhattan_path` or `drive_path` yet — just see that
the program is short **because the functions do all the work**.

(Those seven lines are the *interesting* part. In your `robot.py` they are the body of
the module's last test function, and the two functions they call live in two new
sections above it — MANHATTAN PLANNER and NAVIGATOR — on top of the LINE TRACKING and
GRID DRIVING sections you already have. The `RUN` block waits for the button as always.
All of that is left out here so the shape stands out.)

## Two halves, two jobs

<CardGrid>
  <InfoCard tag="Planner" title="compute_manhattan_path">
    Told where the robot is and where it wants to go, it computes a <strong>list of intersections</strong> to follow. It never touches the robot.
  </InfoCard>
  <InfoCard tag="Driver" title="drive_path">
    Given that list, it <strong>drives the robot</strong> through each intersection — turning and line-following — and reports where it ended up. It never decides the route.
  </InfoCard>
</CardGrid>

The planner produces a path; the driver consumes it. Each half has exactly one
responsibility — that's called **separation of concerns**, and it makes bugs easy to
find: a wrong route is a planner problem; a wrong turn is a driver problem. And because
the planner is *told* where the robot is rather than remembering, the printed path is
always checkable before the robot moves.

## Your roadmap

Every lesson in this module builds one piece of that program:

- **Lesson 4-1** — coordinates: the `(row, col)` system
- **Lesson 4-2** — tuples: storing a position like `(2, 3)` (scratch work, nothing goes in the file yet)
- **Lesson 4-3** — lists: storing a path like `[(1,0), (2,0), (3,0)]` (scratch work too)
- **Lesson 4-4** — the Manhattan algorithm: computing paths on paper, then in code — the MANHATTAN PLANNER section of `robot.py` opens
- **Lesson 4-5** — the planner function: its name, its promises, and why it is told where the robot is
- **Lesson 4-6** — testing your code without a robot: a test harness joins the planner section
- **Lesson 4-7** — turning logic: headings as numbers — the NAVIGATOR section opens
- **Lesson 4-8** — driving the path, built on your Module 2 line-tracking functions
- **Lesson 4-9** — the final project: it all comes together in one test function

Notice `drive_path` reuses the Module 2 functions for the actual driving — you're not
starting from scratch. That's the payoff of building a toolkit. (If you did the Module 2
class extensions, Lessons 4-5 and 4-8 each have an optional class version too.)
