Here's the problem this module solves: **get the robot from where it starts to a
destination on the grid, all by itself.**

A taxi in Manhattan has the same problem. Buildings fill every block, so it can't drive
straight from A to B; it can only drive along the streets.

## How to find the route

> **Go across until x is right. Then go up or down until y is right.**

That's the whole algorithm, the one the taxi uses. It's called the **Manhattan
algorithm**.

<Callout kind="note" title="The big assumption: every street is clear">

The algorithm assumes nothing is in the way, so it never needs a detour. **Module 5**
adds obstacles; **Module 6** (optional) adds slow streets.

</Callout>

<TeacherNote title="Manhattan, for the curious">

The grid dates from 1811 and is turned about 29 degrees from true north; the same
distance is called **taxicab distance** in math. The map is a hook, not a lesson.
Lesson 4-3 opens with "Why Manhattan?" and assumes students have seen it.

</TeacherNote>

## Breaking down a complex problem

Knowing the route is only part of it. "Drive over there" sounds like one job, but it's a somewhat complex problem, too much to
get right in one go. One way to tackle a complex problem is to **break it into simpler
sub-problems** and solve each one. That's called **problem decomposition** (or **top-down design**).

## Discuss · How would you split it?

1. Before the robot moves, could you write down every intersection it will drive through?
2. How could you check that list is right, without the robot?
3. Once the list is right, what's left for the robot to do?

<TeacherNote title="Leading the discussion (5–8 min)">

Ask the questions in order and let the class answer; draw the grid on the board.

1. **Yes.** Expect "two right, then three up." Mark each intersection on the board grid in order. If someone says the robot should decide as it goes, ask: "Does it need to? Nothing on the grid changes."
2. **Trace it on the grid by hand**, or have the computer print it and compare. Steer to: *no robot needed*, so the route can be tested on a laptop.
3. **Just drive it:** at each intersection on the list, face the next one and follow the tape there. It doesn't have to decide anything.

Then name the split: **plan** the route, **drive** the plan, with the list passed between
them. Ideas about motors, sensors or turning belong to the driving half; park them there.

</TeacherNote>

## Plan first, then drive

That's one way to split the problem, and the one this module uses: **plan** the whole
route first, then **drive** it.

<Figure
  src="/img/lesson-m4-00/plan-then-drive.svg"
  alt="Left: a 4 by 4 grid with (0, 0) at the bottom-left. The robot starts at (0, 0). A blue route goes right to (1, 0) and (2, 0), then up to (2, 1), (2, 2) and (2, 3), each intersection labeled with its tuple. Right: step 1, Plan: work out the route, print it, check it, no robot needed. An arrow carries the list [(1, 0), (2, 0), (2, 1), (2, 2), (2, 3)], a list of (x, y) tuples, down to step 2, Drive: take the list and drive it, one intersection at a time."
  caption="The plan is a list of (x, y) tuples. One function makes it; another drives it."
/>

1. **Plan.** The planner, `compute_manhattan_path`, works out the whole route. It never
   moves the robot, so you can test it **without a robot**: print the route and check it
   against the grid.
2. **Drive.** Once the plan is right, the driver, `drive_path`, **takes the plan and
   drives it**, then reports where the robot ended up. It decides nothing; the plan
   already did.

Each intersection is a pair of numbers, `(x, y)`, which Python stores as a **tuple**. So
the plan is a **list of tuples**, the one thing the two functions share. (Tuples come in
Lesson 4-1, lists in 4-2.)

One job each is called **separation of concerns**, and it makes bugs easy to find: a
wrong route is a planner problem; a wrong turn is a driver problem.

## From one destination to several

Once the robot can reach one destination, several is just a loop: plan from where it
is, drive, repeat. Here's the *entire* main program you're building toward. Seven lines:

```python
position = (0, 0)
heading = 0                      # facing North
destinations = [(2, 0), (2, 3), (0, 3)]

for dest in destinations:
    path = compute_manhattan_path(position, dest)
    print("Path:", path)
    position, heading = drive_path(path, position, heading)
```

It's short **because the functions do all the work**.

## Wrap-up

- What problem does Module 4 solve? (Drive the robot from where it starts to a destination on its own, then to several destinations in a row.)
- Why plan first? (The planner never moves the robot, so its list of tuples can be printed and checked with no robot at all. Then the driver only has to follow a plan you already trust.)
- What are the two halves and their jobs? (`compute_manhattan_path` plans; `drive_path` drives.)
