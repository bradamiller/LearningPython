**Question 4.** On the way across, how does the planner know when to stop going east?

<Reveal title="Answer 4" hint="discuss first">

**When x equals D's x.** Then it does the same with y. That is the whole planner:
**add 1 to x until it matches D's x, then add 1 to y until it matches D's y.**

</Reveal>

<TeacherNote title="Question 4">

Questions 3 and 4 are the heart of it. Write the rule on the board and underline it.
"Until it matches" is a loop that keeps going while x is less than D's x: Step 2 writes it.

</TeacherNote>

**Question 5.** Leg 2 goes from (2,3) to (1,0). What is different? How does the planner
know which way to go?

<Reveal title="Answer 5" hint="discuss first">

**Both numbers get smaller:** one step west, then three south. Compare where you are with
D, one number at a time. If x is smaller than D's x, go east; if it's bigger, go west.
The same with y gives north or south: **four directions.** Today you write east and north;
west and south are Lesson 4-3.

**Question 6.** What if x already matches D's x at the start? What if S and D are the
same intersection?

<Reveal title="Answer 6" hint="discuss first">

**No steps across:** the robot only goes up or down. **If S is D, the path is empty:** the
robot is already there. The rule handles both with nothing extra.

</Reveal>

<TeacherNote title="Question 6">

If anyone wants a special case, ask: "Does the rule already do the right thing?" Walk it

</TeacherNote>

**Question 7.** Without listing the path, can you tell how many intersections are on it?

<Reveal title="Answer 7" hint="discuss first">

**Steps across plus steps up or down.** Leg 1 is 2 + 3 = 5; Leg 2 is 1 + 3 = 4. That's a
quick check on any path the planner prints.

</Reveal>

<TeacherNote title="Question 7">

Steps across is how far apart the two x's are; steps up or down is how far apart the two
y's are. Don't name it yet: Lesson 5-1 calls it the Manhattan distance.

</TeacherNote>

**Question 8.** Does it matter that we go across first?

<Reveal title="Answer 8" hint="discuss first">

**Not for the length:** up first is 5 blocks too. **It does change which intersections
the robot drives through** (look back at Answer 1).

</Reveal>

intersections you drive through is exactly what matters.

## Activity · Build the planner, one piece at a time

Each step prints something. Before every run, **write down what you expect to see**, then

### Step 1 · Leg 1, by hand

The planner can't write its list out in full, as `DELIVERY_STOPS` does: it doesn't know
the path until it works it out. So it starts with an **empty list**, `[]`, and adds one
position at a time with `append()`, which puts an item on the **end**. `len()` counts the
items:

```python
path = []
path.append((1, 0))
path.append((2, 0))
print(path)          # [(1, 0), (2, 0)]
print(len(path))     # 2
```

Mind the double parentheses in `path.append((1, 0))`: the outer pair belongs to
`append()`, the inner pair is the tuple.

Leg 1 is the trip from the discussion: (0, 0) to (2, 3). Its path is the five
intersections you listed in Answer 2, without the start.

In `compute_manhattan_path()`, keep the `print` line and replace `return [destination]`
with:

1. `path = []`
2. Five `append()` lines, one per move of Leg 1, in order, each followed by
   `print(path)`. The first two are:
   ```python
   path.append((1, 0))
   print(path)
   ```
3. `return path`

Before you run `test_delivery()`: write down the five lists Leg 1 will print, and what
Leg 2's path will be.

### Step 2 · Let a loop do the appending

Look at your five appends. The first two each add 1 to x and append the new position,
until x is right. The last three do the same with y. Doing the same thing until something
is right is a `while` loop.

<Figure
  src="/img/lesson-m4-03/appends-to-loops.svg"
  alt="The five typed lines for (0, 0) to (2, 3), under path = []. The first two, in red, append (1, 0) and (2, 0), each x + 1, and are bracketed to loop 1: while x < dest_x, x = x + 1, path.append((x, y)). The last three, in green, append (2, 1), (2, 2) and (2, 3), each y + 1, and are bracketed to loop 2, the same loop for y."
  caption="Each append is one trip around a loop."
/>

To add 1 to x, the function needs x on its own. **Unpacking**, from Lesson 4-1, takes a
tuple apart: `x, y = start`. Then `x` and `y` are where the plan has got to, and after each
move `(x, y)` puts them back together as a **new tuple** for the path.

Replace the whole `compute_manhattan_path()` function with this. The east loop is written
for you. Add `test_planner()` under it.

```python
def compute_manhattan_path(start, destination):
    """Return the (x, y) steps from start to destination, across
    first, then up or down. The start itself is not in the list."""
    print("computing path from:", start, "to:", destination)
    path = []
    x, y = start              # where the plan is now
    dest_x, dest_y = destination   # where it is going

    # East: keep stepping right until x matches dest_x
    while x < dest_x:
        x = x + 1             # one step right
        path.append((x, y))   # record the new spot

    # North: copy east, but step y until it matches dest_y

    return path

def test_planner():
    print(compute_manhattan_path((0, 0), (2, 3)))
    print(compute_manhattan_path((0, 2), (3, 2)))
    print(compute_manhattan_path((2, 0), (2, 3)))
```

**Paper test:** on paper, write the full path for each of the three trips in
`test_planner()`. Then, knowing only the east loop exists, predict what each will print.
Set the run line to `test_planner()` and run it.

### Step 5 · Why a new tuple every step

Could the loop just add to one tuple instead of making new ones? Predict, then type these
into the shell:

```python
spot = (2, 3)
spot.append(4)
```

<Reveal title="What happened?" hint="predict first">

`AttributeError: 'tuple' object has no attribute 'append'`. A tuple **can't be changed**
once it's made, so the loop makes a new one every step. That's right for a position:
`(2, 3)` should always mean the same intersection. A list is the opposite: it can grow.

The rule of thumb: a **tuple** is one thing made of a fixed number of parts, like a
position. A **list** is any number of things in order, like the stops on a route.

</Reveal>

### Step 6 · Two names, one list

In Lesson 1-9, a variable was a named memory location, and `=` stored a value there. A
list can grow, but a location is a fixed size. So the list lives somewhere else, and the
variable holds its **address**, called a **reference**. Predict both printouts, then run
this in the shell:

```python
a = 5
b = a
b = b + 1
print(a, b)

path = [(1, 0)]
same_path = path
same_path.append((2, 0))
print(path)
```

<Reveal title="What happened?" hint="predict first">

```text
5 6
[(1, 0), (2, 0)]
```

`b = a` copied the **value**: two separate 5s. `same_path = path` copied the **address**:
still one list, so appending through either name changes what both see.

<Figure
  src="/img/lesson-m4-02/number-vs-list.svg"
  alt="Left: the memory locations named a and b each hold their own 5. Right: the locations named path and same_path each hold the number 5120, and arrows run from both of them to one list stored at address 5120."
  caption="b = a makes a second 5. same_path = path makes a second arrow to the same list."
/>

</Reveal>

The same goes for a function's parameter. Predict both printouts, then run it:

```python
def move(spot):
    spot = (9, 9)             # assigns a new value

def extend(steps):
    steps.append((9, 9))      # changes the list itself

here = (1, 1)
move(here)
print(here)

route = [(1, 1)]
extend(route)
print(route)
```

<Reveal title="What happened?" hint="predict first">

```text
(1, 1)
[(1, 1), (9, 9)]
```

`=` stores a new value in the function's own variable, as in Lesson 4-1: the
caller never sees it. `append()` goes to the list itself, and there is only one list.
Module 5 relies on this: a planner sees every obstacle you add to your list.

</Reveal>

<TeacherNote title="What to watch">

"Empty list, append inside a loop" is the pattern the rest of the course builds paths
with. Step 1 is deliberately clumsy: printing after every append shows the list growing
on the end, the repeated path on Leg 2 shows why a planner must use its parameters, and
the count makes the typed version hopeless. Students should leave it wanting the loop.
Keep it to ten minutes.

Take real time on the double parentheses in `path.append((x, y))`, and on Step 3: the
indentation bug is the most common list bug there is, and here it costs one keystroke to
cause and to fix. Check the paper tests before Step 2's run: a wrong prediction sends a
student hunting for a bug that isn't there.

Step 6 **adds** to Lesson 1-9; it doesn't correct it. A variable is still a named
location, and `=` still stores there. The new fact is what the stored value *is* for a
list. A demo that lands: two students hold slips with the same post office box number;
one puts something in the box, and the other finds it there. Don't teach `copy()` or
slicing: nothing in this course needs a separate copy, and Module 5's `BLOCKED` list
relies on the sharing.

The broken delivery run in Step 7 is the hook for Lesson 4-3. Let students say what's
missing.

Scope: `[]`, `append()`, `len()`, unpacking. No indexing yet (Lesson 4-4), and no
`insert`, `pop` or slicing at all.

</TeacherNote>

<TeacherNote title="Solution (teacher copy)">

The MANHATTAN PLANNER section as this lesson leaves it. The NAVIGATOR section and the
main program are unchanged from Lesson 4-1.

```python
# ===== MANHATTAN PLANNER =====
# Plans a route across the grid: given where the robot is and
# where it should go, returns the list of (x, y) tuples to
# drive to. Nothing in here touches a sensor or a motor.

def compute_manhattan_path(start, destination):
    """Return the (x, y) steps from start to destination, across
    first, then up or down. The start itself is not in the list."""
    print("computing path from:", start, "to:", destination)
    path = []
    x, y = start              # where the plan is now
    dest_x, dest_y = destination   # where it is going

    # East: keep stepping right until x matches dest_x
    while x < dest_x:
        x = x + 1             # one step right
        path.append((x, y))   # record the new spot

    # North: copy east, but step y until it matches dest_y
    while y < dest_y:
        y = y + 1             # one step up
        path.append((x, y))

    return path

def test_planner():
    print(compute_manhattan_path((0, 0), (2, 3)))
    print(compute_manhattan_path((0, 2), (3, 2)))
    print(compute_manhattan_path((2, 0), (2, 3)))
```

</TeacherNote>

## Wrap-up

- How does the planner build a path? (Start with `[]`, and `append()` one position on every trip around a loop.)
- Why is a position a tuple and a path a list? (A position is a fixed pair that shouldn't change; a path grows one step at a time.)
- If two names refer to the same list and you append through one, what does the other see? (The change: there is only one list.)
- What still doesn't work? (Trips that go left or down: both loops are skipped.)
