## The toolkit you already have

Module 2 ended with four functions in the LINE TRACKING section of `robot.py`, and
Module 3 drove the whole grid with them. Here they are again, because everything in
this lesson is built from them:

| Function | What it does | Ends when |
|---|---|---|
| `track_to_intersection()` | Follows the line forward | both sensors see the cross |
| `turn_clockwise()` | Pivots right | the sensors find the next line |
| `turn_counterclockwise()` | Pivots left | the sensors find the next line |
| `drive_past_intersection()` | Drives straight 8.75 cm | the distance is done |

Notice what's *not* in that table: any mention of rows, columns, headings or paths. The
Module 2 functions know how to follow tape. They have no idea where the robot is. That's
the split from Lesson 4-5 again — the planner doesn't know how to drive, and the driving
functions don't know what a path is. Today's three functions sit between them.

## The wrinkle: where the robot turns

`track_to_intersection()` stops the moment both sensors see the cross. But the sensors are
at the front of the robot, and it turns about its **center of rotation**, 8.75 cm further
back. It's the wrinkle Lesson 2-9 solved, and the fix is the same:

<Figure
  src="/img/lesson-m2-09/park-on-cross-turns.svg"
  alt="Animation of two XRP robots seen from above, each stopped with its line sensors on a taped cross and its center of rotation 8.75 cm behind them. Left: the robot turns right straight away, swinging about a point short of the intersection, and its sensors end up beside the cross street. Right: the robot first drives forward 8.75 cm so its center of rotation is on the cross, then turns right, and its sensors land on the cross street."
  caption="Turn where the track stops and the sensors miss the new line. Drive past first and the robot spins on the cross."
/>

So `drive_path()` arrives at **every** intersection with the pair from Module 3, whichever
way it turns next. The drive-past parks the robot so a turn spins on the intersection,
and it carries the sensors past the cross so the *next* track starts clean.

```python
track_to_intersection()        # sensors reach the cross
drive_past_intersection()      # center of rotation on the cross; sensors past it
```

<KnowledgeCheck
  question="Why does the robot call drive_past_intersection() after every track_to_intersection(), even when it is going straight on?"
  options={[
    {text: 'To speed up the run'},
    {text: 'The sensors stop short of the cross, so the center of rotation has to be moved onto it — otherwise a turn pivots in the wrong place, and the next track would see the same cross immediately', correct: true},
    {text: 'Only turns need it; going straight it is skipped'},
    {text: 'To recharge the battery'},
  ]}
  explanation="The sensors lead the center of rotation. Parking it on the cross makes every turn pivot on the intersection, and it moves the sensors off the tape so the next line-follow starts clean. Doing it every time means no special cases."
/>

<TeacherNote title="The 8.75 cm is sensor-to-center-of-rotation; do not let it become folklore">

The distance in `drive_past_intersection()` is the gap between the reflectance sensors
and the center of rotation (the pen hole between the drive wheels) on an XRP, so that point ends up where the sensors were. If a class
has a robot with a different mounting, measure it. The old version of this lesson only
cleared the intersection in the straight-ahead case and relied on the turn to clear it
otherwise; that depended on turn behavior nobody had checked. Doing it after every
track removes the special case, and the turns now pivot on the cross, which is what
makes a sensor-ended turn land on the new line reliably.

</TeacherNote>

## This lesson's skeleton

Paste this into `robot.py` at the end of the NAVIGATOR section, under
`desired_heading()`. The two outlines are the Lesson 4-7 designs; `drive_path()`'s step
3 has grown the wrinkle.

```python
# --- Lesson 4-8: turn to a heading, drive a path ---
# turn_to() turns the robot with the LINE TRACKING turns, the
# short way round. drive_path() is the loop: for each
# intersection, face it, arrive with the track-then-drive-past
# pair, and record the new position. Both hand back what they
# changed, because the caller keeps the only record.

def turn_to(heading, desired):
    """Turn from heading to desired the short way round and
    return desired, the new heading."""
    # 1. turns = (desired - heading) % 4
    # 2. if turns is 3: one turn_counterclockwise()
    #    otherwise: turn_clockwise(), turns times
    # 3. return desired
    pass

def drive_path(path, position, heading):
    """Turn and drive through every intersection in path, from
    position facing heading; return the final (position, heading)."""
    # for each next_pos in path:
    #     1. needed = desired_heading(position, next_pos)
    #     2. heading = turn_to(heading, needed)
    #     3. arrive: track_to_intersection(), then
    #        drive_past_intersection()
    #     4. position = next_pos -- the robot is there now
    # return position, heading
    pass
```

Read the two assignments in `drive_path()` carefully. `heading = turn_to(heading,
needed)` — the turn function hands back the new heading and the loop keeps it.
`position = next_pos` — the robot has arrived, so its position is the intersection it
just drove to. And the function returns both at the end, so whoever called it can keep
its own record straight:

```python
position, heading = drive_path(path, position, heading)
```

Forget that left-hand side and the robot drives fine — once. The next path gets planned
from where the robot *was*.

If you built the `LineTrack` class in Lesson 2-9, the four driving calls in these
outlines are `tracker.turn_clockwise()`, `tracker.track_to_intersection()` and so on —
the same names with the object in front.

## Plan, print, button, drive

Here is the test that puts the planner and the navigator together — the shape of every
driving program from here on. Note the order:

```python
def test_drive_path():
    position = (0, 0)
    heading = 0                   # facing North
    destination = (2, 3)

    path = compute_manhattan_path(position, destination)
    print("Path:", path)

    board.wait_for_button()       # read the path, THEN press

    position, heading = drive_path(path, position, heading)
    print("Arrived at:", position, "facing", HEADING_NAMES[heading])
```

The path is planned and **printed before the button**. Read it. Is it what you expect?
Then press the button. This habit costs two lines and is the first thing to check when a
run goes wrong: if the printed path is right and the robot still went wrong, the bug is
in the driving, not the planner — and you know which half of the file to open.

That makes two button presses per run, and both are useful. The one in the `RUN` block
starts the test: the path prints and the robot sits still while you read it. The one in
the test is *go*. A test that drives is the only kind that waits twice.

```python
def turn_to(heading, desired):
    """Turn from heading to desired the short way round and
    return desired, the new heading."""
    turns = (desired - heading) % 4
    if turns == 3:
        turn_counterclockwise()
    else:
        for i in range(turns):
            turn_clockwise()
    return desired

def drive_path(path, position, heading):
    """Turn and drive through every intersection in path, from
    position facing heading; return the final (position, heading)."""
    for next_pos in path:
        needed = desired_heading(position, next_pos)
        heading = turn_to(heading, needed)
        track_to_intersection()
        drive_past_intersection()
        position = next_pos
    return position, heading
```

<TeacherNote title="Build incrementally, and test on the desktop first">

Write and test one function at a time — the three steps above — never the whole
section at once. The paper test in step 1 is the old "desktop mode" without editing
the Module 2 functions: it walks the path with `desired_heading()` and the `% 4`
arithmetic and prints what the robot *would* do, which is where most logic bugs get
caught. Hammer the reuse point: the Module 2 functions drove the Module 3 square and
now drive grid paths unchanged. The two button presses per driving test (start, then
go) will need saying once; after that students like it, because the first press is
when they read the path.

Usual bugs, in order of frequency: not assigning `position, heading` from `drive_path`'s
return; the start sneaking into the path (Lesson 4-5's promise 1 — `desired_heading`
raises, which is the lesson working as intended); and a `turn_to` that forgets to
`return desired`.

**Hardware:** turns end when the sensors find the next line, not on a timer, so they
tolerate battery level and floor friction. If a turn overshoots, the blind first part of
the turn in Module 2's `turn_clockwise()` is the thing to shorten.

<OptionalExtension title="The Navigator class — and what self really is">

If you did the Module 2 class extensions, the three driving functions can become a
`Navigator` class — and this is the first class in the course whose constructor takes
real parameters, which makes it the right moment to say what `self` actually is.

Back in Lesson 2-7, the class was a blueprint and the objects were the houses built from
it. Here is the same picture with one thing added: every house has an **address**.

<Figure
  src="/img/lesson-m4-08/house-address.svg"
  alt="A blueprint labeled 'class House:' listing __init__(self, color) and paint(self). Below it, three houses built from the plan, each with an address plaque: red at 12 Oak, yellow at 48 Elm, blue at 7 Pine, with the code that built each one. At the bottom, the call elm.paint() with an arrow to the yellow house and the note: inside paint(), self is 48 Elm — the one house this call is about."
  caption="The plan says what painting is. The address says which house. When you call elm.paint(), self is 48 Elm — nothing else."
/>

The plan says what "paint" means — the same instructions for every house. But the
painters have to be sent *somewhere*. `elm.paint()` means "paint the house at 48 Elm",
and inside `paint()`, `self` is that address. Call `oak.paint()` and the identical code
runs with `self` meaning 12 Oak. **`self` is the address of the one object this call is
about.** That's all it is. `self.color` is "the color at this address"; `self.position`
is "the position of this navigator, not any other".

Think of a method as a **work order written once for every house, with a blank for the
address.** That's why `self` is the first parameter in the `def` — it's the blank. And
when you call `elm.paint()`, Python fills the blank in from the object you pointed at —
that's why `self` is absent from the call. Two errors everyone makes become easy to read:

- `def paint():` with no `self` — a work order with no address blank. Python says
  *"takes 0 positional arguments but 1 was given"*: it tried to fill in the blank and
  found none.
- `color` instead of `self.color` inside the method — a work order that names a color
  with no address attached. Python says *"NameError: name 'color' is not defined"*.

Two identical houses are still two houses. `Navigator((0, 0), 0)` and
`Navigator((3, 3), 2)` are two objects from one plan with different numbers on the door.

Now the Navigator. Its constructor takes the start position and heading — the first
time a constructor in this course is handed real data — and stores them at its own
address. This is the class-track skeleton for the whole NAVIGATOR section: paste it in
place of the three functions (keep `HEADING_NAMES` and your tests), and move your three
bodies into the three methods.

```python
# ===== NAVIGATOR (class version) =====
# One Navigator object owns the robot's position and heading.
# It HAS a LineTrack (built in __init__) and gives it the
# driving orders; it is told where to go and keeps its own
# record of where it got to. Same three methods as the
# function version, same names, with navigator. in front.
class Navigator:
    def __init__(self, start, heading):
        self.position = start
        self.heading = heading
        self.line_track = LineTrack()        # has-a LineTrack

    def desired_heading(self, next_pos):
        # your function; position is self.position now, so
        # it is no longer a parameter
        pass

    def turn_to(self, desired):
        # your function, with self.heading in place of the
        # parameter and self.line_track. in front of each
        # turn; it STORES the new heading, not returns it
        pass

    def drive_path(self, path):
        # your function, with self. in front of position,
        # heading and the two LINE TRACKING calls; it stores
        # the final position instead of returning it
        pass

navigator = Navigator((0, 0), 0)
```

`__init__` is the new idea, so it's given, and it's worth reading twice: the two
parameters land in `self.position` and `self.heading`, and from then on every method
reads and updates *those* instead of being handed them. That is why the signatures
shrank — `desired_heading(self, next_pos)` has lost its `position` parameter and
`turn_to(self, desired)` its `heading`, because the object already knows both. And
nothing is returned, because the record lives at the object's address: the caller
reads `navigator.position` whenever it wants to know.

Your tests change the same way. `drive_path([(1, 0)], (0, 0), 0)` becomes
`navigator.drive_path([(1, 0)])`, and the print afterwards reads `navigator.position`
and `navigator.heading`. The planner call in `test_drive_path()` is handed
`navigator.position`. Run all three tests again; the robot should not be able to tell
the difference.

```python
    def desired_heading(self, next_pos):
        row_diff = next_pos[0] - self.position[0]
        col_diff = next_pos[1] - self.position[1]
        if col_diff == 0 and row_diff == -1: return 0   # North
        if row_diff == 0 and col_diff ==  1: return 1   # East
        if col_diff == 0 and row_diff ==  1: return 2   # South
        if row_diff == 0 and col_diff == -1: return 3   # West
        raise ValueError(str(self.position) + " and " + str(next_pos) + " are not neighbors")

    def turn_to(self, desired):
        turns = (desired - self.heading) % 4
        if turns == 3:
            self.line_track.turn_counterclockwise()
        else:
            for i in range(turns):
                self.line_track.turn_clockwise()
        self.heading = desired

    def drive_path(self, path):

            needed = self.desired_heading(next_pos)
            self.turn_to(needed)
            self.line_track.track_to_intersection()
            self.line_track.drive_past_intersection()
            self.position = next_pos
```

This is the one class in the course with a *felt* reason to exist. On the left,
`position` and `heading` have to be threaded through every call and assigned back from
every return — forget once and the robot plans from the wrong place. On the right, the
navigator owns them: they live at its address, `drive_path()` updates them there, and the
caller just reads `navigator.position` whenever it wants to know. There is nothing to
pass back and forth, so there is nothing to forget.
