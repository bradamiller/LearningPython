## Why "Manhattan"?

Picture the streets of Manhattan in New York. To get from one corner to another, you
can't cut diagonally through the buildings — you walk along the streets and avenues.
The total distance is the number of blocks across **plus** the number of blocks up or
down. That's the **Manhattan distance** (taxi drivers know it too — it's also called
"taxicab distance").

Our robot is in the same situation: it drives along grid lines, never diagonally. So
the distance from one intersection to another is just *steps across + steps up or down* — the
exact idea you computed by hand in Lesson 4-1.

The strategy we'll use is the simplest one that always works: **move across first
until x is right, then move up or down until y is right.** That always traces an
L-shaped path (or a straight line, if x or y is already correct).

## Activity · Code the algorithm

Build it in two stages: get the easy half working and *run it* before you
generalize. A half-finished algorithm you have tested beats a whole one you
haven't.

### Step 1 · East and north only

Start with just the two "positive" directions (moving right and up) — steps 1 to 4
of the outline. Step 1 uses **tuple unpacking**, which is new: one line pulls both
numbers out of a tuple into two variables.

```python
x, y = start     # start is (0, 0): x is 0, y is 0
```

Do the same for `end`, and the loops compare plain numbers. Each loop is the
build-in-a-loop pattern from Lesson 4-3, with a `while` instead of a `for`: as long
as x is still short of the destination x, step it by one and append the new
`(x, y)` — the double parentheses in `append((...))` are the function call around
the tuple.

Then write a test — say `test_paper_paths()` — that prints `compute_path((0, 0),
(2, 3))` and `compute_path((1, 1), (3, 4))`. Set the run line to it, run it, and compare
with your paper traces: both should give exactly the hand-traced lists, 5 steps each.
Don't go on until they match.

**Now find the limit:** add `compute_path((3, 3), (1, 0))` to the test and run it
again. An empty list! `3 < 1` is False and `3 < 0` is False, so *neither* loop runs.
Going left or down, this version does nothing. We need west and south too.

### Step 2 · All four directions

The fix is elegant: **add two more while loops**, one for west (x decreases) and one
for south (y decreases). Each is the mirror of the loop it sits next to: the
comparison flips and the step goes the other way. No `if/else` needed — for any single
trip, at most one x loop and one y loop will run; the others are skipped because
their condition is False from the start. Keep the two x loops together, before the
two y loops, so the path always goes across first.

`[(2,3), (1,3), (1,2), (1,1), (1,0)]` — five steps, matching |3−1| + |3−0|.

<TeacherNote title="Redirect anyone reaching for if/else">

The four-loop design is the lesson's big idea: *a while loop whose condition starts
False simply does nothing.* Students who've seen conditionals will try to wrap this in
`if x < dest_x ... elif x > dest_x`. Steer them back — the four loops are simpler and
handle every case, including same-position (all four skipped → `[]`). Take real time on
tuple unpacking (`x, y = start`) and on the double parentheses in
`append((x, y))`: the outer pair is the function call, the inner pair is the tuple.

</TeacherNote>

## Activity · The edge cases

Good algorithms handle the awkward inputs without special code. Write a second test —
`test_edge_cases()` — with three calls: **same column**, `(2, 0)` to `(2, 3)`; **same
row**, `(0, 2)` to `(3, 2)`; and **same spot**, `(1, 1)` to `(1, 1)`. Trace all three
on paper and write your prediction as a comment next to each call *before* you set the
run line to it.

<Reveal title="Check the three edge cases" hint="predict all three first">

```
[(2, 1), (2, 2), (2, 3)]
[(1, 2), (2, 2), (3, 2)]
[]
```

Same column (same x) means the two x loops are skipped; same row (same y) skips the
y loops; same position skips all four and returns `[]`. Nothing special written — the loops just
don't run when there's no distance to cover.

</Reveal>

<Reveal title="Check your compute_path()" hint="write and test it first">

```python
def compute_path(start, end):
    """Return the (x, y) steps from start to end, across
    first, then up or down. The start itself is not in the list."""
    path = []
    x, y = start
    dest_x, dest_y = end

    # Move east (x increases)
    while x < dest_x:
        x = x + 1
        path.append((x, y))

    # Move west (x decreases)
    while x > dest_x:
        x = x - 1
        path.append((x, y))

    # Move north (y increases)
    while y < dest_y:
        y = y + 1
        path.append((x, y))

    # Move south (y decreases)
    while y > dest_y:
        y = y - 1
        path.append((x, y))

    return path
```

The first and third loops are stage 1; the other two are the mirrors you added in
stage 2. If yours is laid out differently and passes both tests, keep yours.

</Reveal>

The MANHATTAN PLANNER section of `robot.py` as this lesson leaves it, plus the run
block; the rest of the file is as the Lesson 3-4 teacher copy left it. The file is

```python
# ===== MANHATTAN PLANNER =====
# Plans a route across the grid: given where the robot is and
# where it should go, returns the list of (x, y) tuples to
# drive to, across first and then up or down. Pure arithmetic --
# nothing in here touches a sensor or a motor, so every test
# in this section runs on screen with the robot sitting still.

def compute_path(start, end):
    """Return the (x, y) steps from start to end, across
    first, then up or down. The start itself is not in the list."""
    path = []
    x, y = start
    dest_x, dest_y = end

    while x < dest_x:
        x = x + 1
        path.append((x, y))

    while x > dest_x:
        x = x - 1
        path.append((x, y))

    while y < dest_y:
        y = y + 1
        path.append((x, y))

    while y > dest_y:
        y = y - 1
        path.append((x, y))

    return path

def test_paper_paths():
    print(compute_path((0, 0), (2, 3)))   # east, then north
    print(compute_path((1, 1), (3, 4)))
    print(compute_path((3, 3), (1, 0)))   # west, then south

def test_edge_cases():
    print(compute_path((2, 0), (2, 3)))   # same column
    print(compute_path((0, 2), (3, 2)))   # same row
    print(compute_path((1, 1), (1, 1)))   # same spot: []

# ===== RUN =====
board.wait_for_button()
test_edge_cases()
```

## Wrap-up

- What does "across first, then up or down" produce? (An L-shaped path — predictable and always valid.)
- Why four while loops instead of `if/else`? (Only the relevant loops run; a False condition just skips.)
- Why isn't the starting position in the path? (The robot is already there; `len(path)` = number of steps.)
