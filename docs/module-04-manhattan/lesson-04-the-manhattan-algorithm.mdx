## The strategy: across first, then up or down

Each step moves the robot to a neighboring intersection, so **exactly one of x or y
changes, by 1**. Never both: that would be a diagonal, and the robot can't drive one.

<Figure
  src="/img/lesson-m4-04/one-step.svg"
  alt="A 3 by 3 grid with the robot's intersection (1, 1) in the middle. Red arrows go right to (2, 1), x + 1, and left to (0, 1), x − 1. Green arrows go up to (1, 2), y + 1, and down to (1, 0), y − 1. A dashed diagonal to (2, 2) is crossed out: x and y both change, so it is not one step."
  caption="One step changes x or y by 1, never both."
/>

The strategy is the simplest one that always works: **step across until x is right,
then step up or down until y is right.** That traces an L-shaped path, or a straight
line if x or y is already right.

## From the trace table to a loop

Write the code the same way you worked out each new position. `x` and `y` are the
robot's **current position**: they start as the start tuple (`x, y = start`) and
change by 1 on every move. `dest_x` and `dest_y` are the destination
(`dest_x, dest_y = destination`).

The function doesn't know on its own where the robot is. Whoever calls it supplies the
robot's position as the `start` parameter, so the same function plans from any
intersection.

In one loop, keep adding 1 to x while x is less than `dest_x`. In a second loop, do
the same for y. Inside each loop, append the new current position `(x, y)` to the
path.

<Figure
  src="/img/lesson-m4-04/trace-to-loops.svg"
  alt="The trace table for (0, 0) to (2, 3). Rows 1 and 2, in red, say x + 1 and are bracketed to loop 1: while x < dest_x, x = x + 1, path.append((x, y)). Rows 3 to 5, in green, say y + 1 and are bracketed to loop 2, the same loop for y."
  caption="Each row is one trip around a loop."
/>

Going left or down, the same loops subtract 1 instead; that's Step 3.

## This lesson's skeleton

A new kind of work gets a new section in `robot.py`; you'll paste it in at Step 1
below. It is the first section in the file with no driving in it at all: a function that takes two tuples and returns a list.

```python
# ===== MANHATTAN PLANNER =====
# Plans a route across the grid: given where the robot is and
# where it should go, returns the list of (x, y) tuples to
# drive to, across first and then up or down. Pure arithmetic --
# nothing in here touches a sensor or a motor, so every test
# in this section runs on screen with the robot sitting still.

def compute_path(start, destination):
    """Return the (x, y) steps from start to destination, across
    first, then up or down. The start itself is not in the list."""
    path = []
    x, y = start              # where the robot is now
    dest_x, dest_y = destination   # where it is going

    # East: keep stepping right until x matches dest_x
    while x < dest_x:
        x = x + 1             # one step right
        path.append((x, y))   # record the new spot

    # West: copy east, flip < to > and + to -

    # North: copy east, but step y until it matches dest_y

    # South: copy north, flip < to > and + to -

    return path

def test_paper_paths():
    print(compute_path((0, 0), (2, 3)))   # your trace table
    print(compute_path((0, 1), (3, 3)))
    print(compute_path((3, 3), (1, 0)))   # left and down

def test_edge_cases():
    print(compute_path((2, 0), (2, 3)))   # same column
    print(compute_path((0, 2), (3, 2)))   # same row
    print(compute_path((1, 1), (1, 1)))   # same spot
```

This skeleton gives you more than usual: the whole east loop and both tests are
written for you. Your job is the other three loops, and each one is a copy of the east
loop with a small change. The tests are **paper tests** — they print a path, you
compare it with your answer key, and nothing moves. The robot can stay on the desk.

### Step 3 · West and south: copy and flip

The fix is **two more while loops**, and you already have both, backwards. West is the
east loop flipped: copy it under the west comment, then flip the comparison (`<`
becomes `>`) and the step (`+ 1` becomes `- 1`). South is the north loop, flipped the
same way.

**Why two x loops can sit next to each other:** a while loop checks its condition
before its first trip. To go left, x is already bigger than `dest_x`, so the east
loop's `x < dest_x` is False on that first check and the east loop never runs. Only
the west loop moves x. Going right, it's the other way round. The two y loops work the
same way, so no `if/else` is needed.

<Figure
  src="/img/lesson-m4-04/one-x-loop-runs.svg"
  alt="Going left with x = 3 and dest_x = 1. The east loop, while x < dest_x, is grayed out: 3 < 1 is False on the first check, so it never runs. The west loop, while x > dest_x, is highlighted: 3 > 1 is True, so it runs twice and x goes 3, 2, 1."
  caption="For any trip, at most one of the two x loops runs. The same goes for the two y loops."
/>

The comments keep the two x loops together, before the two y loops, so the path always
goes across first.

<TeacherNote title="Redirect anyone reaching for if/else">

The four-loop design is the lesson's big idea: *a while loop whose condition starts
False simply does nothing.* Students who've seen conditionals will try to wrap this in
`if x < dest_x ... elif x > dest_x`. Steer them back — the four loops are simpler and
handle every case, including same-position (all four skipped → `[]`). Check that
tuple unpacking from Lesson 4-2 (`x, y = start`) stuck, and take real time on the
double parentheses in `path.append((x, y))`: the outer pair is the function call, the
inner pair is the tuple.

</TeacherNote>

## Activity · The edge cases

Good algorithms handle the awkward inputs without special code. The second test in
your skeleton, `test_edge_cases()`, has three of them: **same column**, `(2, 0)` to
`(2, 3)`; **same row**, `(0, 2)` to `(3, 2)`; and **same spot**, `(1, 1)` to `(1, 1)`.
They are paths 4 to 6 in your answer key. Set the run line to `test_edge_cases()`, run
it, and check all three lines against your key.

Same column (same x) means the two x loops are skipped; same row (same y) skips the
y loops; same position skips all four and returns `[]`. Nothing special written — the
loops just don't run when there's no distance to cover.

<Reveal title="Check your compute_path()" hint="write and test it first">

```python
def compute_path(start, destination):
    """Return the (x, y) steps from start to destination, across
    first, then up or down. The start itself is not in the list."""
    path = []
    x, y = start              # where the robot is now
    dest_x, dest_y = destination   # where it is going

    # East: keep stepping right until x matches dest_x
    while x < dest_x:
        x = x + 1             # one step right
        path.append((x, y))   # record the new spot

    # West: copy east, flip < to > and + to -
    while x > dest_x:
        x = x - 1
        path.append((x, y))

    # North: copy east, but step y until it matches dest_y
    while y < dest_y:
        y = y + 1             # one step up
        path.append((x, y))

    # South: copy north, flip < to > and + to -
    while y > dest_y:
        y = y - 1
        path.append((x, y))

    return path
```

East was given, north is its copy, and west and south are those two flipped. If yours
is laid out differently and passes both tests, keep yours.

</Reveal>

## Real-world connections

"Move one axis, then the other" and Manhattan distance show up all over computing:

<CardGrid>
  <InfoCard tag="Games" title="Grid movement">
    Turn-based and tile games measure moves in Manhattan steps — no diagonal shortcuts.
  </InfoCard>
  <InfoCard tag="AI" title="Pathfinding heuristics">
    Manhattan distance is a classic "how far, roughly?" estimate that guides search algorithms like A*.
  </InfoCard>
  <InfoCard tag="Data" title="Clustering">
    Some machine-learning methods group points by Manhattan (taxicab) distance instead of straight-line distance.
  </InfoCard>
</CardGrid>

## Wrap-up

- What does "across first, then up or down" produce? (An L-shaped path — predictable and always valid.)
- Why four while loops instead of `if/else`? (Only the relevant loops run; a False condition just skips.)
- Why isn't the starting position in the path? (The robot is already there; `len(path)` = number of steps.)
