## Why "Manhattan"?

Picture the streets of Manhattan in New York. To get from one corner to another, you
can't cut diagonally through the buildings — you walk along the streets and avenues.
The total distance is the number of blocks across **plus** the number of blocks up or
down. That's the **Manhattan distance** (taxi drivers know it too — it's also called
"taxicab distance").

Our robot is in the same situation: it drives along grid lines, never diagonally. So
the distance from one intersection to another is just *steps across + steps up or down* — the
exact idea you computed by hand in Lesson 4-1.

The strategy we'll use is the simplest one that always works: **move across first
until x is right, then move up or down until y is right.** That always traces an
L-shaped path (or a straight line, if x or y is already correct).

## From the trace table to a loop

Look back at your trace table. **Each row is one trip around a loop.** Rows 1 and 2
both say *x +1*: that's one loop going around twice, stepping east. Rows 3 to 5 say
*y +1*: a second loop going around three times, stepping north.

Say the east loop in plain words first: *keep stepping right until your x matches the
end x.* The code unpacks the end tuple into `dest_x` and `dest_y` (Lesson 4-2), so
"until x matches" becomes `while x < dest_x`: as long as x is still short, take another
step. Each trip around does exactly what one row of your table did:

| In your trace table | In the code |
|---|---|
| Action: x +1 | `x = x + 1` |
| New position | `next_spot = (x, y)` |
| Path so far | `path.append(next_spot)` |

When x reaches `dest_x` the condition is False and the loop stops, just as you stopped
writing *x +1* rows once you reached x = 2.

## This lesson's skeleton

A new kind of work gets a new section. Paste this into `robot.py` above `RUN`, after
the GRID DRIVING section. It is the first section in the file with no driving in it at
all: a function that takes two tuples and returns a list.

```python
# ===== MANHATTAN PLANNER =====
# Plans a route across the grid: given where the robot is and
# where it should go, returns the list of (x, y) tuples to
# drive to, across first and then up or down. Pure arithmetic --
# nothing in here touches a sensor or a motor, so every test
# in this section runs on screen with the robot sitting still.

def compute_path(start, end):
    """Return the (x, y) steps from start to end, across
    first, then up or down. The start itself is not in the list."""
    path = []
    x, y = start              # where the robot is now
    dest_x, dest_y = end      # where it is going

    # East: keep stepping right until x matches dest_x
    while x < dest_x:
        x = x + 1             # one step right
        next_spot = (x, y)    # the spot it just stepped to
        path.append(next_spot)

    # West: copy east, flip < to > and + to -

    # North: copy east, but step y until it matches dest_y

    # South: copy north, flip < to > and + to -

    return path

def test_paper_paths():
    print(compute_path((0, 0), (2, 3)))   # your trace table
    print(compute_path((0, 1), (3, 3)))
    print(compute_path((3, 3), (1, 0)))   # left and down

def test_edge_cases():
    print(compute_path((2, 0), (2, 3)))   # same column
    print(compute_path((0, 2), (3, 2)))   # same row
    print(compute_path((1, 1), (1, 1)))   # same spot
```

This skeleton gives you more than usual: the whole east loop and both tests are
written for you. Your job is the other three loops, and each one is a copy of the east
loop with a small change. The tests are **paper tests** — they print a path, you
compare it with your trace, and nothing moves. The robot can stay on the desk.

### Step 2 · West and south: copy and flip

The fix is **two more while loops**, and you already have both, backwards. West is the
east loop flipped: copy it under the west comment, then flip the comparison (`<`
becomes `>`) and the step (`+ 1` becomes `- 1`). South is the north loop, flipped the
same way. No `if/else` needed — for any single trip, at most one x loop and one y loop
will run; the others are skipped because their condition is False from the start. The
comments keep the two x loops together, before the two y loops, so the path always
goes across first.

<TeacherNote title="Redirect anyone reaching for if/else">

The four-loop design is the lesson's big idea: *a while loop whose condition starts
False simply does nothing.* Students who've seen conditionals will try to wrap this in
`if x < dest_x ... elif x > dest_x`. Steer them back — the four loops are simpler and
handle every case, including same-position (all four skipped → `[]`). Check that
tuple unpacking from Lesson 4-2 (`x, y = start`) stuck. The loops build the tuple on
its own line (`next_spot = (x, y)`) and append it on the next, so there are no double
parentheses to untangle. If a student meets `path.append((x, y))` elsewhere, it's the
same two lines squeezed into one.

</TeacherNote>

## Activity · The edge cases

Good algorithms handle the awkward inputs without special code. The second test in
your skeleton, `test_edge_cases()`, has three of them: **same column**, `(2, 0)` to
`(2, 3)`; **same row**, `(0, 2)` to `(3, 2)`; and **same spot**, `(1, 1)` to `(1, 1)`.
Trace all three on paper and add your prediction to the comment on each call *before*
you set the run line to it.

<Reveal title="Check the three edge cases" hint="predict all three first">

```
[(2, 1), (2, 2), (2, 3)]
[(1, 2), (2, 2), (3, 2)]
[]
```

Same column (same x) means the two x loops are skipped; same row (same y) skips the
y loops; same position skips all four and returns `[]`. Nothing special written — the loops just
don't run when there's no distance to cover.

</Reveal>

<Reveal title="Check your compute_path()" hint="write and test it first">

```python
def compute_path(start, end):
    """Return the (x, y) steps from start to end, across
    first, then up or down. The start itself is not in the list."""
    path = []
    x, y = start              # where the robot is now
    dest_x, dest_y = end      # where it is going

    # East: keep stepping right until x matches dest_x
    while x < dest_x:
        x = x + 1             # one step right
        next_spot = (x, y)    # the spot it just stepped to
        path.append(next_spot)

    # West: copy east, flip < to > and + to -
    while x > dest_x:
        x = x - 1
        next_spot = (x, y)
        path.append(next_spot)

    # North: copy east, but step y until it matches dest_y
    while y < dest_y:
        y = y + 1             # one step up
        next_spot = (x, y)
        path.append(next_spot)

    # South: copy north, flip < to > and + to -
    while y > dest_y:
        y = y - 1
        next_spot = (x, y)
        path.append(next_spot)

    return path
```

East was given, north is its copy, and west and south are those two flipped. If yours
is laid out differently and passes both tests, keep yours.

</Reveal>

## Real-world connections

"Move one axis, then the other" and Manhattan distance show up all over computing:

## Wrap-up

- What does "across first, then up or down" produce? (An L-shaped path — predictable and always valid.)
- Why four while loops instead of `if/else`? (Only the relevant loops run; a False condition just skips.)
- Why isn't the starting position in the path? (The robot is already there; `len(path)` = number of steps.)
