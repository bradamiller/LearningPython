## A name for the algorithm

There are many ways to plan a route between two points. Each method, called an
**algorithm**, has its own strengths. The Manhattan planner is fast and easy to write, but it
fails if a road is blocked; later you'll build more robust planners. When every planner makes
the same promises (its **interface**), a program can swap one for another as the need changes.
That's why the Manhattan planner gets a unique name that reflects its algorithm:
`compute_manhattan_path()`.

## What the function promises

A function is a kind of contract: give me these inputs, and I guarantee this output. Write
the guarantee down, right under the `def` line, in a **docstring** — a string in triple
quotes that Python keeps attached to the function:

```python
def compute_manhattan_path(start, destination):
    """Compute a Manhattan path from start to destination.

    start:       an (x, y) tuple -- where the robot is now
    destination: an (x, y) tuple -- where it needs to go

    Returns a list of (x, y) tuples the robot should move to,
    not including the start itself.
    """
    path = []
    ...
```

The function promises three things:

1. The path **never includes the start.**
2. The path **ends at the destination.**
3. The path is **empty** if you're already there, because every `while` loop is skipped.

Every planner in this course, Manhattan now and BFS and Dijkstra later, makes the same
three promises.

The MANHATTAN PLANNER section of `robot.py` with the new name and docstring, plus the run block; the rest of the file is as the Lesson 4-3 teacher copy left it. The whole file at

```python
# ===== MANHATTAN PLANNER =====
# Plans a route across the grid: given where the robot is and
# where it should go, returns the list of (x, y) tuples to
# drive to, across first and then up or down. Pure arithmetic --
# nothing in here touches a sensor or a motor, so every test
# in this section runs on screen with the robot sitting still.

def compute_manhattan_path(start, destination):
    """Compute a Manhattan path from start to destination.

    start:       an (x, y) tuple -- where the robot is now
    destination: an (x, y) tuple -- where it needs to go

    Returns a list of (x, y) tuples the robot should move to,
    not including the start itself.
    """
    path = []
    x, y = start              # where the robot is now
    dest_x, dest_y = destination   # where it is going

    # East: keep stepping right until x matches dest_x
    while x < dest_x:
        x = x + 1             # one step right
        path.append((x, y))   # record the new spot

    # West: copy east, flip < to > and + to -
    while x > dest_x:
        x = x - 1
        path.append((x, y))

    # North: copy east, but step y until it matches dest_y
    while y < dest_y:
        y = y + 1             # one step up
        path.append((x, y))

    # South: copy north, flip < to > and + to -
    while y > dest_y:
        y = y - 1
        path.append((x, y))

    return path

def test_paper_paths():
    print(compute_manhattan_path((0, 0), (2, 3)))   # your trace table
    print(compute_manhattan_path((0, 1), (3, 3)))
    print(compute_manhattan_path((3, 3), (1, 0)))   # left and down

def test_edge_cases():
    print(compute_manhattan_path((2, 0), (2, 3)))   # same column
    print(compute_manhattan_path((0, 2), (3, 2)))   # same row
    print(compute_manhattan_path((1, 1), (1, 1)))   # same spot

# ===== RUN =====
board.wait_for_button()
test_paper_paths()
```

## Unit testing

A **unit test** checks one small piece of a program, usually one function, on its own: give it
inputs you chose and compare what it returns with the answer you worked out. Professional
software runs thousands of them every time the code changes, so a mistake is caught minutes
after it is made, by a test, not weeks later by a user. Your planner is an ideal unit:
tuples in, list out.

A robot driving into a wall tells you *something* is wrong, but not *what* or *where*.
A failing test on screen tells you the exact input that produced the wrong output.

This works because of **separation of concerns**: `compute_manhattan_path()` only
*computes* a path, and the driving functions (Lesson 4-6) *drive* it. The planner is
handed the robot's position as a parameter, so there is nothing to set up before a
test: tuples in, list out. Each part can be checked on its own:

| Problem | Where it runs | What you test |
|---|---|---|
| Computing the path | Any computer | Does the path make sense? |
| Driving the path | On the robot | Does the robot follow it? |

## Expected vs. actual

Decide what the answer *should* be **by hand**, then check whether the code agrees. Hand-trace (0,0) → (2,3) — right 2, then up 3 — to get the
expected path, then compare:

```python
expected = [(1, 0), (2, 0), (2, 1), (2, 2), (2, 3)]

actual = compute_manhattan_path((0, 0), (2, 3))

if actual == expected:
    print("Test 1: PASS")
else:
    print("Test 1: FAIL")
    print("  Expected:", expected)
    print("  Actual:  ", actual)
```

## This lesson's skeleton

That compare-and-report pattern repeats for every case, so it becomes a function.
Paste this into `robot.py` at the end of the MANHATTAN PLANNER section — it is a
*harness*: a function whose only job is to test another one. Each `run_test()` call is one
unit test.

```python
# --- Lesson 4-4: the test harness ---

# with one you traced by hand, printing PASS or FAIL. A
# planner test from here on is a list of run_test() calls.

def run_test(test_name, start, destination, expected):
    """Plan start -> destination and compare the result
    with expected; print test_name with PASS or FAIL."""
    pass
```

The body is the expected-vs-actual block above with the four values coming in as
parameters: on a FAIL, print both lists so the difference is on screen. Write it, then
the test that uses it.

## Activity · A suite of cases

Each case is now a single line, and a good suite covers **every direction and every
edge case**, including all three promises. Write `test_planner()`: six `run_test()` calls. Here's one case worked out,
and the five your suite still needs:

```python
run_test("Forward right", (0, 0), (2, 3), [(1,0), (2,0), (2,1), (2,2), (2,3)])
run_test("Backward left", (2, 3), (0, 0), [ ... ])   # trace it, then fill it in
run_test("Same column",   (1, 0), (1, 3), [ ... ])
run_test("Same row",      (0, 2), (3, 2), [ ... ])
run_test("Same spot",     (1, 1), (1, 1), [ ... ])
run_test("One step",      (0, 0), (0, 1), [ ... ])
```

**Work each `expected` out by hand before you run anything.** If a test fails, either
your trace or your code is wrong, and finding out which is the skill.

Set the run line to `test_planner()`. Six PASS lines is the goal; the robot does not
move.

<Reveal title="Check your run_test()" hint="write it and run all six cases first">

```python
def run_test(test_name, start, destination, expected):
    """Plan start -> destination and compare the result
    with expected; print test_name with PASS or FAIL."""
    actual = compute_manhattan_path(start, destination)
    if actual == expected:
        print(test_name, "- PASS")
    else:
        print(test_name, "- FAIL")
        print("  Expected:", expected)
        print("  Actual:  ", actual)
```

```python
# --- Lesson 4-4: the test harness ---

# with one you traced by hand, printing PASS or FAIL. A
# planner test from here on is a list of run_test() calls.

def run_test(test_name, start, destination, expected):
    """Plan start -> destination and compare the result
    with expected; print test_name with PASS or FAIL."""
    actual = compute_manhattan_path(start, destination)
    if actual == expected:
        print(test_name, "- PASS")
    else:
        print(test_name, "- FAIL")
        print("  Expected:", expected)
        print("  Actual:  ", actual)

def test_planner():
    run_test("Forward right", (0, 0), (2, 3), [(1,0), (2,0), (2,1), (2,2), (2,3)])
    run_test("Backward left", (2, 3), (0, 0), [(1,3), (0,3), (0,2), (0,1), (0,0)])
    run_test("Same column",   (1, 0), (1, 3), [(1,1), (1,2), (1,3)])
    run_test("Same row",      (0, 2), (3, 2), [(1,2), (2,2), (3,2)])
    run_test("Same spot",     (1, 1), (1, 1), [])
    run_test("One step",      (0, 0), (0, 1), [(0,1)])

# ===== RUN =====
board.wait_for_button()
test_planner()
```

## Activity · Debug a failing test

When a test fails, don't guess — add print statements inside `compute_manhattan_path`
to watch the logic run. One at the top, and one inside each loop right after the
`append`:

```python
    print("Computing from", start, "to", destination)   # first line
    ...
        print("  added:", (x, y))                          # in each loop
```

The trace shows exactly which loop ran and what it appended. Once you've found and fixed
the bug, **remove the debug prints** so the output stays clean. (Try it: change one `+ 1`
to `- 1`, run `test_planner()`, and watch a test catch the bug — then change it back.)

## Wrap-up

- Why `compute_manhattan_path` and not `compute_path`? (Module 5 adds `compute_bfs_path`; the name says which.)
- What are the three promises? (No start in the path; ends at the destination; `[]` when already there.)
- Why test on screen before the robot? (Faster, and it points to the exact broken input.)
- Where does the expected path come from? (Hand-calculation, before you run the code.)
- What makes a good test suite? (Every direction and edge case, not just one happy path.)

Notice what did *not* happen: `__init__` does not take a start position, and there is
no `self.position`. The rule from this lesson still holds inside a class — the planner
is told where the robot is. The `__init__` is empty because Manhattan has nothing to set
up; BFS in Module 5 will use its `__init__` to hold the list of blocked intersections,
and that's the moment the class earns its keep.

**From here on, use your class.** The lessons ahead are written with the function
name, because that is what every student has; yours is the same call with `planner.`
in front and a shorter name. Where a lesson says `compute_manhattan_path(position,
destination)`, you write `planner.compute_path(position, destination)`, in the final
