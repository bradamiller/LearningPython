Your path is a list of intersections — but the robot has a **heading**, a direction it's
currently facing, and driving forward only works if it's already pointed the right way.
This lesson designs the turning logic on paper: how to figure out which way to face, and
how to turn until you're facing it. The code comes next lesson.

<Objectives>

By the end of this lesson you will be able to:

- Explain why only the row **or** the column changes between adjacent intersections
- Represent heading as a number: 0 = N, 1 = E, 2 = S, 3 = W
- Write `desired_heading(position, next_pos)` returning 0–3 from the coordinate change
- Raise an error when a function is asked something it cannot answer, and say why that
  makes a bug easier to find than letting a wrong value travel
- Count quarter turns with `(desired - heading) % 4`, and explain why 3 clockwise turns become 1 counterclockwise
- Describe how `drive_path` uses both to move through a whole path and hand back where the robot ended up

</Objectives>

## One change at a time → four directions

Look at any two *adjacent* intersections on the grid. Between them, either the row
changes by one **or** the column changes by one — never both (that would be a diagonal,
which the robot can't do). That's exactly four cases, one per compass direction:

| Coordinate change | Direction | Heading number |
|---|---|---|
| row −1 (up) | North | 0 |
| col +1 (right) | East | 1 |
| row +1 (down) | South | 2 |
| col −1 (left) | West | 3 |

The trickiest part to accept: on our grid, **row 0 is at the top** (like a spreadsheet),
so moving *down* means the row number *increases*. Down is South.

## Heading as a number

Store the robot's facing as a number 0–3, clockwise from North: **0 = N, 1 = E, 2 = S,
3 = W.** A handy list converts back to letters for display:

```python
HEADING_NAMES = ["N", "E", "S", "W"]
# HEADING_NAMES[2] -> "S"
```

Why numbers? Because **each clockwise turn just adds 1** — and when you'd reach 4, you
wrap back to 0 (like an odometer rolling over). That single rule is the whole turning
mechanism.

The `desired_heading` function compares where the robot is now with where it's going
next, and returns the matching number. Like the planner, it is *told* the position
rather than remembering it:

```python
def desired_heading(position, next_pos):
    row_diff = next_pos[0] - position[0]
    col_diff = next_pos[1] - position[1]
    if col_diff == 0 and row_diff == -1: return 0   # North
    if row_diff == 0 and col_diff ==  1: return 1   # East
    if col_diff == 0 and row_diff ==  1: return 2   # South
    if row_diff == 0 and col_diff == -1: return 3   # West
    raise ValueError(str(position) + " and " + str(next_pos) + " are not neighbors")
```

Each condition checks *both* differences, which is the "one change at a time" rule from
the top of the lesson written down: North means the row went down by one **and** the
column didn't move at all.

## Say so when you can't answer

That last line is worth as much as the four above it. If none of the four conditions
matched, the two positions aren't a single step apart on the grid — they're diagonal,
or identical, or halfway across the map — and there is simply no heading that answers
the question. `raise` stops the program on the spot and prints the message.

Leave it out and Python does not complain. **A function that runs off the end without
returning anything hands back `None`**, silently. So `desired_heading` returns `None`,
and the next line, `turn_to(heading, None)`, tries to subtract `None` from a number.
*That* is where Python finally stops: an error about `NoneType` and `int`, pointing at
a line inside `turn_to`.

Now go and find that bug. The error is in `turn_to`, so that's where you'd look, and
`turn_to` is perfectly correct. The real problem is somewhere else entirely: whatever
handed `desired_heading` two positions that aren't next to each other. You could read
`turn_to` twenty times and never see anything wrong with it, because there is nothing
wrong with it. And the message tells you nothing about which positions caused it.

With the `raise`, the program stops on the line that *noticed* the problem and tells
you the two positions that caused it. Same bug, ten seconds instead of an afternoon.

That's the real reason to write checks like this, and it's worth doing everywhere, not
just here:

> **When a function is asked something it cannot answer, say so immediately and
> loudly.** Every check like this shortens the distance between where a bug shows up
> and where it actually is — and that distance is most of what makes debugging hard.

A wrong value that gets returned doesn't stay put. It travels into the next function,
and the next, and by the time anything visibly breaks you're a long way from the
mistake. Stopping it at the door is cheaper than chasing it.

<TeacherNote title="This is the debugging lesson, not a Python lesson">

`raise` is new here, but nothing about it needs teaching beyond "the program stops and
prints your message" — students never write `try`/`except` to benefit from it. Don't
turn this into a detour on exception handling.

What is worth ten minutes: ask the class to predict what they'd see if the `raise` were
missing, then how they'd go about finding the cause. The answer — "a robot spinning
forever, and the first place you'd look is the one piece of code that's right" — makes
the point better than any rule. This is the first time the course asks students to write
a line whose only job is to make a *future* problem easier to find, and that idea pays
off for the rest of their programming lives.

If someone asks whether the error can actually happen: with `compute_manhattan_path` feeding it,
no — the planner only ever produces adjacent steps. It becomes reachable the moment they
call `desired_heading` themselves while testing, or wire it into their own project in
Lesson 4-9. That is exactly when a good error message is worth the most.

**Why each condition tests both differences.** Earlier drafts of this function checked
only one — `if row_diff == -1: return 0` — which looks equivalent and isn't. Going from
(2,1) to (3,3) has `row_diff` of 1, so that version returns South and never reaches the
`raise`, for a pair of positions that is plainly not a step apart. A check with a hole
in it is worse than no check, because it buys confidence it hasn't earned. Good thing to
show a fast finisher.

</TeacherNote>

## Turning the short way round

Here's the elegant part. How many clockwise quarter turns get you from `heading` to
`desired`? Subtract — and let the wrap-around handle the rest:

```python
turns = (desired - heading) % 4
```

`%` is the remainder operator, and `% 4` is the odometer wrap written as arithmetic.
Try it on every combination you can think of:

| heading | desired | `desired - heading` | `% 4` | meaning |
|---|---|---|---|---|
| 0 (N) | 1 (E) | 1 | 1 | one clockwise turn |
| 2 (S) | 1 (E) | −1 | 3 | three clockwise turns |
| 1 (E) | 1 (E) | 0 | 0 | already facing it |
| 3 (W) | 0 (N) | −3 | 1 | one clockwise turn |
| 0 (N) | 2 (S) | 2 | 2 | turn around |

The negative cases are the interesting ones: Python's `%` always gives a result from 0
to 3 here, so −1 becomes 3 and −3 becomes 1, which is exactly what walking round the
compass clockwise gives you. One line replaces a loop, a counter and a wrap-around `if`.

Three clockwise turns is the long way round, though — the robot would spin 270° when 90°
the other way does the same job. So the one special case: **3 clockwise is 1
counterclockwise.**

```python
def turn_to(heading, desired):
    turns = (desired - heading) % 4
    if turns == 3:
        turn_counterclockwise()
    else:
        for i in range(turns):
            turn_clockwise()
    return desired
```

`turn_clockwise()` and `turn_counterclockwise()` are the Module 2 functions that turn
the robot until the sensors find the next line. The function returns the new heading,
which is simply `desired`, so the caller can write `heading = turn_to(heading, needed)`
and keep its own record up to date — the same "told, not remembered" rule as the planner.

<TeacherNote title="Paper-heavy on purpose — fill in the table, don't count ahead">

Resist jumping to code. Students need to work the `% 4` table by hand, especially the
negative rows, before Lesson 4-8. Get them physically standing and turning clockwise one
step at a time, calling out 0, 1, 2, 3, 0 — the kinesthetic bit cements it — then ask
"from South to East, which way is shorter?" and let them feel the 270° vs 90° answer.
The grid orientation (row 0 on top, "down is South") is the #1 confusion; draw it,
point at it, quiz it. Odometer analogy for the wrap: "…3, and one more is 0, not 4."
`%` on negative numbers surprises anyone who has used other languages; in Python the
result takes the sign of the divisor, so `-1 % 4` is 3. Show it in the REPL.

Why not always turn clockwise, as an earlier version of this lesson did? Three sensor-
ended turns take three times as long as one and give the line sensors three chances to
miss. Brad's rule from the robotics side: time-based turns are never reliable, sensor
based ones are — but fewer is still better.

</TeacherNote>

## Activity · Putting it together: `drive_path`

With those two helpers, driving the whole path is short — for each intersection, figure
out the heading, turn to it, drive forward one, update position:

```python
def drive_path(path, position, heading):
    for next_pos in path:
        needed = desired_heading(position, next_pos)
        heading = turn_to(heading, needed)
        track_to_intersection()          # drive to the next intersection
        position = next_pos
    return position, heading
```

`track_to_intersection()` is the Module 2 function that follows the line until both
sensors hit a crossing — that's how the robot drives exactly one intersection without
measuring any distance. The function returns `position` and `heading` at the end,
because the caller will want to plan the *next* path from wherever the robot ended up.
This is the paper version; Lesson 4-8 adds one real-world wrinkle to it.

Trace the path `[(1,0), (2,0), (2,1), (2,2)]` starting at (0,0) heading 0 (N):

```
At (0,0) N, next (1,0): row+1 -> want S(2). (2-0)%4 = 2: two clockwise. drive to (1,0).
At (1,0) S, next (2,0): row+1 -> want S(2). (2-2)%4 = 0: no turn.      drive to (2,0).
At (2,0) S, next (2,1): col+1 -> want E(1). (1-2)%4 = 3: one ccw.      drive to (2,1).
At (2,1) E, next (2,2): col+1 -> want E(1). (1-1)%4 = 0: no turn.      drive to (2,2).
```

Notice `position` gets updated every step — otherwise the *next* `desired_heading`
would compare against the wrong current spot. And `heading` is updated from `turn_to`'s
return value for the same reason.

## Wrap-up

- Between adjacent intersections, what can change, and how many cases result? (Row *or* column, four cases.)
- Why store heading as a number? (Each clockwise turn adds 1; `% 4` is the wrap.)
- What does `turn_to` do when you're already facing the right way? (`(d - h) % 4` is 0 — zero turns.)
- When does it turn counterclockwise? (When the answer is 3 — the long way round.)
