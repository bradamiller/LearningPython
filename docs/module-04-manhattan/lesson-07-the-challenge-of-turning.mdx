Your path is a list of intersections — but the robot has a **heading**, a direction it's
currently facing, and driving forward only works if it's already pointed the right way.
This lesson opens the last section of `robot.py`, the NAVIGATOR, and designs the turning
logic: how to figure out which way to face, and how to turn until you're facing it. The
first piece is pure arithmetic, so you write and test it today, on screen; the two that
move the robot are designed on paper here and written next lesson.

<Objectives>

## One change at a time → four directions

Look at any two *adjacent* intersections on the grid. Between them, either x
changes by one **or** y changes by one — never both (that would be a diagonal,
which the robot can't do). That's exactly four cases, one per compass direction:

| Coordinate change | Direction | Heading number |
|---|---|---|
| y +1 (up, away from you) | North | 0 |
| x +1 (right) | East | 1 |
| y −1 (down, toward you) | South | 2 |
| x −1 (left) | West | 3 |

The part to keep straight: x comes first in the tuple, but North and South change the
*second* number. **North is away from you**, so moving North makes y *bigger*, and
moving South makes it smaller.

## Heading as a number

Store the robot's facing as a number 0–3, clockwise from North: **0 = N, 1 = E, 2 = S,
3 = W.** A handy list, `HEADING_NAMES`, converts back to letters for display —
`HEADING_NAMES[2]` is `"S"` — and it is the one setting of the section you're about to
paste.

Why numbers? Because **each clockwise turn just adds 1** — and when you'd reach 4, you
wrap back to 0 (like an odometer rolling over). That single rule is the whole turning
mechanism.

## This lesson's skeleton

The last section of the file. Paste it into `robot.py` above `RUN`, after the
MANHATTAN PLANNER section: the heading names, and the one function you write today.

```python
# ===== NAVIGATOR =====
# Drives a planned path. The MANHATTAN PLANNER section says
# WHERE to go (a list of intersections); this section works
# out which way to face at each one and does the driving with
# the LINE TRACKING functions. It is the only code that knows
# the robot's position and heading, and it hands both back.
HEADING_NAMES = ["N", "E", "S", "W"]    # HEADING_NAMES[2] -> "S"

def desired_heading(position, next_pos):
    """Return the heading (0-3) that points from position to
    next_pos, which must be one step away; raise if it is not."""
    # 1. x_diff and y_diff: next_pos minus position
    # 2. one if per direction, from the table above; each
    #    checks BOTH differences, because the other one is 0
    # 3. none matched: raise ValueError, naming both positions
    pass
```

`desired_heading` compares where the robot is now with where it's going next, and
returns the matching number from the table. Like the planner, it is *told* the position
rather than remembering it. Step 2 is the table as four `if` lines, and each condition
checks *both* differences, which is the "one change at a time" rule from the top of the
lesson written down: North means y went up by one **and** x didn't move at
all.

## Say so when you can't answer

Step 3 of the outline is worth as much as the four lines above it. If none of the four
conditions matched, the two positions aren't a single step apart on the grid — they're
diagonal, or identical, or halfway across the map — and there is simply no heading that
answers the question. `raise` is new, and it does one thing: it stops the program on
the spot and prints your message.

```python
raise ValueError("what went wrong, in words")
```

`ValueError` is Python's name for "the values I was given make no sense"; the message
is yours. Make it name the two positions — `str(position)` turns a tuple into text you
can add to a string — so the person reading it knows exactly which pair caused it.

Leave the `raise` out and Python does not complain. **A function that runs off the end without
returning anything hands back `None`**, silently. So `desired_heading` returns `None`,
and the next line, `turn_to(heading, None)`, starts the turning loop you'll design below:
keep turning until the heading equals `None`. It never will. The robot spins in place,
turn after turn, and nothing is printed at all.

Now go and find that bug. The robot is spinning inside `turn_to`, so that's where you'd
look, and `turn_to` is perfectly correct. The real problem is somewhere else entirely:
whatever handed `desired_heading` two positions that aren't next to each other. You could
read `turn_to` twenty times and never see anything wrong with it, because there is nothing
wrong with it. And there is no message at all to tell you which positions caused it.

With the `raise`, the program stops on the line that *noticed* the problem and tells
you the two positions that caused it. Same bug, ten seconds instead of an afternoon.

<Figure
  src="/img/lesson-m4-07/raise-spin.svg"
  alt="Two rows. Without the raise: desired_heading is asked for the heading from (1, 1) to (2, 2), matches none of its cases and silently returns None; turn_to receives None and its loop waits for a heading of None that never comes, so the robot spins forever with no error, while the mistake was back at desired_heading. With the raise: desired_heading stops immediately with a ValueError naming both positions, and turn_to never runs."
  caption="Same bad input both times. Without the raise the program never even stops; with it, it stops where the mistake is."
/>

That's the real reason to write checks like this, and it's worth doing everywhere, not
just here:

> **When a function is asked something it cannot answer, say so immediately and
> loudly.** Every check like this shortens the distance between where a bug shows up
> and where it actually is — and that distance is most of what makes debugging hard.

A wrong value that gets returned doesn't stay put. It travels into the next function,
and the next, and by the time anything visibly breaks you're a long way from the
mistake. Stopping it at the door is cheaper than chasing it.

<TeacherNote title="This is the debugging lesson, not a Python lesson">

`raise` is new here, but nothing about it needs teaching beyond "the program stops and
prints your message" — students never write `try`/`except` to benefit from it. Don't
turn this into a detour on exception handling.

What is worth ten minutes: ask the class to predict what they'd see if the `raise` were
missing, then how they'd go about finding the cause. The answer — "a robot spinning
forever, and the first place you'd look is the one piece of code that's right" — makes
the point better than any rule. This is the first time the course asks students to write
a line whose only job is to make a *future* problem easier to find, and that idea pays
off for the rest of their programming lives.

If someone asks whether the error can actually happen: with `compute_manhattan_path` feeding it,
no — the planner only ever produces adjacent steps. It becomes reachable the moment they
call `desired_heading` themselves — the diagonal call at the end of `test_headings()`
does exactly that, on purpose — or wire it into their own project in Lesson 4-9. That
is exactly when a good error message is worth the most.

**Why each condition tests both differences.** Earlier drafts of this function checked
only one — `if y_diff == 1: return 0` — which looks equivalent and isn't. Going from
(2,1) to (3,3) has `x_diff` of 1, so that version returns East and never reaches the
`raise`, for a pair of positions that is plainly not a step apart. A check with a hole
in it is worse than no check, because it buys confidence it hasn't earned. Good thing to
show a fast finisher.

</TeacherNote>

## Activity · Write it, then ask it the four questions

Write the body of `desired_heading()` from the outline. Then a paper test —
`test_headings()` — that prints the heading from `(1, 1)` to each of its four
neighbors: `(0, 1)`, `(1, 2)`, `(2, 1)` and `(1, 0)`. Work out the four answers from the
table before you run it, and print `HEADING_NAMES[...]` of each result next to the
number so you can read it. Set the run line to `test_headings()`; the robot stays on
the desk.

Then add one more call at the *end* of the test: `(1, 1)` to `(2, 2)`, a diagonal.
Run it again. The four answers print as before, and then the program stops with your
message — read it, and check that it names both positions. That is the `raise` doing
its job, and the reason the call goes last: nothing after it runs.

<Reveal title="Check your desired_heading()" hint="run test_headings() first">

```python
def desired_heading(position, next_pos):
    """Return the heading (0-3) that points from position to
    next_pos, which must be one step away; raise if it is not."""
    x_diff = next_pos[0] - position[0]
    y_diff = next_pos[1] - position[1]
    if x_diff == 0 and y_diff ==  1: return 0   # North
    if y_diff == 0 and x_diff ==  1: return 1   # East
    if x_diff == 0 and y_diff == -1: return 2   # South
    if y_diff == 0 and x_diff == -1: return 3   # West
    raise ValueError(str(position) + " and " + str(next_pos) + " are not neighbors")
```

The four neighbors of `(1, 1)`, in the order the test lists them, come out 3, 0, 1, 2:
W, N, E, S. `(0, 1)` is one step left, so it is West.

</Reveal>

## Turning until you face it

Turning works like every sensor loop in Module 2: keep doing something until a condition
is true. Here the something is one clockwise quarter turn, and the condition is "facing
the heading I want":

```python
# while heading is not desired:
#     one turn_clockwise()
#     heading goes up by 1, wrapping 3 back to 0
```

The wrap is the odometer from the top of the lesson, and `%` (the remainder operator
from Lesson 2-5) does it in one expression:

```python
heading = (heading + 1) % 4
```

For 1, 2 and 3 the remainder is the number itself, and `4 % 4` is 0, so after West comes
North, never a heading 4. Trace the loop from South (2) to East (1):

| pass | heading before | turn | heading after, `(h + 1) % 4` | facing East? |
|---|---|---|---|---|
| 1 | 2 (S) | clockwise | 3 (W) | no |
| 2 | 3 (W) | clockwise | 0 (N) | no |
| 3 | 0 (N) | clockwise | 1 (E) | yes, the loop ends |

Three passes. The loop never asks which way is shorter: it always goes right, so from
South it spins three quarters of the way around to face what is a quarter turn to its
left. It works, and it's simple. Next lesson you'll watch the robot do it, and there's an
optional challenge there for making it quicker.

That is the design of `turn_to(heading, desired)`, the function you write next lesson.
If the robot already faces the right way, the condition is false on the first check and
the loop does nothing, with no special case. `turn_clockwise()` is the Module 2 function
that turns the robot until the sensors find the next line. The function returns
`heading` at the end, which by then equals `desired`, so the caller can write
`heading = turn_to(heading, needed)` and keep its own record up to date — the same
"told, not remembered" rule as the planner.

<TeacherNote title="The long way round is on purpose">

Resist jumping to the driving code — `desired_heading()` is the only function written
today, and it runs on the desk. Get students standing and turning clockwise a quarter at
a time, calling out 0, 1, 2, 3, 0 — the kinesthetic bit cements the wrap. The grid
orientation (x first in the tuple, but North is +y, away from you) is the #1 confusion; draw it, point at it,
quiz it. Odometer analogy for the wrap: "…3, and one more is 0, not 4."

The loop always turns clockwise, and that is deliberate: it is the simplest turn that
always works. In Lesson 4-8 students write it, run a path that bends left, and watch the
robot spin 270°; an optional challenge there has them turn whichever way is fewer turns.
If someone spots the problem today, agree, and point them at that challenge. Why it's
worth doing for those who want it: three sensor-ended turns take three times as long as
one and give the line sensors three chances to miss.

An earlier version of this lesson taught `turns = (desired - heading) % 4` with a special
case for 3. It works, but it leans on `%` with a negative number (`-1 % 4` is 3 in
Python), which surprises nearly everyone; the loop only ever needs `(heading + 1) % 4`.

</TeacherNote>

## Activity · Putting it together: `drive_path` on paper

With those two helpers, driving the whole path is short — for each intersection, figure
out the heading, turn to it, drive forward one, update position. Here is the design as
you'll meet it in next lesson's skeleton:

```python
def drive_path(path, position, heading):
    """Turn and drive through every intersection in path, from
    position facing heading; return the final (position, heading)."""
    # for each next_pos in path:
    #     1. needed = desired_heading(position, next_pos)
    #     2. heading = turn_to(heading, needed)
    #     3. drive to the next intersection (LINE TRACKING)
    #     4. position = next_pos -- the robot is there now
    # return position, heading
    pass
```

Step 3 is `track_to_intersection()`, the Module 2 function that follows the line until
both sensors hit a crossing — that's how the robot drives exactly one intersection
without measuring any distance. The function returns `position` and `heading` at the
end, because the caller will want to plan the *next* path from wherever the robot ended
up. This is the paper version; Lesson 4-8 adds one real-world wrinkle to step 3.

Trace the path `[(1,0), (2,0), (2,1), (2,2)]` starting at (0,0) heading 0 (N), one
line per step — next intersection, heading needed, the headings the turning loop steps
through, what the robot does:

<Reveal title="Check your trace" hint="all four lines first">

```
At (0,0) N, next (1,0): x+1 -> want E(1). N, E: one clockwise.          drive to (1,0).
At (1,0) E, next (2,0): x+1 -> want E(1). already E: no turn.           drive to (2,0).
At (2,0) E, next (2,1): y+1 -> want N(0). E, S, W, N: three clockwise.  drive to (2,1).
At (2,1) N, next (2,2): y+1 -> want N(0). already N: no turn.           drive to (2,2).
```

</Reveal>

Notice `position` gets updated every step — otherwise the *next* `desired_heading`
would compare against the wrong current spot. And `heading` is updated from `turn_to`'s
return value for the same reason.

## Wrap-up

- Between adjacent intersections, what can change, and how many cases result? (x *or* y, four cases.)
- Why store heading as a number? (Each clockwise turn adds 1; `% 4` wraps 4 back to 0.)
- How does `turn_to` know when to stop? (Its loop runs until the heading equals the one it wants; already facing it means zero turns.)
- What's the catch with always turning clockwise? (South to East takes three right turns for what is a quarter turn left. It still gets there; an optional challenge in Lesson 4-8 makes it quicker.)
