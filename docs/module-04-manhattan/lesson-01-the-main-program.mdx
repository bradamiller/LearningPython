## The main program in words

The robot starts at (0, 0) facing North. For each destination on its list:

1. **Plan** the path from where it is now.
2. **Drive** the path, which leaves it somewhere new, facing a new way.

Then it plans the next leg from *there*. So the program keeps track of the robot's
**position** and its **heading**: 0 means North (the rest comes in Lesson 4-4).

## This lesson's skeleton

Paste this into `robot.py` above `RUN`, after the Module 3 code. The two functions are
stubs; Step 2 says what's in them.

```python
# ===== MANHATTAN PLANNER =====
# Plans a route across the grid: given where the robot is and
# where it should go, returns the list of (x, y) tuples to
# drive to. Nothing in here touches a sensor or a motor.

def compute_manhattan_path(start, destination):
    """STUB: a pretend path that jumps straight to the
    destination. Lesson 4-2 replaces it."""
    print("computing path from:", start, "to:", destination)
    return [destination]

# ===== NAVIGATOR =====
# Drives a planned path, one intersection at a time, and hands
# back where the robot ended up and which way it faces.

def drive_path(path, current_position, current_heading):
    """STUB: pretend to drive -- just jump to each
    intersection in path. Lesson 4-4 replaces it."""
    for next_pos in path:
        print("moving: from", current_position, "to:", next_pos)
        current_position = next_pos
    return current_position, current_heading

# --- The main program: the delivery run ---
DELIVERY_STOPS = [(2, 3), (1, 0), (3, 1), (2, 2), (0, 0)]

def test_delivery():
    # 1. robot_position starts at (0, 0); robot_heading
    #    starts at 0, North
    # 2. for each delivery_destination in DELIVERY_STOPS:
    #      plan the path from robot_position, and print it
    #      drive it, and assign the pose it hands back
    #      print "new position:", robot_position,
    #            "heading:", robot_heading
    pass
```

## Activity · Build the main program, one piece at a time

Each step prints something. Before every run, **write down what you expect to see**, then
run it and compare. Set the run line to `test_delivery()`.

### Step 1 · A position, and a list of them

Python stores a position as **one value**, written as on the map: `(0, 0)`. That is a
**tuple**: parentheses, a comma, x first. `(2, 3)` and `(3, 2)` are different intersections.

`DELIVERY_STOPS` in the skeleton is a **list**: square brackets, commas between the items,
here five tuples in order. `for delivery_destination in DELIVERY_STOPS:` runs its body once
per item, first to last. It's the `for` loop from Lesson 1-10, with a list in place of
`range()`.

Replace `pass` with outline step 1, `robot_position = (0, 0)` and `robot_heading = 0`, then
the `for` line, with one line inside the loop:

```python
        print("next stop:", delivery_destination)
```

Before you run it: how many lines will print, and what is the first one?

### Step 2 · Plan with a stub

A **stub** is a stand-in function: same name, same parameters, same kind of return value,
and just enough inside to let the program run. Each stub **prints what the real function
will print**, so the printout shows it was called, and with what. The planner stub returns
`[destination]`: a list with one position in it. That path is wrong (a robot can't jump
three blocks), but a list of positions is all the main program needs today.

Replace the `print` in the loop with outline step 2's first line:

```python
        path = compute_manhattan_path(robot_position, delivery_destination)
        print(path)
```

Before you run it: what will the first two lines be? And where will every
`computing path from:` start?

### Step 3 · Drive, and catch the pose

The driver stub ends with `return current_position, current_heading`. A comma between two
values makes a tuple, so it hands back both at once: where the robot is and which way it
faces, together called its **pose**. Where you call it, give each value its own variable:

```python
        robot_position, robot_heading = drive_path(
            path, robot_position, robot_heading)
```

That's **unpacking**: the first variable gets the first value, the second gets the second.
There must be one variable per value, or Python stops with a `ValueError`.

Don't leave the left side off. Inside `drive_path()`, `current_position = next_pos`
changes only the function's own variable (as in Lesson 2-7), so the return value is the
only way the new pose gets back to the main program.

<TeacherNote title="Why the main program comes first">

An earlier version of this module spent three lessons on parts before anything
connected, and students lost the thread. Here the whole program runs in the first coding
lesson, and every later lesson swaps one stub for the real thing and runs the same test.

Tuples, lists and the `for` loop get a sentence or two each, inside the step that uses
them, on purpose. Don't expand them: `append()` arrives in 4-2, `==` in 4-3, indexing in
4-4.

Watch for the dropped return value: a student who calls `drive_path()` with nothing on
the left sees every `computing path from:` line say `(0, 0)`. It is the most common
Module 4 bug, and it normally surfaces on the floor, on leg 2, where the robot drives leg
1 right and then plans every later leg from home. If someone asks why the stub planner returns a wrong path, that's
the right question: a stub only has to keep the program running.

</TeacherNote>

## Wrap-up

- How does Python store a position, and several destinations? (A tuple, `(x, y)`; a list of tuples, in square brackets.)
- What is a stub for, and why does it print? (It lets the program run before the real function is written; the print shows it was called, and with what.)
- Why must the main program write `robot_position, robot_heading = drive_path(...)`? (Assigning inside a function changes only its own variable; the return value is the only way the new pose gets back.)
