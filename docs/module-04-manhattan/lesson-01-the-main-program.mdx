## The main program in words

The robot starts at (0, 0) facing North. To make a delivery:

1. **Plan** the path from where it is now.
2. **Drive** the path, which leaves it somewhere new, facing a new way.

The next delivery is planned from *there*. So the program keeps track of the robot's
**position** and its **heading**: 0 means North (the rest comes in Lesson 4-4).

## This lesson's skeleton

Paste this into `robot.py` above `RUN`, after the Module 3 code. The two functions are
stubs; Step 1 says what's in them.

```python
# ===== MANHATTAN PLANNER =====
# Plans a route across the grid: given where the robot is and
# where it should go, returns the list of (x, y) tuples to
# drive to. Nothing in here touches a sensor or a motor.

def compute_manhattan_path(start, destination):
    """STUB: a pretend path that jumps straight to the
    destination. Lesson 4-2 replaces it."""
    print("computing path from:", start, "to:", destination)
    return [destination]

# ===== NAVIGATOR =====
# Drives a planned path, one intersection at a time, and hands
# back where the robot ended up and which way it faces.

def drive_path(path, current_position, current_heading):
    """STUB: pretend to drive -- just jump to each
    intersection in path. Lesson 4-4 replaces it."""
    for next_pos in path:
        print("moving: from", current_position, "to:", next_pos)
        current_position = next_pos
    return current_position, current_heading

# --- The main program: the delivery run ---

def test_delivery():
    # 1. robot_position starts at (0, 0); robot_heading
    #    starts at 0, North
    # 2. plan the path from robot_position to (2, 3),
    #    and print it
    # 3. drive it, and assign the pose it hands back
    # 4. print "new position:", robot_position,
    #          "heading:", robot_heading
    pass
```

## Activity · Build the main program, one piece at a time

Each step prints something. Before every run, **write down what you expect to see**, then
run it and compare. Set the run line to `test_delivery()`.

### Step 1 · One position, one plan

  caption="x increases to the right and y increases up, both from (0, 0), the corner nearest you."

Python stores a position as **one value**, written as on the map: `(0, 0)`. That is a
**tuple**: parentheses, a comma, x first. `(2, 3)` and `(3, 2)` are different intersections.

The planner in the skeleton is a **stub**: a stand-in function with the real one's name,
parameters and kind of return value, and just enough inside to let the program run. It
**prints what the real planner will print**, so the printout shows it was called, and with
what. It returns a pretend path that jumps straight to the destination. A robot can't jump
three blocks, but a path is all the main program needs today.

Replace `pass` with outline steps 1 and 2:

```python
    robot_position = (0, 0)
    robot_heading = 0               # facing North
    path = compute_manhattan_path(robot_position, (2, 3))
    print(path)
```

Before you run it: what two lines will print?

<Reveal title="Check your output" hint="predict first">

```text
computing path from: (0, 0) to: (2, 3)
[(2, 3)]
```

The stub prints the first line; your `print(path)` prints the second. The square brackets
hold the path's positions, here just one. Step 4 shows how to make a list like that yourself.

</Reveal>

### Step 2 · Drive, and catch the pose

The driver stub ends with `return current_position, current_heading`. A comma between two
values makes a tuple, so it hands back both at once: where the robot is and which way it
faces, together called its **pose**. Where you call it, give each value its own variable:

```python
    robot_position, robot_heading = drive_path(
        path, robot_position, robot_heading)
```

That's **unpacking**: the first variable gets the first value, the second gets the second.
There must be one variable per value, or Python stops with a `ValueError`.

<Figure
  src="/img/lesson-m4t-01/pose-robot.svg"

The (1, 1) is labeled position; the final 1 is labeled heading, 1 = East. Below: robot_position, robot_heading = drive_path(...), drive_path hands back the pose."
  caption="The pose ((1, 1), 1): at (1, 1), facing East."
/>

Add those lines under `print(path)`, then the last line of the outline:

```python
    print("new position:", robot_position, "heading:", robot_heading)
```

Before you run it: what will the two new lines say?

<Reveal title="Check your output" hint="predict first">

```text

[(2, 3)]
moving: from (0, 0) to: (2, 3)
new position: (2, 3) heading: 0
```

One delivery, four lines. The heading is still 0: the driver stub never turns.

</Reveal>

### Step 3 · A second delivery

Now deliver to (1, 0) as well. Copy your four delivery lines (plan, print, drive, print),
paste the copy under them, and change `(2, 3)` to `(1, 0)` in the copy.

Before you run it: where will the second `computing path from:` line start? Why there?

<Reveal title="Check your output" hint="predict first">

```text
computing path from: (0, 0) to: (2, 3)
[(2, 3)]
moving: from (0, 0) to: (2, 3)
new position: (2, 3) heading: 0
computing path from: (2, 3) to: (1, 0)
[(1, 0)]
moving: from (2, 3) to: (1, 0)
new position: (1, 0) heading: 0
```

The second leg starts at (2, 3), where the first one ended, though the copy never says
(2, 3). `robot_position` holds it, because the drive line assigned the pose that
`drive_path()` handed back.

</Reveal>

That's why the left side of the drive line matters. Inside `drive_path()`,
`current_position = next_pos` changes only the function's own variable (as in Lesson 2-7),
so the return value is the only way the new pose gets back to the main program.

### Step 4 · Now five. Or fifty?

The robot has three more stops: (3, 1), (2, 2), then home to (0, 0). Before you paste three
more copies: how many lines would five deliveries take? Fifty? And from one copy to the
next, what is different?

<Reveal title="Check your thinking" hint="answer first">

Four lines per delivery: 20 lines for five, 200 for fifty. Every copy is the same except
the destination. And each copy is one more place to forget a change.

</Reveal>

When only one value changes, keep the values together and write the code once. A **list**
holds several values in one, in order: square brackets, commas between the items. Put this
above `def test_delivery():` (capitals, because it's a setting for the whole file):

```python
DELIVERY_STOPS = [(2, 3), (1, 0), (3, 1), (2, 2), (0, 0)]
```

A `for` loop runs its body once per item in a list, first to last. Each time round, the
loop variable holds that item:

```python
    for delivery_destination in DELIVERY_STOPS:
```

It's the `for` loop from Lesson 1-10, with a list in place of `range()`.

Rewrite `test_delivery()`: keep the two starting lines, add the `for` line, and indent one
copy of the delivery under it, with `delivery_destination` in place of `(2, 3)`. Delete the
second copy.

Before you run it: how many lines will print, and what will the last one say?

<Reveal title="Check your test_delivery() and its output" hint="predict first">

```python
def test_delivery():
    robot_position = (0, 0)
    robot_heading = 0               # facing North
    for delivery_destination in DELIVERY_STOPS:
        path = compute_manhattan_path(robot_position, delivery_destination)
        print(path)
        robot_position, robot_heading = drive_path(
            path, robot_position, robot_heading)
        print("new position:", robot_position, "heading:", robot_heading)
```

<TeacherNote title="Leading the class to the list and the loop">

Steps 3 and 4 are meant to make students *want* a list and a loop before they see one.

- **After Step 3:** "Where did leg 2 start? Which line put it there?" (The drive line's left
  side.) Seeing the pose carry over now matters: the loop hides it.
- **Step 4, before the list:** "How many lines for fifty stops? What's different in each
  copy?" (Only the destination.) "If only one value changes, what would you want instead
  of copies?" (One copy of the code, and the destinations kept together.)
- Then name the list, and the `for` loop as the 1-10 loop that walks a list instead of
  counting. If someone suggests `range(5)`, that's a good instinct: it repeats, but it gives
  numbers, not stops. The list holds the stops themselves.

Some students will paste all five copies before reading on. Let them run it: the printout
matches the loop's, which is a fine way to check the loop.

</TeacherNote>

<TeacherNote title="Why the main program comes first">

An earlier version of this module spent three lessons on parts before anything
connected, and students lost the thread. Here the whole program runs in the first coding
lesson, and every later lesson swaps one stub for the real thing and runs the same test.

Tuples and unpacking get a sentence or two each, inside the step that uses them. The list
and the `for` loop arrive last, as the fix for copying. Don't expand them: `append()`
arrives in 4-2, `==` in 4-3, indexing in 4-4.

Watch for the dropped return value: a student who calls `drive_path()` with nothing on
the left sees leg 2 start from `(0, 0)`. It is the most common Module 4 bug, and it
normally surfaces on the floor, on leg 2, where the robot drives leg 1 right and then
plans every later leg from home. If someone asks why the stub planner returns a wrong
path, that's the right question: a stub only has to keep the program running.

</TeacherNote>

The new part of `robot.py` as this lesson leaves it, plus the run block.

```python
# ===== MANHATTAN PLANNER =====
# Plans a route across the grid: given where the robot is and
# where it should go, returns the list of (x, y) tuples to
# drive to. Nothing in here touches a sensor or a motor.

def compute_manhattan_path(start, destination):
    """STUB: a pretend path that jumps straight to the
    destination. Lesson 4-2 replaces it."""
    print("computing path from:", start, "to:", destination)
    return [destination]

# ===== NAVIGATOR =====
# Drives a planned path, one intersection at a time, and hands
# back where the robot ended up and which way it faces.

def drive_path(path, current_position, current_heading):
    """STUB: pretend to drive -- just jump to each
    intersection in path. Lesson 4-4 replaces it."""
    for next_pos in path:
        print("moving: from", current_position, "to:", next_pos)
        current_position = next_pos

DELIVERY_STOPS = [(2, 3), (1, 0), (3, 1), (2, 2), (0, 0)]

def test_delivery():

board.wait_for_button()
test_delivery()
```

## Wrap-up

- How does Python store a position? (A tuple, `(x, y)`: parentheses, a comma, x first.)
- What is a stub for, and why does it print? (It lets the program run before the real function is written; the print shows it was called, and with what.)
- Why must the main program write `robot_position, robot_heading = drive_path(...)`? (Assigning inside a function changes only its own variable; the return value is the only way the new pose gets back, so the next leg starts in the right place.)
- Why a list and a `for` loop instead of copies? (Only the destination changes. The loop writes the delivery once, and a new stop is one more item in the list.)
